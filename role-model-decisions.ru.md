# Ролевая модель и последовательность выполнения — решения от 21.11.2026

**Статус:** фиксация решений обсуждения архитектуры Manifest от 21.11.2026.
Источники: architecture-brief v0.2.0; architecture-decisions.ru.md;
architecture-audit.ru.md; workflow/README.en.md; решения обсуждения.
Статусы: **Принято** (П), **Предварительно** (ПП), **Отложено** (О),
**Не решено** (Н).

## 1. Ролевая модель

**П — обязательные роли (7):** Оркестратор; Исполнитель/разработчик;
Code Reviewer; Автор документации; Documentation Reviewer; **Tester**;
**Analyst**.

Tester включён в обязательную ролевую модель: готовит тесты до начала
реализации по TEST FIRST (принцип — Brief §10). Это закрывает замечание
audit E-5 и «Н» из decisions §6.

**П — Analyst:** работает с пользователем на этапе подготовки задачи в
Backlog; анализирует доступную информацию Manifest (контекст проекта,
предыдущие задачи, их зависимости, спецификации); помогает прорабатывать
задачи, выявляет зависимости, предлагает решения; пользователь обсуждает
предложения, корректирует, при необходимости поручает доработку; аналитик
создаёт задачу в Todoing — это согласовано с универсальным правилом
Todoing о создании задач агентами только по разрешению пользователя:
разрешение реализуется через совместную работу с пользователем на этапе
Backlog; пользователь участвует в доработке и
**самостоятельно переводит задачу в статус «К выполнению»**; после этого
работа аналитика над задачей заканчивается — далее действует оркестратор.

**П — Оркестратор:** получает подготовленную и утверждённую задачу
в статусе «К выполнению»; организует исполнение и взаимодействие ролей;
может обращаться к пользователю за уточнениями в ходе выполнения; не
подменяет аналитика на этапе подготовки и не принимает за пользователя
решения об утверждении задач. **П: оркестратор всегда использует модель
GLM-5.3 Flash.**

**П — независимая проверка:** исполнитель не проверяет собственную работу
(Brief §9, §14 п. 5); Code Reviewer и Documentation Reviewer проверяют
независимо в своих областях; при замечаниях Reviewer сообщает оркестратору;
оркестратор повторно запускает исполнителя для исправления; цикл
«исправление → повторная проверка» продолжается до полного устранения
замечаний; при блокирующей ошибке оркестратор эскалирует пользователю.

Роли, определённые в workflow/README.en.md (Architect, Planner), в
обязательный перечень не включены; их судьба — Н (см. §5).

## 2. Модели и агентские сессии

- **П:** одна модель может использоваться для разных ролей; для каждой роли
  создаётся отдельный агент со своей задачей, контекстом и инструкциями;
  закрепление модели за ролью не требуется.
- **ПП:** простые задачи предполагается передавать локальным моделям —
  направление требует практических испытаний.
- **О:** механизм распределения моделей по ролям — до технического
  проектирования и испытаний.
- **П:** настройка агентов, их полномочий и прав чтения/записи в конкретном
  AI-harness — ответственность пользователя (согласуется с Brief §14 п. 9).

## 3. Последовательность выполнения

**П — обязательное правило Manifest:** агенты запускаются последовательно;
параллельный запуск не допускается; ограничение распространяется на все
виды работы (анализ, реализация, проверка).

**П:** в рамках одного проекта одновременно выполняется только одна
глобальная задача; следующая задача выбирается с учётом зависимостей;
при блокировке задачи переход к следующей допускается только при отсутствии
зависимости от заблокированной; при наличии зависимости — ожидание
разблокировки. **П:** исключения для параллельного выполнения сейчас не
предусматриваются.

**П — контроль последовательности:** оркестратор запускает следующего агента
только после завершения предыдущего. **ПП:** техническая блокировка
параллельного запуска — через доступные механизмы конкретного harness
(например, hooks ZCode). **Н:** универсальная техническая гарантия для всех
harness не определена; если harness не предоставляет механизмов — фиксируется
как ограничение интеграции. Manifest не настраивает harness самостоятельно.

## 4. Зависимости задач

**П:** зависимости определяются при участии Analyst; аналитик изучает
предыдущие задачи и контекст при подготовке каждой новой задачи; новая
задача становится последней в списке; следующая задача анализирует
обновлённый список, включая предыдущую задачу; повторный анализ всего
списка после завершения каждой задачи не требуется без конкретной
необходимости.

## 5. Противоречия с действующими документами (не исправлять самостоятельно)

1. **Brief §9 (5 ролей) vs настоящий документ (7 ролей):** Tester и Analyst
   добавлены. Требуется обновление Brief при следующей ревизии.
2. **Brief §6 (допускаются временные ветки «для параллельной независимой
   работы») vs §3 настоящего документа (параллельный запуск запрещён, одна
   задача на проект):** прямое противоречие, требует ревизии Brief §6.
3. **decisions §7 «Н: параллелизм задач» и audit E-6:** настоящим документом
   решено (параллелизм запрещён) — противоречие устранено этим решением,
   но decisions/Brief не обновлены.
4. **decisions §6 «Н: эскалация Оркестратор/Reviewer»:** для цикла
   исправлений задан эскалационный путь (блокирующая ошибка → пользователь);
   общий вопрос разногласия Оркестратор/Reviewer остаётся «Н».
5. **workflow/README.en.md:** роли Architect и Planner не входят в новый
   обязательный перечень; статус этих ролей — Н.

## 6. Нерешённые и отложенные вопросы (свод)

- О: механизм распределения моделей по ролям (§2).
- ПП: локальные модели для простых задач — до испытаний (§2).
- Н: универсальная техническая гарантия последовательности для всех harness (§3).
- Н: статус ролей Architect/Planner workflow-README (§1, §5).
- Н: общий порядок эскалации при разногласии Оркестратор/Reviewer вне цикла
  исправлений (§5 п. 4).
- Связанные открытые вопросы decisions §12 остаются в силе в своих частях,
  не затронутых настоящим документом.
