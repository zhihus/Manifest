# Описание
Запланированные работы для workflow проекта «Манифест». Реализованные
пункты помечены соответствующим статусом; остальные остаются будущими
результатами.

## 1. Процесс верификации

### 1.1. Коммит — реализовано

Модель обязана коммитить; требование зафиксировано в
`workflow/agent-rules.ru.md` (§ Commits) и распространяется на
подключённые проекты изменением `add-init-temp-and-commit-distribution`.

### 1.2. Верификация — реализовано

`scripts/verify.sh` запускается pre-commit hook
(`scripts/hooks/pre-commit`); требование проходить проверку перед
коммитом зафиксировано в тех же правилах агента. Hook относится к
dev-инфраструктуре самого проекта и исключается из дистрибутива
фреймворка (см. 1.6).

### 1.3. Скрипт — реализовано

Универсальный формат; все машинно проверяемые проверки:

* наличие реквизитов, заголовков, нумерации разделов, форматов
  `Version` / `Updated`;
* состав (содержимое) НЕ проверяется — он меняется от проекта к проекту;
* версия и дата проверяются по git-дельте (staged vs HEAD):
  содержимое изменилось → `Updated` обязан отличаться; `approved` →
  `Version` обязан отличаться; `draft` → версия не проверяется;
* `Type` выбирает набор проверок.

### 1.4. Второй hook — `commit-msg` — реализовано

`scripts/hooks/commit-msg` проверяет сообщения коммитов по корневому
`commit-rules.md`: допустимый тип, необязательный scope в нижнем
регистре, тему на английском в нижнем регистре, отсутствие точки в
конце, согласованность маркера breaking change и footer. Ограничение
в 50 символов остаётся рекомендацией, а не жёстким запретом. Hook
относится к dev-инфраструктуре проекта и исключается из дистрибутива
(см. 1.6).

### 1.5. Открытые вопросы — решены

* формат блока метаданных: blockquote (текущая практика в `workflow/`);
* обязанности модели (коммит, верификация) зафиксированы в файле
  правил агента (`workflow/agent-rules.ru.md`), а не в `AGENTS.md`.

### 1.6. Сборка дистрибутива — исключения

В `dist/` manifest-init не должны попадать `scripts/verify.sh` и
`scripts/hooks/` Манифеста: это dev-инфраструктура самого проекта,
а не фреймворка. Будущий change по наполнению `dist/` должен
включать приёмочный сценарий, подтверждающий отсутствие этих файлов.

### 1.7. Расширения скрипта — реализовано

Расширения парсера структуры реализованы:

* `scripts/structure-parser.sh --dir <directory>` рекурсивно
  проверяет обычные файлы с расширением `.md` в нижнем регистре,
  не переходя по символическим ссылкам;
* прежний режим проверки одного файла сохранён;
* ошибки агрегируются по всем найденным файлам;
* документирован запуск через cron и Windows Task Scheduler.
  Manifest не устанавливает и не настраивает планировщики.

## 2. Документационные проекты

### 2.1. Шаблон правил для doc-проектов

`doc-content-rules.template.md` — шаблон правил для
**документационных** проектов (создающих документацию, а не код).
Содержание:

* правила для документационных проектов (аналог
  `code-rules.template.md`, но для документации): Clarity, Accuracy,
  Completeness, Consistency, Structure, Change Discipline,
  Verification;
* временный блок защиты контекстных файлов: при изменении
  agent/rules-файлов — показать изменения, провести ревью и получить
  явное согласие пользователя до коммита (пока нет Git Hook);
* git workflow — не определён (см. 2.2).

Статус: **не реализовано** — в
`docs/templates/doc-content-rules.template.md` находится заглушка
`{{PENDING}}`; пункт считается завершённым только после выполнения
всех требований, включая git workflow.

### 2.2. Открытые вопросы

* git workflow для документационных проектов (ветка на задачу,
  слияние в `develop`, stop-and-report): где его зафиксировать —
  не решено; возможно, в отдельном agent-файле;
* отдельный project-context-файл для документационных проектов:
  возможно, agent-файл; не решено.
