# Описание
Процесс работы с LLM-агентами на пайплайне OpenSpec; правила задач —
в `openspec-rules.md`.

Последовательное выполнение — правило Manifest: агенты запускаются
строго по одному, без параллельного запуска (анализ, реализация,
проверка); в проекте одновременно одна глобальная задача.

## 0. Конфигурация и переключатели workflow

Перед началом работы Оркестратор читает `.manifest/manifest.yaml` и
проверяет SHA-256 по `.manifest/manifest.yaml.checksum`. Проверка целостности
обязательна и не управляется переключателями. При отсутствии файла,
несовпадении checksum, неподдерживаемой версии или некорректном значении
переключателя Оркестратор останавливается и сообщает точный ключ/причину.
Старые конфигурации без `format_version` и секций переключателей не
мигрируются автоматически.

Для `format_version: 1` действуют следующие независимые переключатели:

| Ключ | Включён по умолчанию | Поведение |
|---|---:|---|
| `components.todoing.enabled` | `true` | Использовать Todoing API, задачи, историю и блокировки |
| `components.openspec.enabled` | `false` | Использовать OpenSpec changes и постоянные спецификации |
| `checks.workflow_preflight.enabled` | `false` | Выполнять workflow Preflight |
| `checks.git_hooks.enabled` | `false` | Устанавливать/запускать Git hooks Manifest |
| `checks.git_checks.enabled` | `false` | Выполнять дополнительные Git-проверки Manifest |
| `checks.openspec_validation.enabled` | `false` | Запускать `openspec validate` |
| `checks.tests.enabled` | `false` | Запускать тесты |
| `checks.review_gate.enabled` | `false` | Запускать отдельный Review/verify-гейт |
| `checks.additional_gates.enabled` | `false` | Запускать прочие необязательные контрольные механизмы |

Оркестратор проверяет соответствующий флаг непосредственно перед каждым
этапом. При `false` этап, команда, hook или субагент не запускается;
в журнале этап отмечается `SKIPPED`, а не `PASSED`. Один флаг не изменяет
значения остальных.

Если Todoing включён, а OpenSpec выключен, задачи ведутся в Todoing без
обязательной ссылки на OpenSpec. Если OpenSpec включён, а Todoing выключен,
изменения ведутся в OpenSpec без вызовов Todoing. Когда включены оба
компонента, одна Todoing-задача соответствует одному OpenSpec change:
название задачи Todoing должно в точности совпадать с ID каталога change,
а связь `openspec.change` обязательна.

Переключатель `workflow_preflight` управляет только этапом Preflight
рабочего процесса. Обязательные проверки безопасности самого
`manifest-init.sh` (Git work tree, доступность шаблонов, возможность
безопасной записи и необходимые инструменты) остаются включёнными.
Защита checksum и запрет автоматической перезаписи существующей конфигурации
всегда действуют. Повторное подключение работает аддитивно: добавляет только
отсутствующие элементы, сохраняя существующие файлы и настройки. Эти механизмы
нельзя отключить настройками.

## 1. Роли

Пайплайн существует внутри контекста **Оркестратора** (основная сессия /
дирижёр). Он никогда не выполняет работу специалиста: восстанавливает
состояние пайплайна, запускает нужного субагента на каждом шаге,
проверяет отчёт агента и гейтит переход к следующему шагу. Это
сохраняет ключевую инварианту: **никто никогда не проверяет свою
собственную работу.**

| Шаг | Артефакт | Агент | Вход → Выход |
|---|---|---|---|
| — | состояние пайплайна | Оркестратор (всегда GLM-5.3 Flash) | запускает шаги, гейтит переходы |
| 0 | задача в Todoing (если компонент включён) | Аналитик | Backlog → утверждённая задача «К выполнению» |
| 1 | proposal.md (если OpenSpec включён) | Аналитик | слова пользователя → «зачем / что» |
| 2 | spec.md (если OpenSpec включён) | Аналитик | proposal → сценарии, граничные случаи, PBT |
| 3 | design.md (если OpenSpec включён) | Архитектор | proposal + spec → решение (опционально) |
| 4 | tasks.md (если OpenSpec включён) | Планировщик | spec + design → атомарный чек-лист задач |
| 5.1 | тесты (если checks.tests.enabled) | Тестировщик | свойства спеки → тесты до реализации |
| 5.2 | код или документ | Реализатор / Документатор | tasks + spec → реализация |
| 6 | verify.md (если checks.review_gate.enabled) | Ревьюэр | артефакты + spec → отчёт ✅/❌ |
| 7 | архив (если OpenSpec включён) | Оркестратор | verify весь ✅ → спеки обновлены |

Каждая роль работает в собственной сессии агента (отдельный запуск
субагента); одна модель может обслуживать разные роли, закрепление
модели за ролью не требуется. Оркестратор может совмещать роли на разных
изменениях, но никогда — в рамках одного результата работы (deliverable).
Замечания Ревьюэра передаются Оркестратору, который повторно запускает
Реализатора до полного устранения замечаний; блокирующие ошибки
эскалируются пользователю. Обязательный перечень ролей —
`docs/architecture/architecture-brief.ru.md` §9 (7 ролей, включая Тестировщика и Аналитика).

## 2. Семь шагов и гейты

### 2.1. Proposal (Аналитик)

Отвечает на вопросы *зачем* и *что* меняется, без деталей поведения и
технических решений. Разделы: `Why`, `What Changes`, `Capabilities`.

**Гейт:** `Why` присутствует, `What Changes` непустой, список
capability явно указан. Провал → возврат к Аналитику.

### 2.2. Spec (Аналитик)

Поведенческий контракт: каждое требование proposal развёрнуто в user
stories, сценарии `GIVEN / WHEN / THEN`, граничные случаи и — там, где
ожидается исполняемое поведение — в **свойства для property-based
тестов (P1, P2, …)**. Источник истины для Тестировщика — спецификация,
а не код. Если поведение не описано в спеке — его не существует.

**Гейт:** у каждого требования ≥1 сценария; граничные случаи
перечислены; свойства PBT выведены (для кодовых изменений). Провал →
возврат к Аналитику.

### 2.3. Design (Архитектор)

Технический план: структуры данных, алгоритмы, компромиссы. Не может
противоречить спеке; при конфликте спека правится осознанно
(Аналитиком), а не обходится молча. Опционален для небольших
изменений, обязателен, когда есть выбор между решениями.

**Гейт:** design ссылается на спеку и не вводит требований,
отсутствующих в ней. Провал → возврат к Аналитику (пересмотр спеки).

### 2.4. Tasks (Планировщик)

Атомарные, по отдельности проверяемые задачи, каждая трассируема к
сценарию или свойству. Следует `openspec-rules.md`: нумерация FR,
волновые группы, калибровка размера (одна задача = один запуск
исполнителя, < 10 минут, механический критерий останова), строка
`Maps to scenarios:`.

**Гейт:** каждая задача — чекбокс и трассируется к сценарию/свойству;
волновая структура валидна. Провал → возврат к Планировщику.

### 2.5. Apply (Тестировщик → Реализатор / Документатор)

Две различные роли, именно в этом порядке. Тестировщик запускается только при `checks.tests.enabled: true`; при `false` шаг 5.1 и сам агент пропускаются со статусом `SKIPPED`. Реализация при этом продолжается без запуска тестов.

#### 2.5.1. Тестировщик пишет тесты до реализации

Только из `spec.md` (свойства P1–P3 …), никогда из кода. Благодаря
этому тесты проверяют требования, а не подгоняются под реализацию.

#### 2.5.2. Реализатор пишет реализацию под эти тесты

Вход: `tasks.md` + `spec.md`. Реализатор никогда не правит тесты:
падающий тест — это баг в реализации. Свойства меняются только путём
осознанной правки спеки Аналитиком.

#### 2.5.3. Doc-only путь

Для документационных результатов шаг 5.1 пропускается (нет
исполняемого контракта; свойство «документ соответствует спеке»
проверяется чтением). Роль Реализатора выполняет **Документатор** —
отдельный агент, чья единственная работа — произвести документ по
`spec.md` + `design.md`; задача помечается `doc-only` в `tasks.md`.
Если изменение содержит и код, и документацию, Документатор
запускается отдельной сессией, как и остальные агенты —
последовательно, параллельный запуск запрещён. Ревью всё
равно проводится (шаг 6) — семантическая проверка: полнота,
согласованность, отсутствие требований, которых нет в спеке.

**Гейт:** для кода — тесты не изменялись с момента написания
Тестировщиком; Реализатор не касался файлов тестов. Для doc-only —
задача помечена `doc-only`, артефакт создан, Документатор не правил
файлы спек. Провал → возврат к шагу 5.

### 2.6. Verify (Ревьюэр)

Этап выполняется только при `checks.review_gate.enabled: true`; иначе отдельный Review/verify-гейт и Ревьюэр пропускаются со статусом `SKIPPED`.

Проверка соответствия спеке, а не ревью стиля. Для каждого сценария и
свойства: покрыто тестом и проходит на реализации (код), либо документ
соответствует сценариям и не добавляет ничего нового (doc-only). Тесты
не тавтологичны; все пункты `tasks.md` закрыты. Ревьюэр ничего не
правит — он создаёт `verify.md` (✅/❌) и маршрутизирует провалы:
пробел в тестах → Тестировщику, падающий тест → Реализатору,
противоречие спеке → Аналитику, неполный документ → Документатору.

**Гейт:** в `verify.md` только ✅ → переход к шагу 7. Любой ❌ →
маршрутизация назад и повтор затронутого шага.

### 2.7. Archive (Оркестратор / автоматизация)

Этап выполняется только при `components.openspec.enabled: true`; иначе OpenSpec archive не запускается.

Перед архивированием, если `checks.openspec_validation.enabled: true`, выполните `openspec validate` и остановитесь при ошибке. При `false` команду не запускайте и отметьте проверку `SKIPPED`. Архивирование запускается только при включённом OpenSpec и после выполнения применимых гейтов. Дельта-спека из
`changes/<name>/specs/` вливается в постоянные `openspec/specs/`,
папка изменения перемещается в `changes/archive/<date>-<name>/`.
Механическая операция, обычно через CLI (`openspec archive <name>`).
С этого момента требование — постоянный закон для всех будущих
изменений.

## 3. Связь с openspec-rules.md

* Шаги 1–4 = работа «сильная модель / человек» согласно файлу правил.
* Результат шага 4 = волны, нумерация FR, калибровка размера.
* Шаг 5 = запуски исполнителя: один запуск субагента = одна задача
  (FR); исполнитель коммитит после каждого завершённого этапа.
* Тяжёлая верификация — отдельная задача (шаг 6 в своём запуске).
* Архив (шаг 7) соответствует `openspec/changes/archive/`.

## 4. Язык

Все артефакты (`proposal.md`, `spec.md`, `design.md`, `tasks.md`,
`verify.md`) и контекстные файлы процесса пишутся на английском, если
правила проекта не говорят иного. Тела сценариев внутри спек могут
быть на предметном языке проекта, если этого требует потребляющий их
рантайм (например, русский Gherkin для 1С/Vanessa), при этом сам
документ спеки остаётся на английском.

## 5. Минимальный ранбук (глазами пользователя)

1. Сформулируйте изменение простыми словами; подтверждайте граничные
   случаи, когда спрашивают.
2. Оркестратор ведёт шаги 1–7, запуская по одной роли на шаг и
   сообщая результаты гейтов.
3. Вы вмешиваетесь только когда гейт проваливается настолько, что
   Оркестратор маршрутизирует возврат к вам (вопросы объёма, конфликты
   спек) либо на финальном verify ✅.


## 6. Интеграция с Todoing

Этот раздел применяется только при `components.todoing.enabled: true`. При `false` Оркестратор не вызывает `todoing`, не читает `.todoing/` и не выполняет операции Todoing.

Todoing — источник истины для состояния задач, версий, истории, блокировок и Review. Manifest владеет OpenSpec, Git и политикой оркестрации. Единственный клиент Todoing API — основной Оркестратор.

### 6.1. Bootstrap и Project ID

Поддерживаются два режима использования: обычная установка в PATH и портативная поставка по явному пути. Скрипты резолвера (`scripts/resolve-todoing.sh` / `scripts/resolve-todoing.py`) применяют строгий приоритет и проверяют версию до операций со store:

1. Явный `TODOING_BIN` — должен указывать на существующий файл; отсутствующий файл — остановка.
2. Портативная сборка в кэше релизов Manifest: `.todoing-cache/portable/<VERSION>/<PLATFORM>-<ARCH>/todoing[.exe]`.
3. `todoing` в PATH.

Несовместимая версия — остановка: резолвер никогда не переключается на другой бинарник молча. Кэш релизов (`.todoing-cache/`) хранит скачанные релизы, разделённые по версии и платформе, никогда не смешивается со store задач (`.todoing/`) и не попадает в Git.

1. Убедитесь, что резолвер нашёл бинарный файл и `todoing version` совпадает с требуемой версией (сейчас `1.2.0`); проверьте его совместимость с указанной ниже базовой сборкой. Отсутствие бинарного файла или несовместимая сборка означают остановку с диагностикой. Manifest не устанавливает и не обновляет Todoing. JSON API вызывается как `todoing --json api`: один JSON-запрос передаётся через stdin, один JSON-ответ читается из stdout.

Для полного workflow Manifest требуется Todoing build из commit `6acca6087fbd4b39ad0dcd5f12db52dc4d84b163` или его проверенного потомка. Этот commit закреплён в acceptance CI Manifest. Текущая публичная ветка `todoing-x/main` не содержит `task.external-ref.*`, `task.review.*` и `task.commit.finalize`; бинарный файл из неё несовместим с полным workflow. `todoing version` подтверждает наличие CLI, но не обязательно его исходный commit — происхождение сборки проверяется отдельно.
2. Если `.manifest/project-id` и SQLite store отсутствуют, сгенерируйте UUIDv4 и создайте файл атомарно, без перезаписи существующего файла.
3. Если store существует, а Project ID отсутствует — остановитесь. Не генерируйте новый ID и не вызывайте `store.init`.
4. Если Project ID существует, используйте его без изменения. После подключения к существующему store вызовите `store.info` и `store.verify`; несовпадение ID или ошибка целостности означает остановку.
5. Проверьте `.todoing/config.toml`. Если store уже существует, а конфиг отсутствует — остановитесь: не создавайте конфигурацию с неизвестной политикой поверх существующего store. Если store отсутствует, создайте конфигурацию только при отсутствии legacy Markdown-задач и `index.json`: записывайте её атомарно через временный файл и rename, только если целевой файл всё ещё отсутствует. Существующий конфиг не перезаписывайте: проверьте его и остановитесь при несовместимости.
6. Рекомендуемая конфигурация: `format_version = 1`; статусы `backlog`, `ready`, `in_progress`, `review`, `verified`, `completed`; только `completed` имеет `outcome = "completed"`. Разрешённые переходы: `backlog → ready → in_progress → review`; из `review` — в `in_progress` или `verified`; из `verified` — в `completed`.
7. В `[locking]` задайте `lease_seconds = 720`, `heartbeat_seconds = 60`, `recovery_grace_seconds = 60`. Значения обязательны для описанного ниже режима блокировки.

Рекомендуемое содержимое `.todoing/config.toml` для нового проекта:

```toml
format_version = 1

[locking]
lease_seconds = 720
heartbeat_seconds = 60
recovery_grace_seconds = 60

[[statuses]]
id = "backlog"
label = "Backlog"
enabled = true

[[statuses]]
id = "ready"
label = "Ready"
enabled = true

[[statuses]]
id = "in_progress"
label = "In Progress"
enabled = true

[[statuses]]
id = "review"
label = "Review"
enabled = true

[[statuses]]
id = "verified"
label = "Verified"
enabled = true

[[statuses]]
id = "completed"
label = "Completed"
enabled = true
outcome = "completed"

[[transitions]]
from = "backlog"
to = "ready"

[[transitions]]
from = "ready"
to = "in_progress"

[[transitions]]
from = "in_progress"
to = "review"

[[transitions]]
from = "review"
to = "in_progress"

[[transitions]]
from = "review"
to = "verified"

[[transitions]]
from = "verified"
to = "completed"
```

Создавайте этот файл только если его ещё нет. При существующем конфиге не применяйте snippet автоматически.
8. Для нового проекта вызовите `store.init` ровно один раз с Project ID. Затем проверьте `store.info` и `store.verify`. При существующем store повторный `store.init` запрещён. Legacy-данные не мигрируйте автоматически: сначала dry-run и отдельное подтверждение пользователя.

### 6.2. Контракт API и задача

Каждый вызов — отдельный процесс `todoing api`, одна JSON-команда через stdin и один JSON-ответ через stdout. Envelope содержит `api_version: 1`, `project_id`, `actor_id`, `operation`, `args`; `lock_token` передаётся только в envelope owner-запроса. Ошибки определяйте по машинному `code`, не по тексту сообщения. Токен нельзя помещать в аргументы CLI, prompt субагента, task content, логи или Git.

Пример чтения списка задач (подставьте фактический Project ID):

```bash
printf '%s' '{"api_version":1,"project_id":"<PROJECT_ID>","actor_id":"manifest-orchestrator","operation":"task.list","args":{}}' | todoing --json api
```

Один OpenSpec change соответствует одной Todoing task. При включённых Todoing и OpenSpec название задачи Todoing должно в точности совпадать с ID каталога change; FR-задачи внутри change отдельными Todoing-задачами не становятся:
- Создайте задачу через `task.create` со статусом `backlog`.
- Добавьте project-scoped reference через `task.external-ref.add`: namespace `openspec.change`, value — ID каталога change, relation `implements`, scope `project`.
- Переход `backlog → ready` разрешён только после явного одобрения пользователя. После одобрения зафиксируйте baseline текущей версии через `task.version.approve`.
- Не запускайте реализацию, не приобретайте lock и не переводите задачу в `in_progress` до одобрения.
- Зависимости ведите через `task.dependency.add`, `task.dependency.remove`, `task.dependency.list`. Перед запуском проверьте каждую prerequisite-задачу: её outcome должен быть `completed`. Если зависимость заблокирована или её состояние нельзя проверить, работу не начинайте. Todoing хранит связи и запрещает циклы; решение о готовности принимает Manifest.
- `actor_id` — атрибуция, а не аутентификация. Вызовы отправляет Оркестратор; для Review указывайте стабильный идентификатор роли/сессии Reviewer в envelope.

### 6.2.1. Режим Todoing без OpenSpec

Этот режим применяется, когда `components.todoing.enabled: true`, а
`components.openspec.enabled: false`. Todoing ведёт самостоятельные задачи
проекта; OpenSpec не является обязательной зависимостью.

1. В начале рабочей сессии получите список активных задач через
   `task.list`. Для подходящей существующей задачи используйте её, а не
   создавайте дубликат. Если состояние задачи нельзя проверить (например,
   задача скрыта из списка из-за чужой блокировки), остановитесь и выясните
   состояние; не считайте её отсутствующей.
2. Создавайте задачу через `task.create` только для самостоятельного
   результата работы, а не для каждого шага реализации. Подзадачи,
   технические шаги и промежуточные действия остаются внутри описания
   исходной задачи. Перед созданием проверьте, нет ли уже активной задачи
   с тем же результатом.
3. Новая задача создаётся в `backlog`. В `title` укажите краткий
   результат, в `body` — цель, границы и критерии приёмки. Не добавляйте
   приоритеты: текущая конфигурация Manifest их не использует. Для изменения
   существующей задачи используйте `task.update` только после `task.get`;
   меняются только `title` и `body`. Существенное изменение объёма или критериев
   после утверждения требует нового явного решения пользователя и фиксации
   новой baseline-версии через `task.version.approve`.
4. Только явное поручение пользователя выполнить эту работу разрешает
   переход `backlog → ready`. Просьба обсудить, проанализировать или
   составить план сама по себе не является разрешением на реализацию.
   После разрешения выполните `task.status.set` → `ready`, прочитайте
   актуальную версию через `task.get` и зафиксируйте её через
   `task.version.approve`.
5. Связи предпосылок добавляйте и удаляйте через `task.dependency.add` и
   `task.dependency.remove` только для реальных зависимостей между самостоятельными
   задачами. До начала работы проверьте их через `task.dependency.list`: outcome
   каждой prerequisite-задачи должен быть `completed`. При незавершённой,
   заблокированной или непроверяемой зависимости не начинайте работу.
6. Затем выполните общий протокол §6.3: acquire lock, переход
   `ready → in_progress`, heartbeat перед каждым блокирующим запуском
   субагента. Только Main Orchestrator вызывает Todoing API.
7. После значимого Git commit добавьте его через `task.commit.add`.
   Перед передачей результата на проверку переведите задачу в `review`;
   используйте Review API по §6.4. После одобрения — `verified`.
8. Завершайте задачу после acceptance checks: зафиксируйте итоговый Git SHA
   через `task.commit.finalize`, переведите задачу в `completed` и
   освободите lock. Команды OpenSpec archive и ссылки
   `openspec.change` в этом режиме не используются.
9. Отмену выполняйте только после решения пользователя через
   `task.cancel`; OpenSpec archive не запускайте. При восстановлении после
   сбоя сверяйте Todoing и Git, не выполняя слепых повторов.

`task.list` не показывает задачи, заблокированные другим владельцем.
Manifest допускает только одну активную глобальную задачу и одного Main
Orchestrator на проект; параллельные оркестраторы не запускаются.

### 6.3. Lock custody и исполнение

Оркестратор — единственный владелец Todoing API и lock token:
1. Перед работой вызовите `task.lock.acquire`; сохраните `owner_id`, `lock_token`, `fencing_generation`, `expires_at` в защищённом состоянии основной сессии.
2. Сразу после acquire переведите задачу `ready → in_progress` через `task.status.set`, передав token в envelope.
3. Перед каждым блокирующим запуском субагента выполните `task.lock.heartbeat`. Lease 720 секунд покрывает hard timeout 600 секунд и запас 120 секунд.
4. Во время выполнения субагента heartbeat не отправляется. Субагент не получает token и не вызывает Todoing.
5. Все owner-запросы передают token в envelope и актуальные `owner_id`/generation в args. При `stale_lock` прекратите операции со старым token.
6. После завершения задачи или подтверждённой отмены освободите lock через `task.lock.release`.

`actor_id` — атрибуция, а не аутентификация. Правило «Todoing API вызывает только Main Orchestrator» само по себе является процедурным, а не технической защитой: Todoing не блокирует прямые вызовы другого процесса. Если среда запуска предоставляет ролевым субагентам прямой доступ к CLI, строгая изоляция ролей и запрет самостоятельного `backlog → ready` технически не обеспечены. Не заявляйте обратное; зафиксируйте ограничение и эскалируйте его.

### 6.4. Статусы и Review

- Перед передачей результата Reviewer переведите задачу в `review` через `task.status.set`.
- Review запишите через `task.review.add`: стабильный `review_id`, проверяемый `version_no`, `reviewer`, outcome и упорядоченный массив `comments`.
- При `approved` переведите задачу в `verified`.
- При `changes_requested` Todoing атомарно увеличивает `revision_count` один раз; после записи Review верните задачу в `in_progress`.
- Повтор с тем же `review_id` и payload — no-op; иной payload с тем же ID — конфликт. Не имитируйте счётчик числом версий.

### 6.5. Завершение и отмена

Успешное завершение выполняется строго по порядку:
1. Review approved, статус `verified`.
2. Acceptance checks Todoing ↔ OpenSpec ↔ Git.
3. Выполните `openspec archive <change-id> --yes`: delta specs вливаются в permanent specs.
4. Git merge согласно правилам проекта.
5. `task.commit.finalize` с SHA итогового merge commit.
6. `task.status.set` → `completed` (переход сам устанавливает outcome `completed`).
7. `task.lock.release`.

Любой агент может рекомендовать отмену с обоснованием; подтвердить её может только пользователь. После подтверждения выполните строго по порядку:
1. `task.cancel` с причиной.
2. Выполните `openspec archive <change-id> --yes --skip-specs`: change архивируется без изменения permanent specs.
3. `task.lock.release`.

Не удаляйте external reference. Не заменяйте отмену одним лишь архивированием.

### 6.6. Snapshot и восстановление

- Создавайте snapshot через `store.snapshot`, а не копированием активного SQLite-файла.
- Перед передачей или восстановлением проверьте его через `store.snapshot.verify`; сохраняйте SHA-256.
- `store.snapshot` и `store.snapshot.restore` запрещены при активных task locks.
- `store.snapshot.restore` восстанавливает только Todoing SQLite, требует snapshot того же Project ID и схемы, создаёт safety snapshot в `.todoing/backups/`.
- Restore — разрушающая операция: выполняйте её только по явному разрешению пользователя, передавая сохранённый `expected_sha256`.
- Restore не отменяет Git commits и OpenSpec archive. После восстановления обязательно сверьте Todoing, OpenSpec и Git до продолжения работы.

### 6.7. Recovery

Восстановление Todoing из snapshot откатывает только SQLite-состояние Todoing; оно не отменяет OpenSpec archive и Git commits. После restore сверяйте все три системы до любых повторных операций.

После прерывания сначала сверяйте фактическое состояние: Todoing через `task.get`, `task.version.list`, `task.history.list`, `task.review.list`, `task.external-ref.list` и `task.dependency.list`; OpenSpec (change и archive); Git (ветка, merge, SHA). Не повторяйте non-idempotent операции вслепую.
- Если ответ на `task.lock.release` потерян:
  1. Сначала выполните `task.lock.heartbeat`.
  2. Повторите release только после успешного подтверждения владения.
- `lock_expired`: дождитесь истечения lease и recovery grace (60 секунд), затем вызовите `task.lock.recover`; используйте только новый token и fencing generation. Recovery атомарен: конкурирующие вызовы сериализуются транзакцией и CAS по `fencing_generation`; первый успешный вызов получает новый token, последующий получает `task_locked`. После recovery проверьте актуальную версию задачи и состояние артефактов до продолжения работы.
- `stale_lock`: старый token больше не использовать.
- Сценарии частичного сбоя:
- **S1 — после OpenSpec archive, до Git merge:** не повторяйте archive; проверьте, что change находится в архиве и permanent specs обновлены, затем выполните Git merge.
- **S2 — после Git merge, до final marker:** получите фактический SHA merge commit и вызовите `task.commit.finalize`; повтор с тем же SHA безопасен.
- **S3 — после перехода в `completed`, до release:** проверьте владение через `task.lock.heartbeat`; повторяйте release только после успешного heartbeat. `stale_lock` означает, что старый token больше не действителен.
- **S4 — lease истёк во время субагента:** после lease expiry и recovery grace выполните явный `task.lock.recover`, получите новый token/generation, проверьте версию задачи и артефакты; старый token не используйте.
- **S5 — сбой при отмене:** сверяйте outcome, archive и lock. Если outcome уже `cancelled`, не повторяйте `task.cancel`; завершите только недостающие шаги. При отмене delta specs не вливаются в permanent specs.
- После merge без final marker получите фактический merge SHA и вызовите `task.commit.finalize`.
- После `completed` не повторяйте `task.status.set` или `task.complete`; проверьте состояние и освободите lock после проверки владения.
- При отмене не повторяйте `task.cancel`, если outcome уже `cancelled`; продолжайте только недостающие шаги после сверки.

Todoing, OpenSpec и Git не образуют общей транзакции. При неоднозначном состоянии остановитесь и эскалируйте пользователю.


### Индивидуальное подключение файлов контекста

Каждый файл контекста управляется собственным переключателем `context_files.<id>.enabled` в `.manifest/manifest.yaml`. Поддерживаемые ID: `agents`, `llm-navigation`, `versioning`, `releases`, `logging`, `code-rules`, `test-rules`, `commit-rules`, `version`, `llmignore`. Все переключатели новых проектов по умолчанию `false`. Файл подключается только при включённом собственном переключателе. Отключение не удаляет уже существующий файл. Существующие конфигурации без секции `context_files` не изменяются автоматически: подключение файлов контекста откладывается до отдельной согласованной миграции.
