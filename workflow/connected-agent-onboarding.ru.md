# Description
Временный обязательный контекст агента для проектов, подключённых к Manifest.

## 1. Назначение и область действия

Эта инструкция определяет, как агент подключённого проекта использует Manifest, OpenSpec и Todoing как единую систему управления изменениями.

Она действует до появления механизма Manifest, который формирует и подключает отдельные файлы контекста по назначению и конфигурации проекта. После появления такого механизма правила должны быть распределены по соответствующим файлам без потери требований.

Инструкция не заменяет AGENTS.md проекта, его архитектурные документы, пользовательские решения и нормативные контракты Manifest/OpenSpec/Todoing. При расхождении агент останавливается и сообщает о конфликте; он не выбирает удобное толкование самостоятельно.

## 2. Обязательная проверка при старте

Перед использованием интеграции Main Orchestrator:

1. Читает AGENTS.md проекта и сначала проверяет правила доступа из .llmignore.
2. Читает .manifest/manifest.yaml и проверяет его SHA-256 по .manifest/manifest.yaml.checksum.
3. Проверяет format_version и фактические switches компонентов. Имена ключей берёт из схемы именно этой версии Manifest; не предполагает их по памяти.
4. Определяет режим работы по значениям switches.
5. Если Todoing включён, проверяет доступность совместимого бинарника, Project ID, конфигурацию и хранилище по разделу 6.1 workflow/README.en.md.
6. При отсутствии файла, несовпадении checksum, неизвестной версии, несовместимом бинарнике, несовпадении Project ID или ошибке хранилища останавливается. Не исправляет и не переинициализирует существующее состояние автоматически.

Manifest в подключённом проекте использует Todoing через `todoing --json api`. Допустимый способ обнаружения бинарника — явно заданный `TODOING_BIN` либо `todoing` в PATH, согласно bootstrap-контракту. Не использовать development-скрипты или кэш репозитория Manifest как runtime-зависимость подключённого проекта. Требуемый baseline Todoing — commit `653788a954d2a120db1beba854308982814d8222` или проверенный потомок. Номер версии сам по себе не доказывает происхождение сборки.

## 3. Режимы интеграции

Режим определяется только фактической конфигурацией проекта:

| Todoing | OpenSpec | Обязанности агента |
|---|---|---|
| enabled | enabled | Координированный режим: одна Todoing task на одну OpenSpec change; поддерживать связь и общий lifecycle. |
| enabled | disabled | Todoing-only: вести самостоятельные задачи; не создавать OpenSpec changes и не добавлять фиктивные ссылки openspec.change. |
| disabled | enabled | OpenSpec-only: вести спецификации без вызовов Todoing и без требования наличия Todoing store. |
| disabled | disabled | Не вызывать ни Todoing, ни OpenSpec. |

Если запрос пользователя требует спецификации, но OpenSpec отключён, агент сообщает об этом и запрашивает разрешение на включение компонента/изменение конфигурации. Он не обходит switch и не создаёт параллельную самодельную систему спецификаций. Аналогично, отключённый Todoing нельзя использовать в обход конфигурации.

Нельзя автоматически менять switches, создавать хранилище поверх существующего или переписывать пользовательскую конфигурацию. Изменения конфигурации выполняются только по разрешённому запросу и по правилам bootstrap.

## 4. Когда создавать спецификацию и задачу

Агент сначала определяет характер запроса.

- Вопрос, консультация, исследование, объяснение, разовая правка текста или обсуждение идеи сами по себе не требуют OpenSpec change и Todoing task.
- Изменение поведения продукта, архитектуры, публичного контракта, существенного процесса или набора взаимосвязанных требований обычно оформляется OpenSpec change, если OpenSpec включён.
- До реализации агент формирует proposal, spec, при необходимости design и tasks.md по workflow OpenSpec. Спецификация фиксирует требуемое поведение; реализация не должна вводить неописанные требования.
- Если работа подлежит учёту в Todoing, Main Orchestrator проверяет существующие задачи и переиспользует уже связанную задачу. Он не создаёт дубликаты.
- Если оба компонента включены, создание/сопровождение одной OpenSpec change и одной связанной Todoing task является единым процессом. Если один компонент выключен, действует соответствующий режим из раздела 3.

Создание артефактов не означает разрешение на реализацию. Агент обязан различать подготовку предложения, согласование требований и разрешение приступить к работе.

## 5. Связь OpenSpec и Todoing

В координированном режиме действуют обязательные правила:

1. Одна директория OpenSpec change соответствует ровно одной Todoing task.
2. Заголовок Todoing task точно равен ID директории change.
3. Связь хранится в Todoing как external reference:
   - namespace: `openspec.change`;
   - value: точный ID директории change;
   - relation: `implements`;
   - scope: `project`.
4. Перед созданием задачи Orchestrator проверяет `task.list` и `task.external-ref.list`. При найденной связи переиспользует задачу. При неоднозначности, конфликте или нескольких совпадениях останавливается и согласует восстановление целостности.
5. FR, пункты декомпозиции, чек-листы и исполнительские шаги остаются в `tasks.md`. Они не создаются отдельными Todoing tasks.
6. Todoing — источник истины для статуса, outcome, версий, истории, блокировок и Review. OpenSpec — источник требований и спецификаций. Git — источник фактической истории изменений и commit SHA. Manifest координирует их согласованность.

Не заменять external reference совпадением названия, текстовой ссылкой в описании задачи или собственным реестром соответствий.

## 6. Полномочия и жизненный цикл

Main Orchestrator — единственный клиент Todoing API в рамках принятой процедуры. Ролевые агенты выполняют порученную работу с артефактами, но не создают задачи, не меняют статусы, не управляют блокировками и не получают lock token.

Основной lifecycle Todoing:

`backlog → ready → in_progress → review → verified → completed`

- `backlog → ready` — только после явного решения пользователя. Ни один агент не вправе трактовать молчание, предложение или собственную оценку как разрешение.
- При переводе в `ready` Orchestrator фиксирует утверждённую версию через `task.version.approve` до lock и dispatch.
- `ready → in_progress` — Orchestrator при фактическом назначении исполнителя.
- `in_progress → review` — Orchestrator после передачи результата исполнителем.
- Review выполняет независимый Reviewer; исполнитель не проверяет собственную работу.
- При `changes_requested` задача возвращается в `in_progress`; замечания устраняются, затем проводится новый независимый Review.
- `review → verified` — только после успешного Review.
- `verified → completed` — только после итоговой проверки Orchestrator и завершения обязательных действий OpenSpec/Git.
- Отмена возможна только по решению пользователя. Агент может рекомендовать отмену, но не принимать это решение.
- Архивирование OpenSpec и Todoing выполняется в установленном порядке завершения; архив не подменяет workflow status.

Точная последовательность API, lock/heartbeat/fencing/recovery, Review records, final commit marker, архивирование и обработка частичных сбоев определены в разделах 6.2–6.6 `workflow/README.en.md` и контракте `docs/architecture/todoing-contract.ru.md`. Эти нормативные документы имеют приоритет перед кратким описанием здесь. Не импровизировать и не повторять неидемпотентные операции после потери ответа: сначала сверить фактическое состояние всех систем.

Разграничение полномочий является процедурным правилом. Todoing не аутентифицирует пользователя и не доказывает наличие его согласия; `actor_id` — атрибуция вызывающей стороны, а не доказательство личности.

## 7. Порядок работы агента

Для каждого изменения, которое проходит через OpenSpec:

1. Main Orchestrator восстанавливает состояние проекта, switches и активных changes/tasks.
2. Уточняет требования с пользователем и определяет, нужна ли формальная change.
3. Analyst готовит proposal и spec; Architect готовит design, когда это требуется; Planner формирует проверяемые задачи в tasks.md.
4. Orchestrator проверяет полноту и согласованность артефактов, создаёт или переиспользует связанную Todoing task в backlog.
5. Orchestrator показывает пользователю подготовленную задачу и ждёт явного разрешения перевести её в ready.
6. После разрешения фиксирует baseline, получает lock и последовательно запускает нужные роли. Параллельная работа нескольких исполнителей в одном проекте запрещена действующим workflow.
7. Независимый Reviewer проверяет результат относительно spec. Замечания возвращаются исполнителю через Orchestrator.
8. Orchestrator выполняет итоговые проверки, синхронизирует OpenSpec, Todoing и Git в нормативном порядке и освобождает lock.
9. В отчёте указывает ссылки на change/task, результат Review, проверки и фактический итоговый commit SHA.

Для документационной задачи применяется doc-only путь действующего OpenSpec workflow; отсутствие кода не является основанием пропускать спецификацию или независимую проверку, если они требуются процессом.

## 8. Восстановление после прерывания

После перезапуска, потери ответа или частичного сбоя Orchestrator не повторяет операцию вслепую. Он сверяет:

- Todoing: task, версии, историю, Review, external references, dependencies и lock;
- OpenSpec: состояние change, содержимое delta specs и факт архивации;
- Git: ветку, рабочее дерево, commit/merge SHA и фактическое содержимое изменений.

Если согласованность нельзя однозначно восстановить, работа останавливается и передаётся пользователю. Нельзя создавать вторую задачу, повторный Review, повторно архивировать change или подменять итоговый SHA без проверки состояния.

## 9. Завершение временного режима

Эта инструкция остаётся обязательной, пока Manifest не научится формировать отдельные контекстные файлы по ролям и процессам и автоматически подключать их на основании конфигурации проекта.

При переходе на новую архитектуру:

1. Разнести правила по соответствующим общим и специализированным файлам контекста.
2. Сохранить точки входа и ссылки, чтобы агент не потерял обязательные инструкции.
3. Проверить, что каждый режим switches покрыт, а правила не дублируются и не противоречат друг другу.
4. Выполнить сквозную проверку обнаружения контекста и workflow.
5. Только после успешной проверки снять обязательность этой временной инструкции.

До выполнения всех пяти условий агент обязан читать и соблюдать этот документ.
