# Описание
Универсальные правила описания коммитов проекта, подключённого к
фреймворку «Манифест».

## 1. Формат сообщения

### 1.1. Формат: `<type>(<scope>): <тема>`.

### 1.2. Тема

Английский, повелительное наклонение, нижний регистр, единственное
число, без точки в конце; цель — до 50 символов, не жёсткий лимит.

### 1.3. Список типов

`feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`,
`ci`, `chore`, `revert`.

### 1.4. Scope

Необязательный короткий стабильный идентификатор затронутой области
(модуль, компонент, подсистема).

### 1.5. Ломающие изменения

`!` после типа/scope и `BREAKING CHANGE: <описание>` в footer —
одновременно.

## 2. Содержание коммитов

### 2.1. Одна логическая правка на коммит.

### 2.2. Коммиты — только по текущей задаче или плану.

### 2.3. Что не коммитится

Временные логи, диагностические скрипты, одноразовые обходные пути
и артефакты сессии; коммитится финальный результат, а не история
отладки. Исключение — постоянные инструменты проекта.
Исследовательские прогоны коммитов не делают.

### 2.4. Известно сломанное состояние не коммитится

Перед коммитом запускаются применимые проверки (тесты, сборка,
линтеры); не влияющие на изменение проверки не требуются.

## 3. История

### 3.1. История не переписывается

Без явного разрешения владельца — никаких amend, rebase, reset,
force-push и удаления базовых коммитов.

## 4. Примеры

### 4.1. Сообщения коммитов

Правильно

✅ `feat(audio-capture): add noise gate`
✅ `fix(parser)!: handle empty input`

Неправильно

❌ `Added audio-capture module` — нет типа, не повелительное наклонение
❌ `chore: добавить шумоподавление` — сообщение не на английском
