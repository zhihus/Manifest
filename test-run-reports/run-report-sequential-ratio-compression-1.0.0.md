## 3. Точки отказа и аномалии

1. **Точка отказа — не инференс.** Во всех трёх 600-секундных окнах сервер не зафиксировал ни одного события: ни запросов, ни разрывов соединений, ни ошибок. Последний перед окном запрос завершился штатно (50–77 tok/s, cache hit 82–99%, очередь ≤0.1 s). Сервер простаивал, будучи здоровым.
2. **Точка отказа — шаг разрешения tool-call на клиенте.** В каждом случае последний ответ модели содержал tool-вызов; следующее событие в клиентском логе — `tool.permission.resolved` — появилось только через 5 мс после принудительной отмены. При `permissionMode: bypassPermissions` разрешение должно быть мгновенным; его завершение только при отмене означает дедлок в `core.tool.executor` (шаг permission-resolution).
3. **Watchdog — единственный механизм выхода.** `timeoutMs: 600000` захардкожен в `core.subagent` («Explore subagent activity watchdog fired»); в пользовательской конфигурации ключ отсутствовал (проверены setting.json, config.json, bot-config.v3.json, agents-state.json, provider_config.json).
4. **Ни одного ретрая инференса** (`attempt:1` во всех запросах зависших агентов); ошибок HTTP/подключений не зафиксировано.
5. **Потеря данных**: model-io-транскрипты зависших субагентов ротированы/удалены на момент повторного анализа (зафиксированы при первом осмотре: 15 запросов, все attempt:1); у `agent_35b82ed4` остались осиротевшие tool-result JSON — run оборвался посреди задачи.
6. **Рассогласование отчёта и работы** (сбой 1): reviewer выполнил мердж (develop → `4185b40`, fast-forward, без merge-коммита — отклонение от инструкции `--no-ff`), но финальный отчёт не выдал: ход «сформировать отчёт» был после зависания.
7. Повторные 600-с паузы не аккумулируются прогревом/кэшем: окна возникают после любого по счёту хода (15-й запрос во второй попытке; разные фазы у reviewer и doccer).
