# Спецификация минимального контракта Todoing для Manifest — v3

> Редакция, устраняющая замечания аудита v2 (финальная). Документация только для
> рассмотрения: код не меняется, OpenSpec change не создаётся, задачи Todoing не
> создаются, коммиты не выполняются.
>
> Предыдущая редакция сохранена отдельно: `contract-spec-final.ru.md` (v2).

## 0. Что изменилось относительно v2

Аудит v2 выявил 8 групп замечаний. В v3 они устранены:

| # | Замечание | Разрешение в v3 |
|---|-----------|-----------------|
| 1 | Параллельные WAL-транзакции: потерянные обновления `index.json`/`counter.json` | **commit-lock** — сериализация фазы фиксации; read-modify-write под одним замком (§3.5) |
| 2 | Heartbeat от `acquired_at`; гонки захвата; поведение при истечении собственного TTL | Heartbeat от **текущего момента**; атомарный check-and-act под commit-lock; захват через create-new + rebase; явное поведение при истечении (§3.7) |
| 3 | Нет команды восстановления soft-delete | Команда **`restore`** с определением влияния на историю/версии/статус/видимость (§3.6) |
| 4 | Формула восстановления `next_id` неверна | Разделение случаев **отсутствующего** и **повреждённого** счётчика; `max(все ID) + 1` (§3.4) |
| 5 | OpenSpec: кто проверяет завершение change; уникальность 1:1 | Ответственность за проверку — **Manifest** (не Todoing); уникальность через инварианты `bind` (§3.9) |
| 6 | JSON-режим, `project_id` в standalone, синтаксис `init`, формат ошибок, управление статусами | Единый `--json`; `project_id: null` в standalone; `init --project` согласован; новые коды ошибок; команды `status-add`/`status-remove` (§2, §3.1) |
| 7 | Состав записи истории; `control_version` в истории; создаёт ли `approve` версию | Полный состав записи; `control_version` в каждой записи; `approve` **создаёт** версию-снимок (§3.3) |
| 8 | Нет тестовых сценариев конкурентности/аварий | §8 — сценарии с исходными условиями, действиями, ожидаемым результатом |

## 2. Принятые решения пользователя (сохранены из v2)

Решения П1–П8 и дополнительные уточнения **не меняются** (ограничение: не менять
утверждённые пользователем решения). Перечислены для полноты; детали — в v2 §1.

- **П1** — `--owner` обязателен для `lock`/`heartbeat`/`unlock`; генерируется
  клиентской сессией, хранится непрозрачной строкой.
- **П2** — TTL по умолчанию 300 с; heartbeat каждые 60 с.
- **П3** — повторный `approve` разрешён; контрольная версия только вперёд, только
  явной операцией.
- **П4** — `deleted` и `status` независимы; soft-delete не меняет статус; физическое
  удаление запрещено.
- **П5** — `final_commit` устанавливается отдельной явной операцией.
- **П6** — standalone допустим; при интеграции `init` и Project ID обязательны.
- **П7** — `ls` показывает ID и `locked` для чужой заблокированной задачи, без
  содержимого.
- **П8** — `openspec_change` проверяется только по формату; Todoing не зависит от
  OpenSpec.

## 3. Контракт CLI/JSON

### 3.1 Версия контракта и совместимость

- Версия контракта — semver, например `2.0.0` (major повышен относительно v2: добавлен
  commit-lock, `restore`, изменение формулы `next_id` — ломающие изменения для
  реализации, хотя для потребителя JSON аддитивны).
- Носители:
  - `todoing contract` → `{"contract_version":"2.0.0","capabilities":[...]}`;
  - поле `contract_version` в **каждом** JSON-ответе;
  - `todoing version` дополняется строкой `contract: 2.0.0`.
- **Capabilities**: `project_id, history, versions, control_version, locks,
  atomicity, commit_lock, restore, configurable_statuses, openspec_change`.
- **Правила совместимости**: major — ломающее; minor/patch — аддитивное; потребитель
  игнорирует неизвестные поля.
- **Несовместимый major** → `CONTRACT_MISMATCH`; отсутствующая capability →
  `CAPABILITY_MISSING`.

### 3.2 JSON-режим и формат вывода

- **Единый JSON-режим**: глобальный флаг `--json` включает машиночитаемый вывод для
  **любой** команды. Без `--json` — человекочитаемый вывод (для интерактивного
  использования). Контракт Manifest использует **только** `--json`.
- **Вывод в `--json`**:
  - успех → stdout, JSON-обёртка (§3.4), код выхода `0`;
  - ошибка → stderr, JSON-обёртка (§3.5), код выхода `1`.
- **Каждая команда** в `--json` возвращает ту же обёртку; payload в `data` зависит от
  команды (таблица §3.3).

### 3.3 Команды и их payload

| Команда | Назначение | `data` при успехе |
|---------|-----------|-------------------|
| `init --project <id>` | Создать хранилище с Project ID | `{"project_id": "<id>"}` |
| `contract` | Версия + capabilities | `{"contract_version","capabilities"}` |
| `version` | Версия бинарника + контракт | `{"version","contract_version"}` |
| `add …` | Создать задачу | объект задачи (§3.6) |
| `ls [--include-deleted]` | Список задач | массив объектов (полных или `{id, locked}`) |
| `see <id>` | Чтение задачи | объект задачи (§3.6) |
| `status <id> <s>` | Сменить статус | объект задачи |
| `label <id> …` | Изменить метки | объект задачи |
| `body <id> …` / `append <id> …` | Изменить тело | объект задачи |
| `commit <id> <ref>` | Добавить commit-ref | объект задачи |
| `bind <id> --change <name>` | Привязать OpenSpec change | объект задачи |
| `final-commit <id> <ref>` | Установить итоговую ссылку | объект задачи |
| `delete <id>` | Soft-delete | объект задачи (`deleted: true`) |
| `restore <id>` | Восстановить soft-deleted задачу | объект задачи (`deleted: false`) |
| `approve <id>` | Поставить контрольную версию | объект задачи |
| `lock <id> --owner <o> [--ttl <s>]` | Захват блокировки | `{"owner","acquired_at","expires_at"}` |
| `heartbeat <id> --owner <o> [--ttl <s>]` | Продлить блокировку | `{"owner","expires_at"}` |
| `unlock <id> --owner <o>` | Освободить блокировку | `{"released": true}` |
| `status-add <name>` | Добавить кастомный статус | `{"custom_statuses":[…]}` |
| `status-remove <name>` | Удалить кастомный статус | `{"custom_statuses":[…]}` |
| `status-list` | Список валидных статусов | `{"base":[…],"custom":[…]}` |

> `init` принимает `--project` как **позиционный аргумент команды** (не глобальный
> флаг), т.к. при инициализации хранилище ещё не существует и глобальный `--project`
> не может быть проверен. Для всех остальных команд `--project` — глобальный флаг.

### 3.4 Формат ответа (успех)

```json
{
  "contract_version": "2.0.0",
  "project_id": "manifest",
  "ok": true,
  "data": { }
}
```

- `project_id` — строка или `null`. В **standalone-режиме** (без `init`)
  `project_id: null`. При интеграции — значение из `project.json`.

### 3.5 Формат ошибки

Ошибки — на stderr, код выхода `1`:

```json
{
  "contract_version": "2.0.0",
  "project_id": "manifest",
  "ok": false,
  "error": {"code": "LOCK_HELD", "message": "task 7 is locked by 'sess-a1b2' until 2026-11-23T12:05:00"}
}
```

**Каталог кодов ошибок**:

| code | Смысл |
|------|-------|
| `INVALID_PROJECT` | `--project` не совпадает с Project ID хранилища |
| `NO_PROJECT` | Хранилище не инициализировано (нет `project.json`) при интеграции |
| `UNKNOWN_TASK` | Задача с таким ID не существует |
| `LOCK_HELD` | Задача заблокирована другим клиентом (активный чужой замок) |
| `LOCK_OWNER` | Операция над чужим замком (не владелец) |
| `LOCK_EXPIRED` | Собственная блокировка истекла (владелец пытается оперировать, но TTL прошёл) |
| `CONCURRENT_MODIFICATION` | Базовое состояние изменилось между prepare и commit; требуется повтор |
| `CONTRACT_MISMATCH` | Major-версия контракта несовместима |
| `CAPABILITY_MISSING` | Требуемая capability отсутствует |
| `VALIDATION` | Нарушение валидации (пустой title, неизвестный статус, формат `openspec_change`, двойная привязка) |
| `HOOK_REJECTED` | Хук отклонил операцию (exit ≠ 0) |
| `CONFIG_CORRUPT` | Повреждена конфигурация (`project.json`, `statuses.json`, `counter.json`) и она не восстановлена автоматически |
| `IO_ERROR` | Ошибка ввода-вывода (файл недоступен, диск полон) |

### 3.6 Объект задачи

```json
{
  "id": 7,
  "title": "Минимальный контракт Todoing",
  "status": "in_progress",
  "labels": ["mvp", "integration"],
  "body": "Спецификация контракта",
  "commits": ["a1b2c3d", "e4f5a6b"],
  "final_commit": "e4f5a6b",
  "openspec_change": "add-todoing-contract",
  "deleted": false,
  "added_at": "2026-11-23T10:00:00",
  "current_version": 4,
  "control_version": 3,
  "versions": [
    {"version": 1, "status": "todo",        "created_at": "2026-11-23T10:00:00", "event": "create",  "control_version": null},
    {"version": 2, "status": "in_progress", "created_at": "2026-11-23T11:00:00", "event": "status",  "control_version": null},
    {"version": 3, "status": "in_progress", "created_at": "2026-11-23T12:00:00", "event": "approve", "control_version": 3},
    {"version": 4, "status": "in_progress", "created_at": "2026-11-23T13:00:00", "event": "final-commit", "control_version": 3}
  ]
}
```

- `versions[]` — краткий список (только `version`, `status`, `created_at`, `event`,
  `control_version`). Полный снимок каждого состояния — в истории (§4.3).
- `control_version` в объекте задачи — текущее значение указателя.

### 3.7 `ls` и блокировка

- Для чужой заблокированной задачи `ls` возвращает **только** `{"id", "locked": true}`
  (П7), без содержимого и остальных полей.
- Для своей (владельца) или незаблокированной задачи — полный объект задачи.
- `ls --include-deleted` включает soft-deleted задачи (иначе они скрыты).

## 4. Модель

### 4.1 Статусы

- **Базовый набор** (встроен, всегда валиден, не удаляется): `todo`, `in_progress`,
  `done`, `cancelled`.
- **Расширение**: `.todoing/statuses.json` хранит **только кастомные** статусы:
  ```json
  {"custom_statuses": ["review", "blocked"]}
  ```
- **Управление кастомными статусами** (новое в v3):
  - `status-add <name>` — добавить кастомный статус (валидация: непустой, без
    пробелов/специальных символов, не совпадает с базовым).
  - `status-remove <name>` — удалить кастомный статус (не удаляет базовые; если
    статус используется в задаче → `VALIDATION`).
  - `status-list` — вернуть `{"base":[…],"custom":[…]}`.
  - Эти команды **не требуют** блокировки (они не мутации задачи) и **не создают**
    версий задач.
- **Валидация**: целевой статус должен быть в валидном наборе → иначе `VALIDATION`.
- **Переходы**: свободные между валидными статусами. Внутренние этапы Manifest — не
  статусы Todoing.
- Статусы — простые строки в JSON (нет enum в контракте).

### 4.2 Project ID

- **Создание**: `todoing init --project <id>` создаёт `.todoing/project.json`:
  ```json
  {"project_id": "manifest", "contract_version": "2.0.0"}
  ```
- **Источник истины**: `.todoing/project.json`.
- **Неизменяемость**: после создания `project_id` не меняется. Несовпадение
  `--project` → `INVALID_PROJECT`.
- **Обработка несовпадения**:
  - `--project` задан и не совпадает → `INVALID_PROJECT`.
  - `--project` задан, но `project.json` отсутствует → `NO_PROJECT`.
  - `--project` не задан (standalone) → Project ID не требуется (П6); в JSON
    `project_id: null`.
- **Повреждённый `project.json`**: не читается/не парсится → `CONFIG_CORRUPT`
  (не восстанавливается автоматически, т.к. Project ID — источник истины и его
  нельзя угадать).
- **Граница**: механизм передачи `--project` из AI-harness — **вне Manifest**.

### 4.3 История и версии

- **Append-only журнал**: `.todoing/history/{id}.jsonl` — по одной неизменяемой
  записи на строку.
- **Полный состав записи истории** (новое в v3 — определён полностью):
  ```json
  {
    "version": 4,
    "task_id": 7,
    "status": "in_progress",
    "title": "Минимальный контракт Todoing",
    "labels": ["mvp", "integration"],
    "body": "Спецификация контракта",
    "commits": ["a1b2c3d", "e4f5a6b"],
    "final_commit": "e4f5a6b",
    "openspec_change": "add-todoing-contract",
    "deleted": false,
    "control_version": 3,
    "event": "final-commit",
    "created_at": "2026-11-23T13:00:00"
  }
  ```
  Запись — **полный снимок** состояния задачи на момент версии (не дифф). Это
  обеспечивает однозначное восстановление любого состояния, включая контрольное.
- **`control_version` в записи**: каждая запись хранит значение `control_version` на
  момент создания версии. Это позволяет однозначно восстановить контрольное
  состояние: контрольная версия = запись с `version == control_version`.
- **Аддитивность/неизменяемость**: записи только дописываются, никогда не
  переписываются и не удаляются. Текущее состояние = последняя версия.
- **Триггер версии**: каждое успешное сохранение (`add`, `status`, `label`, `body`,
  `append`, `commit`, `bind`, `final-commit`, `approve`, `delete`, `restore`)
  дописывает новую версию.
- **Контрольная версия**:
  - `control_version` — указатель на номер версии, устанавливается **только**
    явной операцией `approve` (П3).
  - **`approve` создаёт новую версию** (v3-уточнение): `approve` дописывает запись с
    `event: "approve"`, в которой `control_version` устанавливается в
    `current_version + 1` (номер создаваемой версии). Снимок этой записи = текущее
    состояние задачи на момент `approve`.
  - **Повторный `approve`** (П3): создаёт ещё одну версию-снимок, `control_version`
    передвигается вперёд (к более высокому номеру).
  - До первого `approve` `control_version = null` во всех записях.
  - **Восстановление контрольного состояния**: читается запись с
    `version == control_version` из истории — это полный снимок контрольного
    состояния (все поля).

### 4.4 ID задач

- **Проблема**: «max по существующим файлам + 1» недостаточен.
- **Решение**: **монотонный счётчик** `.todoing/counter.json`:
  ```json
  {"next_id": 8}
  ```
- **Выдача**: при создании задачи читается счётчик, выдаётся `next_id`, счётчик
  увеличивается на 1 и **записывается атомарно** (под commit-lock, §4.5).
- **Монотонность**: счётчик только растёт.
- **Восстановление** (v3-исправление формулы):
  - **Счётчик отсутствует** (файл не существует): `next_id = max(ID всех файлов задач) + 1`.
    Если файлов нет → `next_id = 1`.
  - **Счётчик повреждён** (файл существует, но не парсится): `next_id = max(ID всех
    файлов задач, значение из повреждённого файла если извлекаемо) + 1`. Если
    значение не извлекаемо → `CONFIG_CORRUPT` (счётчик — источник истины, угадывать
    нельзя).
  - **Ключевое**: `max` берётся по **всем** файлам задач, включая soft-deleted
    (`deleted: true`), т.к. soft-delete сохраняет файл. Это исключает повторное
    использование ID после soft-delete.
  - **Исключение ненужного пропускания**: восстановление не «перескакивает» на
    произвольное большое значение — оно равно ровно `max + 1`, т.е. минимальное
    свободное ID выше всех использованных.

### 4.5 Атомарность и восстановление (WAL) — с commit-lock

- **Проблема v2**: параллельные транзакции могли потерять обновления `index.json` и
  `counter.json` (read-modify-write без сериализации).
- **Решение v3**: **commit-lock** — сериализация фазы фиксации.

  **Файл commit-lock**: `.todoing/.commit.lock` — глобальный эксклюзивный замок
  (flock / O_EXCL с rebase), удерживается только в фазе **Apply**.

  **Структура транзакции** (одна успешная мутация):
  1. **Prepare** (без commit-lock):
     - прочитать текущее состояние (файл задачи, `index.json`, `counter.json`,
       хвост истории);
     - вычислить намеренные артефакты (новую версию, новое содержимое файла, новый
       индекс, новый счётчик);
     - запустить хуки (до журнала);
     - записать базовые хеши: `base_task_hash`, `base_index_hash`, `base_counter`.
  2. **Journal**: атомарно записать `.todoing/journal/{txn_id}.json`:
     ```json
     {
       "txn_id": "…", "task_id": 7,
       "version_record": {…}, "task_content": "…",
       "index_content": […], "counter": 8,
       "base_task_hash": "…", "base_index_hash": "…", "base_counter": 7,
       "state": "prepared"
     }
     ```
  3. **Acquire commit-lock**: занять `.todoing/.commit.lock` (эксклюзивно).
  4. **Under commit-lock — validate-and-rebase**:
     - пере-прочитать `index.json`, `counter.json`, файл задачи;
     - сверить с `base_*` хешами/значениями:
       - **совпадение** → применить намеренные артефакты;
       - **несовпадение** → **rebase**: пере-вычислить артефакты из текущего
         состояния + дельту транзакции, пере-записать журнал, применить.
         Если дельта **неприменима** к текущему состоянию (например, переход
         статуса из другого базового статуса) → транзакция **прерывается** кодом
         `CONCURRENT_MODIFICATION`, журнал удаляется, commit-lock освобождается
         (см. SC-9).
     - **Apply** (порядок фиксирован, каждый шаг атомен, всё под commit-lock):
       1. обновить журнал: `state: "applying"`, присвоить `seq` (инкремент
          `.todoing/seq` под lock) — **до** записи артефактов;
       2. дописать `version_record` в `history/{id}.jsonl`;
       3. заменить `tasks/{id}.md` (`atomic_write`);
       4. заменить `index.json` (`atomic_write`);
       5. (для создания) заменить `counter.json` (`atomic_write`);
       6. обновить журнал: `state: "committed"`.
  5. **Release commit-lock**, **Cleanup**: удалить журнал.

  **Почему нет потерянных обновлений**: `index.json` и `counter.json` читаются и
  записываются **под одним commit-lock** (read-modify-write в критической секции).
  Две транзакции не могут одновременно прочитать старый индекс/счётчик и записать
  поверх — вторая дождётся освобождения commit-lock и увидит результат первой
  (через rebase).

  **Порядок фиксации**: транзакция **не считается завершённой** до фиксации всех
  частей (история + файл + индекс + счётчик + `committed`).

  **Нумерация порядка (`seq`)**: под commit-lock в **начале** Apply (при переходе
  `state: "prepared"` → `state: "applying"`) журналу присваивается монотонный `seq`
  (из `.todoing/seq`, инкремент под lock) **до** записи артефактов. `seq` определяет
  **порядок фиксации** транзакций. Это гарантирует: любой журнал, у которого Apply
  начался, имеет `seq`; журнал без `seq` — значит Apply не начинался и артефакты не
  писались.

  **Восстановление после аварийного завершения** (forward-recovery):
  - При старте / перед операцией сканируется `.todoing/journal/`.
  - Журналы обрабатываются **по возрастанию `seq`** (порядок фиксации сохраняется).
  - Для каждого незавершённого журнала — **идемпотентное** приведение артефактов к
    намеренному состоянию (как в v2: история/файл/индекс/счётчик).
  - **Журналы без `seq`** (`state: "prepared"`, commit-lock не захвачен): Apply не
    начинался, артефакты не писались → журнал **изолируется** в
    `.todoing/journal/quarantine/`, транзакция **не считается завершённой**,
    команда должна быть повторена пользователем.
  - **Повреждённые журналы** (не парсятся): изолируются в `quarantine/`, не
    блокируют восстановление остальных.

  **Поведение при одновременных операциях над разными задачами**:
  - Prepare идёт параллельно (без commit-lock).
  - Apply сериализуется commit-lock'ом.
  - Если две транзакции затронули `index.json` (обе меняют индекс), вторая при
    rebase увидит индекс, уже содержащий изменение первой, и применит своё поверх →
    оба изменения сохранены.

  **Хуки** выполняются в Prepare (до commit-lock и до журнала), поэтому медленные
  хуки не блокируют другие транзакции, а отклонённая мутация не оставляет артефактов.

### 4.6 Удаление и восстановление (soft-delete + restore)

- **Физическое удаление запрещено** (П4).
- **`delete <id>`** (soft-delete):
  - устанавливает `deleted: true` (не статус, а отдельное поле), создаёт новую
    версию, **не удаляет** файл задачи и не удаляет записи истории;
  - `deleted` и `status` **независимы** (П4): статус не меняется;
  - задача с `deleted: true` скрыта из `ls` по умолчанию, но доступна через `see`
    и в истории;
  - `ls --include-deleted` показывает её.
- **`restore <id>`** (новое в v3):
  - **Предусловие**: задача существует и `deleted: true`. Иначе → `UNKNOWN_TASK` /
    `VALIDATION` (если не удалена).
  - **Действие**: устанавливает `deleted: false`, создаёт **новую версию** с
    `event: "restore"`.
  - **Влияние на историю**: дописывается новая запись-снимок с `deleted: false`;
    предыдущие записи (включая `deleted: true`) **не изменяются** (append-only).
  - **Влияние на версии**: `current_version` увеличивается на 1.
  - **Влияние на статус**: **не меняется** (П4 — `deleted`/`status` независимы).
  - **Влияние на `control_version`**: **не меняется** (restore не является
    `approve`).
  - **Влияние на видимость в `ls`**: задача снова появляется в `ls` (без
    `--include-deleted`).
  - **ID**: не переиспользуется (ID неизменяемы, счётчик монотонен).
  - **Блокировка**: `restore` — мутация, требует активной блокировки владельцем
    (как все мутации).

### 4.7 Блокировки

- **Файл-замок**: `.todoing/locks/{id}.lock`:
  ```json
  {"owner": "sess-a1b2", "acquired_at": "2026-11-23T12:00:00", "expires_at": "2026-11-23T12:05:00"}
  ```
- **Идентификатор владельца** (П1): генерируется клиентской сессией, хранится
  непрозрачной строкой.
- **Захват (acquire)**: `lock <id> --owner <o> --ttl <s>`:
  - создаёт файл **create-new** (атомарно, O_EXCL).
  - если файл существует:
    - не истёк и чужой → `LOCK_HELD`;
    - не истёк и **свой** (owner совпадает) → идемпотентное продление (возвращает
      текущее `expires_at`);
    - **истёк** (чужой или свой) → **rebase-захват**: атомарно заменяет файл новым
      (create-new после удаления истёкшего). Гонка двух клиентов на истёкший замок
      разрешается create-new: только один победит, второй получит `LOCK_HELD`
      (файл уже занят победителем).
  - `--owner` **обязателен** (П1).
- **Heartbeat** (v3-исправление): `heartbeat <id> --owner <o> --ttl <s>`:
  - **продлевает TTL от текущего момента**: `expires_at = now + TTL` (не от
    `acquired_at`);
  - только владельцем; если owner не совпадает → `LOCK_OWNER`; если замок истёк →
    `LOCK_EXPIRED` (см. ниже).
  - **TTL по умолчанию — 300 с** (П2); **heartbeat каждые 60 с** (П2).
- **Освобождение (release)**: `unlock <id> --owner <o>` удаляет файл, только
  владельцем. `--owner` обязателен (П1).
- **Атомарность check-and-act** (v3-уточнение): проверка владельца/TTL и выполнение
  мутации происходят **под commit-lock** (в фазе validate). Т.е. сервер
  пере-читывает lock-файл под commit-lock и проверяет owner + `expires_at > now`
  **в тот же момент**, когда применяет мутацию. Это исключает TOCTOU: между
  проверкой и операцией замок не может быть захвачен другим (commit-lock удержан).
- **Поведение при истечении собственной блокировки** (v3-уточнение):
  - если владелец выполняет мутацию/heartbeat, но его `expires_at` уже прошёл →
    ошибка `LOCK_EXPIRED`. Замок считается чужим/освободившимся; владелец должен
    повторно захватить (`lock`) перед операцией.
  - это **не** `LOCK_OWNER` (владелец тот же) и **не** `LOCK_HELD` (другой не
    захватил) — отдельный код, т.к. ситуация «свой замок истёк».
- **TTL + crash recovery**: при истечении замок освобождается — новый клиент может
  захватить (rebase-захват). Покрывает аварийное завершение без `unlock`.
- **Эксклюзивность чтения** (П7): пока задача заблокирована, другие клиенты не
  читают её:
  - `see <id>` не владельцем → `LOCK_HELD`;
  - `ls` → только `{"id", "locked": true}` для чужой заблокированной;
  - владелец читает без ограничений.

### 4.8 Системные операции автоматически

- Версионирование, запись в историю, метаданные (`control_version`, `added_at`,
  `deleted`, счётчик ID, `seq`) выполняются **внутри мутации автоматически**.
- Агент вызывает только высокоуровневую команду; системная часть (WAL, commit-lock,
  версия, история, индекс, счётчик) прозрачна.

### 4.9 OpenSpec

- **Поле** `openspec_change`: формат — имя change. **Валидация только по формату**
  (П8): непустая строка, валидный идентификатор. Todoing **не проверяет** наличие
  OpenSpec-каталога и **не зависит от OpenSpec** (П8).
- **Уникальность связи 1:1** (v3-уточнение):
  - **Одна задача Todoing ↔ один OpenSpec change** (активная привязка).
  - **Не допускается две задачи с одной активной привязкой**: `bind <id> --change
    <name>` проверяет, что `<name>` не привязан к другой **активной** задаче
    (задаче с `deleted: false` и незавершённой привязкой). Нарушение → `VALIDATION`.
  - **Активная привязка** = задача с `deleted: false` и `openspec_change == <name>`.
  - После soft-delete задачи её привязка **не является активной** (задача
    `deleted: true`), поэтому `<name>` можно привязать к другой задаче.
- **Кто проверяет завершение предыдущего change** (v3-уточнение): **Manifest**, а не
  Todoing. Todoing не читает OpenSpec и не знает, завершён ли change. Правило
  повторной привязки:
  - повторный `bind` к той же задаче разрешён только если предыдущая привязка
    **снята** (задача soft-deleted) либо Manifest явно подтвердил завершение
    change (через хук/внешний механизм — вне Todoing).
  - Todoing лишь хранит ссылку и проверяет формат + уникальность активной привязки.
- **Жизненный цикл**:
  - **Bind**: `bind <id> --change <name>` (или при `add`).
  - **Работа**: коммиты через `commit <id> <sha>` (поле `commits`).
  - **Завершение**: `final_commit` устанавливается **отдельной явной операцией**
    `final-commit <id> <ref>` (П5). Change архивируется **механизмом OpenSpec**
    (задача Manifest, не Todoing).
- **`final_commit`**: поддерживает итоговую ссылку на **commit или merge**, не
  ограничивает список `commits`.
- **Независимость**: Todoing не читает `openspec/`, не проверяет содержимое.

## 8. Критерии приёмки и тестовые сценарии

### 8.1 Счётчик ID

- **AC-ID-1**: При создании задачи счётчик обновляется атомарно (под commit-lock).
- **AC-ID-2**: ID выдаются монотонно.
- **AC-ID-3**: После soft-delete ID не переиспользуются (max по всем файлам,
  включая soft-deleted).
- **AC-ID-4**: Восстановление при **отсутствующем** счётчике: `next_id = max(ID
  файлов) + 1` (или 1, если файлов нет).
- **AC-ID-5**: Восстановление при **повреждённом** счётчике: `CONFIG_CORRUPT`, если
  значение не извлекаемо; иначе `max(ID файлов, извлечённое) + 1`.
- **AC-ID-6**: Восстановление не пропускает ID (ровно `max + 1`).

### 8.2 WAL, commit-lock, атомарность

- **AC-WAL-1**: Порядок фиксации: журнал → (commit-lock) история → файл → индекс →
  счётчик → `committed` + `seq` → release → cleanup.
- **AC-WAL-2**: Транзакция не завершена до фиксации всех частей.
- **AC-WAL-3**: `index.json`/`counter.json` читаются и пишутся под commit-lock
  (read-modify-write в критической секции).
- **AC-WAL-4**: При несовпадении base-хешей выполняется rebase (пере-вычисление из
  текущего состояния + дельта).
- **AC-WAL-5**: `seq` присваивается под commit-lock; порядок фиксации = порядок
  `seq`.
- **AC-WAL-6**: Forward-recovery обрабатывает журналы по возрастанию `seq`
  (идемпотентно).
- **AC-WAL-7**: Журналы без `seq` (prepared, commit-lock не захвачен) изолируются в
  quarantine; транзакция не завершена; команда повторяется.
- **AC-WAL-8**: Повреждённые журналы изолируются в quarantine и не блокируют
  восстановление остальных.

### 8.3 Блокировки

- **AC-LOCK-1**: `lock`/`heartbeat`/`unlock` требуют `--owner` (П1).
- **AC-LOCK-2**: Захват эксклюзивен: второй клиент на активный чужой замок →
  `LOCK_HELD`.
- **AC-LOCK-3**: TTL по умолчанию 300 с (П2).
- **AC-LOCK-4**: Heartbeat каждые 60 с (П2), только владельцем.
- **AC-LOCK-5**: Heartbeat продлевает `expires_at = now + TTL` (от текущего момента).
- **AC-LOCK-6**: Check-and-act атомен: проверка owner/TTL и мутация под commit-lock.
- **AC-LOCK-7**: Гонка двух клиентов на истёкший замок разрешается create-new: один
  победил, второй → `LOCK_HELD`.
- **AC-LOCK-8**: Истечение собственной блокировки → `LOCK_EXPIRED` (не `LOCK_OWNER`,
  не `LOCK_HELD`); владелец повторно захватывает.
- **AC-LOCK-9**: `ls` → `{id, locked}` для чужой заблокированной (без содержимого)
  (П7).

### 8.4 Soft-delete и restore

- **AC-DEL-1**: `delete` → `deleted: true`, не удаляет файл/историю.
- **AC-DEL-2**: Soft-delete не меняет статус (П4).
- **AC-DEL-3**: Задача с `deleted: true` видна в `see`/истории, скрыта из `ls`.
- **AC-DEL-4**: `restore` → `deleted: false`, создаёт новую версию (`event:
  "restore"`), статус и `control_version` не меняются, задача снова в `ls`.
- **AC-DEL-5**: Восстановление не переиспользует ID.
- **AC-DEL-6**: Физическое удаление никогда не выполняется.

### 8.5 Контрольная версия

- **AC-VER-1**: `control_version` устанавливается только `approve`.
- **AC-VER-2**: `approve` создаёт версию-снимок (`event: "approve"`),
  `control_version = current_version + 1`.
- **AC-VER-3**: Повторный `approve` — только вперёд (П3).
- **AC-VER-4**: Контрольное состояние восстанавливается как запись с
  `version == control_version` (полный снимок).
- **AC-VER-5**: Мутации после `approve` не сдвигают `control_version`.

### 8.6 OpenSpec

- **AC-OS-1**: `openspec_change` валидируется только по формату (П8).
- **AC-OS-2**: Todoing не читает `openspec/`, не зависит от OpenSpec (П8).
- **AC-OS-3**: `bind` 1:1; две задачи с одной **активной** привязкой → `VALIDATION`.
- **AC-OS-4**: После soft-delete привязка неактивна; `<name>` можно привязать к
  другой задаче.
- **AC-OS-5**: Проверка завершения change — за Manifest (не Todoing).
- **AC-OS-6**: `final-commit` — отдельная явная операция (П5), не ограничивает
  `commits`.

### 8.7 Project ID

- **AC-PRJ-1**: `init --project` создаёт `project.json`.
- **AC-PRJ-2**: `project_id` неизменяем.
- **AC-PRJ-3**: Несовпадение → `INVALID_PROJECT`; нет `project.json` → `NO_PROJECT`.
- **AC-PRJ-4**: Standalone → `project_id: null`.
- **AC-PRJ-5**: Повреждённый `project.json` → `CONFIG_CORRUPT`.

### 8.8 Совместимость

- **AC-CMP-1**: `contract` → версия + capabilities.
- **AC-CMP-2**: Major-несовпадение → `CONTRACT_MISMATCH`.
- **AC-CMP-3**: Отсутствие capability → `CAPABILITY_MISSING`.
- **AC-CMP-4**: Потребитель игнорирует неизвестные поля.

### 8.9 Тестовые сценарии конкурентности, гонок и аварий

Для каждого сценария указаны исходные условия, действия, ожидаемый результат.

**SC-1. Конкурентные мутации разных задач (потерянные обновления индекса)**
- *Исходные условия*: задачи 7 и 8 существуют; `index.json` содержит обе; два
  клиента A и B.
- *Действия*: A выполняет `status 7 done`, B одновременно выполняет `status 8 done`.
  Оба проходят Prepare параллельно, затем конкурируют за commit-lock.
- *Ожидаемый результат*: обе мутации зафиксированы; `index.json` содержит обновлённые
  статусы **и** 7, **и** 8 (нет потерянного обновления); `seq` у транзакции A и B
  различны; история каждой задачи содержит свою версию.

**SC-2. Конкурентное создание задач (потерянные обновления счётчика)**
- *Исходные условия*: `counter.json` = `{"next_id": 10}`; два клиента A и B
  одновременно выполняют `add`.
- *Действия*: A и B параллельно создают задачи.
- *Ожидаемый результат*: A получает ID 10, B получает ID 11 (или наоборот);
  `counter.json` = `{"next_id": 12}`; нет двух задач с одним ID; нет пропущенного
  ID.

**SC-3. Гонка захвата истёкшей блокировки**
- *Исходные условия*: задача 7 заблокирована владельцем X, `expires_at` прошёл;
  клиенты A и B одновременно выполняют `lock 7 --owner A` / `lock 7 --owner B`.
- *Действия*: A и B одновременно пытаются rebase-захватить истёкший замок.
- *Ожидаемый результат*: ровно один (скажем, A) успешно захватывает (create-new
  победил); B получает `LOCK_HELD`; в `locks/7.lock` owner = A.

**SC-4. Истечение собственной блокировки**
- *Исходные условия*: клиент A владеет замком задачи 7, `expires_at` прошёл (A не
  слал heartbeat); A выполняет `status 7 done`.
- *Действия*: A пытается мутацию без повторного захвата.
- *Ожидаемый результат*: ошибка `LOCK_EXPIRED`; мутация не применена; A должен
  выполнить `lock 7 --owner A` повторно, затем мутацию.

**SC-5. Аварийное завершение в середине Apply (forward-recovery)**
- *Исходные условия*: задача 7; клиент A выполняет `status 7 done`; процесс убит
  (SIGKILL) после записи в `history/7.jsonl`, но до замены `tasks/7.md`.
- *Действия*: перезапуск Todoing (запускается recovery).
- *Ожидаемый результат*: recovery находит журнал с `seq`, `state: "applying"`;
  идемпотентно доводит: `tasks/7.md` заменён, `index.json` обновлён, журнал
  помечен `committed` и удалён; итоговое состояние согласовано (история, файл,
  индекс совпадают); нет дубликата версии в истории.

**SC-6. Аварийное завершение до commit-lock (журнал без `seq`)**
- *Исходные условия*: задача 7; клиент A выполняет `status 7 done`; процесс убит
  после записи журнала (`state: "prepared"`), но до захвата commit-lock.
- *Действия*: перезапуск Todoing.
- *Ожидаемый результат*: recovery находит журнал без `seq`; он изолируется в
  quarantine; артефакты **не** применяются (Apply не начинался); состояние задачи 7
  не изменилось; транзакция не завершена; пользователю нужно повторить команду.

**SC-7. Повреждённый журнал**
- *Исходные условия*: в `.todoing/journal/` лежит нечитаемый файл `bad.json`
  (обрезанный JSON); также есть валидный незавершённый журнал с `seq`.
- *Действия*: перезапуск Todoing.
- *Ожидаемый результат*: `bad.json` изолируется в quarantine (не парсится);
  валидный журнал восстановлен; `bad.json` не блокировал восстановление;
  повреждённая транзакция не считается завершённой.

**SC-8. Rebase при изменении base**
- *Исходные условия*: задача 7; клиент A в Prepare читает `index.json` (hash H1);
  клиент B успевает зафиксировать мутацию, изменив `index.json` (hash H2), до того
  как A захватил commit-lock.
- *Действия*: A захватывает commit-lock, сверяет base (H1 ≠ H2).
- *Ожидаемый результат*: A выполняет rebase — пере-вычисляет индекс из текущего
  (H2) + свою дельту; применяет; обе мутации (B и A) сохранены в индексе; A не
  получил `CONCURRENT_MODIFICATION` (rebase устранил конфликт).

**SC-9. `CONCURRENT_MODIFICATION` при несовместимой дельте**
- *Исходные условия*: задача 7, статус `todo`; клиент A в Prepare читает статус
  `todo` и готовит переход в `done`; клиент B успевает сменить статус в `cancelled`
  и зафиксировать; A захватывает commit-lock.
- *Действия*: A при rebase обнаруживает, что его дельта (переход из `todo`) не
  применима к текущему состоянию (`cancelled`).
- *Ожидаемый результат*: A получает `CONCURRENT_MODIFICATION`; его журнал удалён;
  состояние задачи = `cancelled` (результат B); A должен повторить операцию от
  текущего состояния.

**SC-10. Эксклюзивность чтения при блокировке**
- *Исходные условия*: задача 7 заблокирована владельцем A; клиент B выполняет
  `see 7` и `ls`.
- *Действия*: B читает заблокированную задачу.
- *Ожидаемый результат*: `see 7` → `LOCK_HELD`; `ls` → для задачи 7 только
  `{"id": 7, "locked": true}` (без содержимого); весь список не отклоняется.

## Итог

v3 устраняет все 8 замечаний аудита v2:
1. **Параллельные WAL** — commit-lock сериализует Apply; read-modify-write
   `index.json`/`counter.json` под одним замком исключает потерянные обновления;
   `seq` сохраняет порядок фиксации; rebase разрешает конфликты base.
2. **Блокировки** — heartbeat от текущего момента; check-and-act атомен под
   commit-lock; rebase-захват истёкшего без гонок; `LOCK_EXPIRED` для собственного
   истечения.
3. **Soft-delete** — команда `restore` с определённым влиянием (новая версия,
   статус/`control_version` не меняются, видимость в `ls`).
4. **Счётчик ID** — разделение отсутствующего/повреждённого счётчика; `max(все ID)
   + 1` без переиспользования и без ненужного пропускания.
5. **OpenSpec** — независимость сохранена; проверка завершения change — за
   Manifest; уникальность 1:1 через инварианты `bind` (активная привязка).
6. **CLI/JSON** — единый `--json`; `project_id: null` в standalone; `init --project`
   согласован; новые коды ошибок (`LOCK_EXPIRED`, `CONFIG_CORRUPT`,
   `CONCURRENT_MODIFICATION`, `IO_ERROR`); `status-add`/`status-remove`/`status-list`.
7. **История** — полный состав записи; `control_version` в каждой записи; `approve`
   создаёт версию-снимок; контрольное состояние восстанавливается однозначно.
8. **Приёмка** — 10 тестовых сценариев (SC-1…SC-10) с исходными условиями, действиями
   и ожидаемым результатом.

Архивирование и SQLite намеренно исключены. 7 открытых вопросов (О1–О7) требуют
решения пользователя и выделены отдельно.
