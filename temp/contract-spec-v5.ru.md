# Спецификация минимального контракта Todoing для Manifest — v5

> Редакция, устраняющая замечания аудита v4: конкурентная безопасность, WAL/recovery и OpenSpec lifecycle.
> В этой редакции изменяется только спецификация: код Todoing, OpenSpec changes и
> задачи Todoing не создаются.
>
> Предыдущие редакции сохранены отдельно и не изменяются:
> `contract-spec-final.ru.md` (v2), `contract-spec-v3.ru.md` (v3), `contract-spec-v4.ru.md` (v4).

## 0. Что изменилось относительно v4

Аудит v4 выявил проблемы конкурентной безопасности, WAL/recovery, реестра
статусов, UUID и OpenSpec lifecycle. В v5 они исправлены:

| # | Проблема v4 | Исправление в v5 |
|---|-------------|------------------|
| 1 | Параллельное создание задач: безопасная выдача уникального ID при конкурентных `add`; rebase обновляет ID, пути, историю, содержимое, индекс | **ID выдаётся под commit-lock** (не в Prepare); rebase при создании пере-вычисляет ID/пути/историю/индекс из текущего состояния; сценарий SC-2 переработан (§4.4, §4.5, §8.9 SC-2) |
| 2 | WAL и `seq`: атомарная и стойкая фиксация `state: applying` + `seq`; все точки сбоев между записями; однозначное восстановление; защита счётчика `seq` | `state: applying` + `seq` фиксируются **одной атомарной записью журнала**; точки сбоев W0–W7 с восстановлением для каждой; счётчик `seq` восстанавливается как `max(файл, max seq журналов)` (§4.5) |
| 3 | Блокировки: атомарный захват истёкшего замка **без разрыва** между удалением старого и созданием нового; какие операции синхронизируются через commit-lock; требования к замкам для всех команд-мутаций; `--owner` и исключения | Lease захватывается под per-task guard с OS-level межпроцессной блокировкой; rename/re-read не используются как арбитраж (§4.7) |
| 4 | Счётчик ID: формула восстановления `next_id = max(max_existing_id + 1, extracted_next_id)`; missing vs corrupted; без лишних пропусков | Формула исправлена; поведение при отсутствии и повреждении счётчика разделено; пропускание только до уже зафиксированного значения счётчика (§4.4) |
| 5 | OpenSpec и привязки: проверка завершения отделена от снятия ссылки; уникальность активной привязки | Manifest проверяет успешный OpenSpec Archive; `unbind` только снимает ссылку; конфликт `restore` → `BINDING_CONFLICT` (§4.9) |
| 6 | Приёмка: сценарии для всех исправленных механизмов; исправление неверной ссылки на интеграционный сценарий в §6 | Добавлены сценарии SC-11…SC-16; интеграционный сценарий вынесен в SC-11, ссылка в §6 исправлена (§6, §8.9) |

**Решения пользователя (зафиксированы в v4):**

- **D1** — `owner` — **UUID** клиентской сессии (UUIDv4).
- **D2** — команда итогового коммита — **`final-commit`**.
- **D3** — проверка завершения OpenSpec change — **ответственность Manifest**.
- **D4** — `approve`, `bind`, `restore`, `unbind` **требуют активной блокировки**
  владельцем.
- **D5** — `unbind` — **самостоятельная операция**, не заменяется soft-delete.

## 2. Принятые решения пользователя

### 2.1 Сохранённые из v2/v3 (П1–П8)

Решения **не меняются** (ограничение: не менять утверждённые пользователем
решения). Перечислены для полноты; детали — в v2 §1.

- **П1** — `--owner` обязателен для `lock`/`heartbeat`/`unlock`; генерируется
  клиентской сессией. **v5-уточнение (D1):** `owner` — **UUIDv4** клиентской
  сессии; Todoing проверяет канонический UUIDv4, включая version=4 и RFC 4122 variant bits.
- **П2** — TTL по умолчанию 300 с; heartbeat каждые 60 с.
- **П3** — повторный `approve` разрешён; контрольная версия только вперёд, только
  явной операцией.
- **П4** — `deleted` и `status` независимы; soft-delete не меняет статус; физическое
  удаление запрещено.
- **П5** — `final_commit` устанавливается отдельной явной операцией. **v4-уточнение
  (D2):** команда — **`final-commit`**.
- **П6** — standalone допустим; при интеграции `init` и Project ID обязательны.
- **П7** — `ls` показывает ID и `locked` для чужой заблокированной задачи, без
  содержимого.
- **П8** — `openspec_change` проверяется только по формату; Todoing не зависит от
  OpenSpec.

### 2.2 Новые решения v4 (D1–D5)

- **D1** — `owner` — UUIDv4 клиентской сессии (см. П1).
- **D2** — команда итогового коммита — `final-commit` (см. П5).
- **D3** — проверка завершения OpenSpec change — ответственность **Manifest**
  (Todoing не читает OpenSpec и не знает, завершён ли change).
- **D4** — `approve`, `bind`, `restore`, `unbind` требуют **активной блокировки**
  владельцем (как и все мутации задачи).
- **D5** — `unbind` — самостоятельная операция; **не заменяется** soft-delete
  задачи (soft-delete освобождает привязку как побочный эффект, но `unbind`
  снимает привязку без удаления задачи).

## 3. Контракт CLI/JSON

### 3.1 Версия контракта и совместимость

- Версия контракта — semver, в v4 — `2.1.0` (minor относительно v3 `2.0.0`:
  добавлена команда `unbind` и capability `unbind` — аддитивное изменение для
  потребителя JSON; изменения алгоритмов WAL/locks/ID — внутренняя реализация,
  для потребителя не ломающие).
- Носители:
  - `todoing contract` → `{"contract_version":"2.1.0","capabilities":[...]}`;
  - поле `contract_version` в **каждом** JSON-ответе;
  - `todoing version` дополняется строкой `contract: 2.1.0`.
- **Capabilities**: `project_id, history, versions, control_version, locks,
  atomicity, commit_lock, restore, unbind, configurable_statuses, openspec_change`.
- **Правила совместимости**: major — ломающее; minor/patch — аддитивное; потребитель
  игнорирует неизвестные поля.
- **Несовместимый major** → `CONTRACT_MISMATCH`; отсутствующая capability →
  `CAPABILITY_MISSING`.

### 3.2 JSON-режим и формат вывода

- **Единый JSON-режим**: глобальный флаг `--json` включает машиночитаемый вывод для
  **любой** команды. Без `--json` — человекочитаемый вывод. Контракт Manifest
  использует **только** `--json`.
- **Вывод в `--json`**:
  - успех → stdout, JSON-обёртка (§3.4), код выхода `0`;
  - ошибка → stderr, JSON-обёртка (§3.5), код выхода `1`.
- **Каждая команда** в `--json` возвращает ту же обёртку; payload в `data` зависит от
  команды (таблица §3.3).

### 3.3 Команды и их payload

| Команда | Назначение | `data` при успехе |
|---------|-----------|-------------------|
| `init --project <id>` | Создать хранилище с Project ID | `{"project_id": "<id>"}` |
| `contract` | Версия + capabilities | `{"contract_version","capabilities"}` |
| `version` | Версия бинарника + контракт | `{"version","contract_version"}` |
| `add … [--owner <uuid>]` | Создать задачу (опц. сразу заблокировать) | объект задачи (§3.6) |
| `ls [--include-deleted]` | Список задач | массив объектов (полных или `{id, locked}`) |
| `see <id>` | Чтение задачи | объект задачи (§3.6) |
| `status <id> <s> --owner <uuid>` | Сменить статус | объект задачи |
| `label <id> … --owner <uuid>` | Изменить метки | объект задачи |
| `body <id> … --owner <uuid>` / `append <id> … --owner <uuid>` | Изменить тело | объект задачи |
| `commit <id> <ref> --owner <uuid>` | Добавить commit-ref | объект задачи |
| `bind <id> --change <name> --owner <uuid>` | Привязать OpenSpec change | объект задачи |
| `unbind <id> --owner <uuid>` | Снять привязку OpenSpec change | объект задачи (`openspec_change: null`) |
| `final-commit <id> <ref> --owner <uuid>` | Установить итоговую ссылку | объект задачи |
| `delete <id> --owner <uuid>` | Soft-delete | объект задачи (`deleted: true`) |
| `restore <id> --owner <uuid>` | Восстановить soft-deleted задачу | объект задачи (`deleted: false`) |
| `approve <id> --owner <uuid>` | Поставить контрольную версию | объект задачи |
| `lock <id> --owner <uuid> [--ttl <s>]` | Захват блокировки | `{"owner","acquired_at","expires_at"}` |
| `heartbeat <id> --owner <uuid> [--ttl <s>]` | Продлить блокировку | `{"owner","expires_at"}` |
| `unlock <id> --owner <uuid>` | Освободить блокировку | `{"released": true}` |
| `status-add <name>` | Добавить кастомный статус | `{"custom_statuses":[…]}` |
| `status-remove <name>` | Удалить кастомный статус | `{"custom_statuses":[…]}` |
| `status-list` | Список валидных статусов | `{"base":[…],"custom":[…]}` |

> `init` принимает `--project` как **позиционный аргумент команды** (не глобальный
> флаг), т.к. при инициализации хранилище ещё не существует. Для всех остальных
> команд `--project` — глобальный флаг.
>
> **`--owner`** (UUIDv4, D1) обязателен для всех команд-мутаций задачи и для
> `lock`/`heartbeat`/`unlock`; для `add` — опционален (заблокировать новую задачу
> при создании); для `status-add`/`status-remove`/`status-list`/`init`/`see`/`ls`/
> `contract`/`version` — не требуется (см. §4.7, таблица требований к `--owner`).

### 3.4 Формат ответа (успех)

```json
{
  "contract_version": "2.1.0",
  "project_id": "manifest",
  "ok": true,
  "data": { }
}
```

- `project_id` — строка или `null`. В **standalone-режиме** (без `init`)
  `project_id: null`. При интеграции — значение из `project.json`.

### 3.5 Формат ошибки

Ошибки — на stderr, код выхода `1`:

```json
{
  "contract_version": "2.1.0",
  "project_id": "manifest",
  "ok": false,
  "error": {"code": "LOCK_HELD", "message": "task 7 is locked by 'a1b2…' until 2026-11-23T12:05:00"}
}
```

**Каталог кодов ошибок**:

| code | Смысл |
|------|-------|
| `INVALID_PROJECT` | `--project` не совпадает с Project ID хранилища |
| `NO_PROJECT` | Хранилище не инициализировано (нет `project.json`) при интеграции |
| `UNKNOWN_TASK` | Задача с таким ID не существует |
| `LOCK_HELD` | Задача заблокирована другим клиентом (активный чужой замок) |
| `LOCK_OWNER` | Операция над чужим замком (не владелец) |
| `LOCK_EXPIRED` | Собственная блокировка истекла (владелец пытается оперировать, но TTL прошёл) |
| `CONCURRENT_MODIFICATION` | Базовое состояние изменилось между prepare и commit; требуется повтор |
| `BINDING_CONFLICT` | Привязка нарушает инвариант 1:1 активной привязки (двойная `bind`, `restore` при занятой привязке) |
| `CONTRACT_MISMATCH` | Major-версия контракта несовместима |
| `CAPABILITY_MISSING` | Требуемая capability отсутствует |
| `VALIDATION` | Нарушение валидации (пустой title, неизвестный статус, формат `openspec_change`) |
| `HOOK_REJECTED` | Хук отклонил операцию (exit ≠ 0) |
| `CONFIG_CORRUPT` | Повреждена конфигурация (`project.json`, `statuses.json`, `counter.json`, `seq`) и она не восстановлена автоматически |
| `IO_ERROR` | Ошибка ввода-вывода (файл недоступен, диск полон) |

> v4-уточнение: конфликт привязки вынесен в отдельный код `BINDING_CONFLICT`
> (ранее — `VALIDATION`), чтобы отличить нарушение инварианта 1:1 от прочих
> ошибок валидации.

### 3.6 Объект задачи

```json
{
  "id": 7,
  "title": "Минимальный контракт Todoing",
  "status": "in_progress",
  "labels": ["mvp", "integration"],
  "body": "Спецификация контракта",
  "commits": ["a1b2c3d", "e4f5a6b"],
  "final_commit": "e4f5a6b",
  "openspec_change": "add-todoing-contract",
  "deleted": false,
  "added_at": "2026-11-23T10:00:00",
  "current_version": 4,
  "control_version": 3,
  "versions": [
    {"version": 1, "status": "todo",        "created_at": "2026-11-23T10:00:00", "event": "create",  "control_version": null},
    {"version": 2, "status": "in_progress", "created_at": "2026-11-23T11:00:00", "event": "status",  "control_version": null},
    {"version": 3, "status": "in_progress", "created_at": "2026-11-23T12:00:00", "event": "approve", "control_version": 3},
    {"version": 4, "status": "in_progress", "created_at": "2026-11-23T13:00:00", "event": "final-commit", "control_version": 3}
  ]
}
```

- `versions[]` — краткий список (только `version`, `status`, `created_at`, `event`,
  `control_version`). Полный снимок каждого состояния — в истории (§4.3).
- `control_version` в объекте задачи — текущее значение указателя.
- `openspec_change` — `null`, если привязка снята (`unbind`) или никогда не
  устанавливалась.

### 3.7 `ls` и блокировка

- Для чужой заблокированной задачи `ls` возвращает **только** `{"id", "locked": true}`
  (П7), без содержимого и остальных полей.
- Для своей (владельца) или незаблокированной задачи — полный объект задачи.
- `ls --include-deleted` включает soft-deleted задачи (иначе они скрыты).

## 4. Модель

### 4.1 Статусы

- Базовые статусы: `todo`, `in_progress`, `done`, `cancelled`.
- `.todoing/statuses.json` содержит только кастомные статусы.
- `status-add` и `status-remove` получают commit-lock до чтения/изменения реестра.
- `status-remove` под тем же lock проверяет все задачи; используемый статус
  удалить нельзя (`VALIDATION`).
- Все мутации задач проверяют целевой статус под commit-lock. Поэтому удаление
  статуса не может вклиниться между проверкой и фиксацией мутации.
- `status-list` читает согласованный снимок; эти команды не создают версии задач.
- Переходы между валидными статусами свободные; внутренние этапы Manifest не
  являются статусами Todoing. Статусы — строки, не enum.
### 4.2 Project ID

- **Создание**: `todoing init --project <id>` создаёт `.todoing/project.json`:
  ```json
  {"project_id": "manifest", "contract_version": "2.1.0"}
  ```
- **Источник истины**: `.todoing/project.json`.
- **Неизменяемость**: после создания `project_id` не меняется. Несовпадение
  `--project` → `INVALID_PROJECT`.
- **Обработка несовпадения**:
  - `--project` задан и не совпадает → `INVALID_PROJECT`.
  - `--project` задан, но `project.json` отсутствует → `NO_PROJECT`.
  - `--project` не задан (standalone) → Project ID не требуется (П6); в JSON
    `project_id: null`.
- **Повреждённый `project.json`**: не читается/не парсится → `CONFIG_CORRUPT`
  (не восстанавливается автоматически, т.к. Project ID — источник истины и его
  нельзя угадать).
- **Граница**: механизм передачи `--project` из AI-harness — **вне Manifest**.

### 4.3 История и версии

- **Append-only журнал**: `.todoing/history/{id}.jsonl` — по одной неизменяемой
  записи на строку.
- **Полный состав записи истории**:
  ```json
  {
    "version": 4,
    "task_id": 7,
    "status": "in_progress",
    "title": "Минимальный контракт Todoing",
    "labels": ["mvp", "integration"],
    "body": "Спецификация контракта",
    "commits": ["a1b2c3d", "e4f5a6b"],
    "final_commit": "e4f5a6b",
    "openspec_change": "add-todoing-contract",
    "deleted": false,
    "control_version": 3,
    "event": "final-commit",
    "created_at": "2026-11-23T13:00:00"
  }
  ```
  Запись — **полный снимок** состояния задачи на момент версии (не дифф). Это
  обеспечивает однозначное восстановление любого состояния, включая контрольное.
- **`control_version` в записи**: каждая запись хранит значение `control_version` на
  момент создания версии. Контрольная версия = запись с `version == control_version`.
- **Аддитивность/неизменяемость**: записи только дописываются, никогда не
  переписываются и не удаляются. Текущее состояние = последняя версия.
- **Триггер версии**: каждое успешное сохранение (`add`, `status`, `label`, `body`,
  `append`, `commit`, `bind`, `unbind`, `final-commit`, `approve`, `delete`,
  `restore`) дописывает новую версию.
- **Контрольная версия**:
  - `control_version` — указатель на номер версии, устанавливается **только**
    явной операцией `approve` (П3).
  - **`approve` создаёт новую версию**: `approve` дописывает запись с
    `event: "approve"`, в которой `control_version` устанавливается в
    `current_version + 1` (номер создаваемой версии). Снимок этой записи = текущее
    состояние задачи на момент `approve`.
  - **Повторный `approve`** (П3): создаёт ещё одну версию-снимок, `control_version`
    передвигается вперёд.
  - До первого `approve` `control_version = null` во всех записях.
  - **Восстановление контрольного состояния**: читается запись с
    `version == control_version` из истории — полный снимок контрольного состояния.

### 4.4 ID задач

- **Проблема**: «max по существующим файлам + 1» недостаточен.
- **Решение**: **монотонный счётчик** `.todoing/counter.json`:
  ```json
  {"next_id": 8}
  ```
- **Выдача (v5-уточнение)**: ID **не выдаётся в Prepare** (там он был бы
  «предварительным» и мог бы конфликтовать при параллельных `add`). ID выдаётся
  **под commit-lock**, в фазе Apply/validate:
  1. Транзакция `add` проходит Prepare **без** конкретного ID (в журнале
     `task_id: null`, артефакты вычислены как «новая задача с ещё не известным ID»).
  2. Под commit-lock транзакция читает `counter.json`, берёт `next_id` как **свой**
     ID, вычисляет все артефакты (файл `tasks/{next_id}.md`, запись истории
     `history/{next_id}.jsonl`, индекс, новый счётчик `next_id + 1`).
  3. Записывает `counter.json` = `next_id + 1` (атомарно, под commit-lock).
  - Таким образом, выдача ID и запись счётчика происходят в одной критической
    секции commit-lock: два параллельных `add` не могут получить один ID.
- **Rebase при создании (v4-исправление)**: если между Prepare и Apply другая
  транзакция изменила `counter.json` (выдала ID), текущая транзакция при rebase
  **пере-вычисляет свой ID** из текущего `counter.json` (берёт свежий `next_id`),
  пере-вычисляет **все** артефакты с новым ID: путь файла `tasks/{new_id}.md`,
  путь истории `history/{new_id}.jsonl`, содержимое файла (поле `id`), запись
  истории (поле `task_id`), запись в `index.json` (ключ = `new_id`). Это
  гарантирует, что ID, пути, история, содержимое и индекс согласованы с фактическим
  выданным ID.
- **Монотонность**: счётчик только растёт.
- **Восстановление (v4-исправление формулы)**:
  - **Общая формула**: `next_id = max(max_existing_id + 1, extracted_next_id)`,
    где `max_existing_id` — максимальный ID среди **всех** файлов задач
    (включая soft-deleted), а `extracted_next_id` — значение `next_id`, извлечённое
    из `counter.json` (если извлекаемо).
  - **Счётчик отсутствует** (файл не существует): `extracted_next_id` считается
    равным `0`, поэтому `next_id = max(max_existing_id + 1, 1)`. Если файлов нет →
    `next_id = 1`.
  - **Счётчик повреждён** (файл существует, но не парсится и значение не
    извлекаемо): `CONFIG_CORRUPT` (счётчик — источник истины, угадывать нельзя).
  - **Счётчик повреждён, но значение извлекаемо** (например, обрезанный, но
    читаемый `next_id`): `next_id = max(max_existing_id + 1, extracted_next_id)`.
  - **Ключевое**: `max` берётся по **всем** файлам задач, включая soft-deleted
    (`deleted: true`), т.к. soft-delete сохраняет файл. Это исключает повторное
    использование ID после soft-delete.
  - **Без ненужного пропускания**: восстановление не «перескакивает» на произвольное
    большое значение. `next_id` — минимальное безопасное значение: оно не меньше
    `max_existing_id + 1` (нет переиспользования) и не меньше
    `extracted_next_id` (нет отката к уже выданным ID). Пропуск ID происходит
    **только** если счётчик уже зафиксировал более высокое значение (ID были
    выданы, но файл задачи не записан из-за сбоя) — такой пропуск **необходим** и
    не является ошибкой.

### 4.5 Атомарность и восстановление (WAL) — v5

**Commit-lock:** постоянный файл `.todoing/.commit.lock`, блокируемый через
межпроцессную эксклюзивную блокировку ОС на открытом дескрипторе. Файл не
удаляется и не заменяется. Блокировка автоматически освобождается ОС при
закрытии дескриптора или аварийном завершении процесса.

**Порядок транзакции:**
1. Prepare без commit-lock: прочитать данные, сформировать семантическую дельту,
   выполнить hooks. Не назначать ID для add, не создавать постоянный журнал и
   не изменять файлы хранилища.
2. Получить commit-lock.
3. Выполнить recovery всех оставшихся журналов под этим lock.
4. Повторно прочитать актуальные задачу, index, counter, statuses и привязки;
   проверить предусловия и выполнить rebase дельты. Неприменимая дельта →
   `CONCURRENT_MODIFICATION`, без журнала и без частичных изменений.
5. Для add назначить ID только теперь, пересчитать все пути и артефакты.
   Если передан `--owner`, подготовить lease новой задачи в той же транзакции.
6. Создать `journal/{txn_id}.json` со всеми окончательными артефактами,
   `state: prepared`, `seq: null`. Журнал создаётся только под commit-lock.
7. Одной атомарной заменой журнала записать `state: applying` и `seq`.
   Затем атомарно обновить `.todoing/seq`.
8. Применить артефакты в порядке: task file, index, counter (для add), lease
   (если add --owner), history; затем пометить журнал `committed`.
9. Успех возвращается только после sync_all файлов, атомарной замены и
   синхронизации родительских каталогов (на Windows — документированный
   эквивалент). Освободить commit-lock, затем удалить committed-журнал.

**Durability:** запись артефакта выполняется через temp-файл в том же каталоге,
`write + flush + sync_all`, атомарную замену целевого файла и sync родительского
каталога. Ошибка синхронизации не маскируется как успешная операция.

**История:** логически append-only. Чтобы исключить оборванную JSONL-строку,
история формируется как новый полный файл: предыдущие строки копируются без
изменения, новая запись добавляется в конец, затем файл атомарно заменяется.
Recovery проверяет `(task_id, version)` и не создаёт дубликат.

**Журнал:** содержит полные конечные байты всех артефактов и их ожидаемые хеши.
Recovery не пересчитывает бизнес-дельту, а идемпотентно приводит артефакты к
записанному состоянию.

**Точки сбоя:**

| Точка | Последнее устойчивое действие | Recovery |
|---|---|---|
| W0 | Нет журнала; Prepare завершён/прерван | Ничего не применять; повтор команды |
| W1 | Журнал prepared, seq отсутствует | Изолировать после получения commit-lock; артефакты не применялись |
| W2 | Журнал applying + seq | Довести все артефакты до записанных хешей |
| W3 | Файл задачи записан | Проверить/довести index, counter, lease и history |
| W4 | Index записан | Проверить/довести counter, lease и history |
| W5 | Counter/lease записаны | Проверить/довести history |
| W6 | History записана | Проверить все артефакты и записать committed |
| W7 | Журнал committed | Проверить артефакты и удалить журнал |

**Recovery и конкуренция:**
- Ни один процесс не сканирует, не изолирует и не применяет журналы до получения
  commit-lock. Поэтому живой процесс не может потерять свой prepared-журнал.
- Recovery выполняется под commit-lock; два процесса не восстанавливают журнал
  одновременно. Новый процесс сначала восстанавливает, затем начинает транзакцию.
- Если после получения commit-lock обнаружен prepared без seq, создавший его
  процесс уже не удерживает lock: журнал изолируется, команда повторяется.
- Applying всегда доводится до конца; committed удаляется после проверки артефактов.
- Журналы обрабатываются по возрастанию seq. Повреждённый журнал изолируется;
  если невозможно доказать целостность последовательности или состояния,
  мутации прекращаются с `CONFIG_CORRUPT`.
- `last_seq = max(значение файла, максимальный seq валидных журналов)`;
  счётчик не уменьшается. Пропуски не объявляются невозможными: при повреждённом
  журнале автоматическое продолжение блокируется до восстановления целостности.

**Rebase:** Prepare содержит только намерение операции. Под commit-lock все
артефакты пересчитываются от актуального состояния. Для add ID и пути назначаются
только под lock; для существующей задачи версия = актуальный current_version + 1.
Предусловия проверяются повторно. Неразрешимый конфликт → `CONCURRENT_MODIFICATION`.

**Порядок блокировок:** commit-lock → per-task guard (§4.7.1). Lease-only операции
берут только per-task guard и никогда не запрашивают commit-lock.

**Hooks:** выполняются до commit-lock. Все предусловия повторно проверяются под
commit-lock; hook не может самостоятельно менять хранилище Todoing.


### 4.6 Удаление и восстановление (soft-delete + restore)

- **Физическое удаление запрещено** (П4).
- **`delete <id>`** (soft-delete):
  - устанавливает `deleted: true` (не статус, а отдельное поле), создаёт новую
    версию, **не удаляет** файл задачи и не удаляет записи истории;
  - `deleted` и `status` **независимы** (П4): статус не меняется;
  - задача с `deleted: true` скрыта из `ls` по умолчанию, но доступна через `see`
    и в истории;
  - `ls --include-deleted` показывает её;
  - **влияние на привязку**: привязка задачи становится **неактивной** (§4.9).
- **`restore <id>`** (D4 — требует активной блокировки):
  - **Предусловие**: задача существует и `deleted: true`. Иначе → `UNKNOWN_TASK` /
    `VALIDATION` (если не удалена).
  - **Действие**: устанавливает `deleted: false`, создаёт **новую версию** с
    `event: "restore"`.
  - **Влияние на историю**: дописывается новая запись-снимок с `deleted: false`;
    предыдущие записи (включая `deleted: true`) **не изменяются** (append-only).
  - **Влияние на версии**: `current_version` увеличивается на 1.
  - **Влияние на статус**: **не меняется** (П4 — `deleted`/`status` независимы).
  - **Влияние на `control_version`**: **не меняется** (restore не является
    `approve`).
  - **Влияние на видимость в `ls`**: задача снова появляется в `ls`.
  - **ID**: не переиспользуется (ID неизменяемы, счётчик монотонен).
  - **Влияние на привязку (v4-уточнение)**: если у задачи есть `openspec_change` и
    этот change **уже активно привязан к другой задаче** (`deleted: false`),
    `restore` **отклоняется** кодом `BINDING_CONFLICT` (инвариант 1:1, §4.9). Если
    change не занят — привязка становится активной.
  - **Блокировка**: `restore` — мутация, требует активной блокировки владельцем
    (D4).

### 4.7 Блокировки

**Файлы:** `.todoing/locks/{id}.lock` — lease; `.todoing/locks/{id}.guard` —
постоянный guard-файл; `.todoing/.commit.lock` — глобальный commit-lock.
Guard-файлы создаются при необходимости и никогда не удаляются/не переименовываются.

**UUID владельца (D1):** `--owner` — канонический UUIDv4. Todoing проверяет
hex-формат, дефисы, version bits = 4 и RFC 4122 variant bits. Некорректное
значение → `VALIDATION` до доступа к lease-файлам.

**§4.7.1 Per-task guard — единственный арбитр lease:**
1. Любая операция над lease открывает стабильный `{id}.guard` и получает
   межпроцессную эксклюзивную блокировку ОС на его дескрипторе.
2. Под guard процесс перечитывает lease, проверяет owner и expires_at.
3. Если lease отсутствует, создаёт его; если истёк — заменяет новым owner.
   Если активен у другого owner — `LOCK_HELD`; если активен у того же owner,
   повторный lock идемпотентно продлевает срок.
4. Temp-файл создаётся в том же каталоге; запись синхронизируется, затем
   атомарно заменяется lease. Rename не является арбитром гонки — арбитр guard.
5. Guard освобождается закрытием/разблокировкой дескриптора; при аварии процесса
   блокировка автоматически снимается ядром.

**Реализация:** использовать OS-level interprocess lock на постоянном файле:
POSIX `flock` либо эквивалент; Windows `LockFileEx` либо проверенную Rust-библиотеку
с обоими backend. Нельзя использовать удаление guard-файла, PID-файлы или
stale-guard cleanup. Все процессы Todoing обязаны соблюдать протокол. Если
платформа/ФС не обеспечивает требуемую семантику, вернуть `IO_ERROR`; не
переходить к небезопасному fallback. Сетевые ФС допускаются только после отдельной
проверки гарантий блокировок.

**Heartbeat:** под per-task guard проверяет owner и `expires_at > now`, затем
устанавливает `expires_at = now + TTL`. Чужой owner → `LOCK_OWNER`; истёкший
lease → `LOCK_EXPIRED`. TTL по умолчанию 300 секунд; heartbeat каждые 60 секунд.

**Unlock:** под per-task guard проверяет owner, удаляет lease и синхронизирует
каталог. Guard-файл остаётся. Чужой owner → `LOCK_OWNER`.

**Check-and-act:** мутация существующей задачи получает commit-lock, затем
per-task guard и удерживает оба до завершения WAL Apply. Owner и TTL проверяются
под guard. Heartbeat/unlock/lock не могут изменить lease между проверкой и
фиксацией. Если lease истёк до получения guard, мутация → `LOCK_EXPIRED`.
После успешной проверки TTL истечение часов во время Apply не прерывает транзакцию:
guard удерживает lease от конкурентной замены до завершения Apply.

**Add:** предсуществующий lease не нужен, но Apply всегда берёт per-task guard новой задачи. Если `--owner` передан, задача,
lease и index создаются одной WAL-транзакцией под commit-lock и guard новой задачи.

**Чтение (П7):** `see` получает per-task guard на время чтения; чужой активный
lease → `LOCK_HELD`. `ls` получает guard для каждой задачи; чужая заблокированная
задача отображается только как `{"id": N, "locked": true}`. Истёкший lease
не считается активным; перехват выполняется отдельной командой lock.

**§4.7.2 Требования к командам:**

| Команда | Per-task guard | Активный lease | --owner |
|---|---:|---:|---|
| `init`, `contract`, `version` | нет | нет | нет |
| `add` | всегда на время Apply | нет до создания | опционален |
| `ls`, `see` | да | нет | нет |
| `status`, `label`, `body`, `append`, `commit` | да | да | обязателен |
| `bind`, `unbind`, `final-commit`, `delete`, `restore`, `approve` | да | да | обязателен |
| `lock`, `heartbeat`, `unlock` | да | по семантике | обязателен |
| `status-add`, `status-remove` | нет | нет | нет |
| `status-list` | нет | нет | нет |

**§4.7.3 Порядок:** мутации задачи — commit-lock → per-task guard → lease check →
WAL Apply. Lease-only команды берут только per-task guard. Чтение берёт per-task
guard. Реестр статусов берёт commit-lock. Recovery берёт commit-lock, затем guard
для затрагиваемой задачи. Ни одна операция не захватывает commit-lock, уже удерживая
per-task guard; обратный порядок запрещён.
### 4.8 Системные операции автоматически

- Версионирование, запись в историю, метаданные (`control_version`, `added_at`,
  `deleted`, счётчик ID, `seq`) выполняются **внутри мутации автоматически**.
- Агент вызывает только высокоуровневую команду; системная часть (WAL, commit-lock,
  версия, история, индекс, счётчик) прозрачна.

### 4.9 OpenSpec

- **Поле** `openspec_change`: формат — имя change. **Валидация только по формату**
  (П8): непустая строка, валидный идентификатор. Todoing **не проверяет** наличие
  OpenSpec-каталога и **не зависит от OpenSpec** (П8, D3).
- **Уникальность связи 1:1** (инвариант активной привязки):
  - **Одна задача Todoing ↔ один OpenSpec change** (активная привязка).
  - **Активная привязка** = задача с `deleted: false` и `openspec_change == <name>`.
  - **Не допускается две задачи с одной активной привязкой**: `bind <id> --change
    <name>` проверяет, что `<name>` не привязан к другой **активной** задаче.
    Нарушение → `BINDING_CONFLICT`.
  - После soft-delete задачи её привязка **не является активной** (задача
    `deleted: true`), поэтому `<name>` можно привязать к другой задаче.
  - `restore` задачи с `openspec_change == <name>`, когда `<name>` уже активно
    привязан к другой задаче → `BINDING_CONFLICT` (§4.6).
- **Кто проверяет завершение change** (D3): **Manifest**, а не Todoing. Todoing не
  читает OpenSpec и не знает, завершён ли change.
- **Завершение change и снятие связи — разные действия**: Manifest самостоятельно
  проверяет успешное завершение штатного OpenSpec Archive. Только после успешной
  проверки Manifest вызывает `unbind <id>`. Команда `unbind` не проверяет, не
  подтверждает и не архивирует change; она только снимает сохранённую ссылку.
- **§4.9.1 Команда `unbind` (v4-новая, D5)**:
  - **Синтаксис**: `unbind <id> --owner <uuid>`.
  - **Предусловие**: задача существует и `openspec_change != null`. Иначе →
    `UNKNOWN_TASK` / `VALIDATION` (если привязки нет).
  - **Действие**: устанавливает `openspec_change: null`, создаёт **новую версию** с
    `event: "unbind"`.
  - **Влияние на историю**: дописывается новая запись-снимок с
    `openspec_change: null`; предыдущие записи **не изменяются** (append-only).
  - **Влияние на статус**: **не меняется** (unbind — не смена статуса).
  - **Влияние на `control_version`**: **не меняется**.
  - **Влияние на `deleted`**: **не меняется** (задача остаётся активной, если не
    была soft-deleted).
  - **Влияние на привязку**: привязка снимается; `<name>` больше не активно
    привязан к этой задаче и может быть привязан к другой.
  - **Блокировка**: `unbind` — мутация, требует активной блокировки владельцем (D4).
  - **Самостоятельность** (D5): `unbind` — самостоятельная операция; **не
    заменяется** soft-delete. Soft-delete освобождает привязку как **побочный
    эффект** (задача `deleted: true` → привязка неактивна), но `unbind` снимает
    привязку **без** удаления задачи.
- **Жизненный цикл**:
  - **Bind**: `bind <id> --change <name>` только после создания задачи отдельной командой.
  - **Работа**: коммиты через `commit <id> <sha>` (поле `commits`).
  - **Завершение**: `final-commit <id> <ref>` устанавливает итоговую ссылку (П5,
    D2). Change архивируется **механизмом OpenSpec** (задача Manifest, не Todoing).
  - **Освобождение**: Manifest проверяет успешный результат штатного OpenSpec Archive, затем вызывает `unbind <id>`. Команда только снимает ссылку и не подтверждает завершение.
- **`final_commit`**: поддерживает итоговую ссылку на **commit или merge**, не
  ограничивает список `commits`.
- **Независимость**: Todoing не читает `openspec/`, не проверяет содержимое.

   `contract`, capabilities (включая `commit_lock`, `restore`, `unbind`), строка в
   `version`.
2. **Project ID** — `init --project`, `project.json`, флаг `--project`,
   `INVALID_PROJECT`/`NO_PROJECT`/`CONFIG_CORRUPT`.

   ID/путей при создании, восстановление `max(max_existing_id + 1,
   extracted_next_id)` без переиспользования и без ненужного пропускания.
4. **Версии + история** — полный состав записи, `versions[]`, append-only
   `history/{id}.jsonl`, `current_version`, `control_version` в каждой записи.
5. **Контрольная версия** — `approve` создаёт версию-снимок, `control_version`
   только вперёд, восстановление контрольного состояния из истории.
6. **Атомарность + commit-lock + recovery** — WAL-журнал, commit-lock (сериализация
   Apply), validate-and-rebase, атомарная фиксация `state: applying` + `seq`,
   полный перечень точек сбоев W0–W7, защита счётчика `seq`
   (`max(файл, max seq журналов)`), forward-recovery, quarantine.
7. **Блокировки** — `lock`/`unlock`/`heartbeat` с `--owner` (UUIDv4), heartbeat от
   текущего момента, check-and-act под commit-lock, **per-task guard
   истёкшего (rename + re-read, без разрыва)**, `LOCK_EXPIRED`, эксклюзивность
   чтения; таблица требований к `--owner` и блокировкам для всех команд.
8. **Soft-delete + restore** — `delete` → `deleted: true`, `restore` →
   `deleted: false` (новая версия, статус/`control_version` не меняются, видимость
   в `ls`; при занятой привязке → `BINDING_CONFLICT`), запрет физ. удаления,
   независимость от статуса, сохранение истории.
9. **Авто-системные операции** — версионирование/история/метаданные/`seq` внутри
   мутаций.
10. **Расширяемые статусы** — `statuses.json`, `status-add`/`status-remove`/
    `status-list`.
11. **OpenSpec-ссылка** — `openspec_change` (формат), `bind` (уникальность 1:1),
    `unbind` (самостоятельная операция, D5), `final-commit` (отдельная операция,
    D2); `BINDING_CONFLICT`.

## 8. Критерии приёмки и тестовые сценарии

### 8.1 Счётчик ID

- **AC-ID-1**: При создании задачи ID выдаётся и счётчик обновляется атомарно (под
  commit-lock).
- **AC-ID-2**: ID выдаются монотонно.
- **AC-ID-3**: После soft-delete ID не переиспользуются (max по всем файлам,
  включая soft-deleted).
- **AC-ID-4**: Восстановление при **отсутствующем** счётчике: `next_id = max(max
  файлов + 1, 1)` (или 1, если файлов нет).
- **AC-ID-5**: Восстановление при **повреждённом** счётчике: `CONFIG_CORRUPT`, если
  значение не извлекаемо; иначе `max(max файлов + 1, extracted_next_id)`.
- **AC-ID-6**: Восстановление не пропускает ID без необходимости: `next_id =
  max(max_existing_id + 1, extracted_next_id)` — минимальное безопасное значение;
  пропуск только до уже зафиксированного значения счётчика.
- **AC-ID-7** (v4): При параллельных `add` каждый клиент получает уникальный ID
  (выдача под commit-lock); rebase при создании пере-вычисляет ID, пути файла/
  истории, содержимое, запись в индексе.

### 8.2 WAL, commit-lock, атомарность

- **AC-WAL-1** (v5): Prepare не пишет постоянных артефактов; commit-lock захватывается
  до recovery, rebase и создания prepared-журнала. Порядок Apply определён в §4.5.
- **AC-WAL-2**: Транзакция не завершена до фиксации всех частей.
- **AC-WAL-3** (v5): index/counter/statuses и WAL согласованно читаются/меняются под
  commit-lock; recovery также выполняется только под commit-lock.
- **AC-WAL-4**: При несовпадении base-хешей выполняется rebase (пере-вычисление из
  текущего состояния + дельта).
- **AC-WAL-5** (v4): `state: applying` и `seq` фиксируются **одной атомарной
  записью журнала** (нет состояния «`applying` без `seq`»).
- **AC-WAL-6** (v4): Счётчик `seq` защищён: записывается атомарно под commit-lock;
  при recovery `last_seq = max(файл, max seq журналов)`; не откатывается и не
  пропускает.
- **AC-WAL-7** (v5): точки W0–W7 восстанавливаются по §4.5; prepared-журнал не может
  быть изолирован другим процессом, поскольку создаётся только под commit-lock.
- **AC-WAL-8**: Forward-recovery обрабатывает журналы по возрастанию `seq`
  (идемпотентно).
- **AC-WAL-9** (v5): prepared без seq изолируется только после получения commit-lock.
- **AC-WAL-10** (v5): повреждённый журнал изолируется; если нельзя доказать целостность
  последовательности, мутации блокируются с CONFIG_CORRUPT.

### 8.3 Блокировки

- **AC-LOCK-1**: `lock`/`heartbeat`/`unlock` требуют `--owner` (UUIDv4, П1, D1).
- **AC-LOCK-2**: Захват эксклюзивен: второй клиент на активный чужой замок →
  `LOCK_HELD`.
- **AC-LOCK-3**: TTL по умолчанию 300 с (П2).
- **AC-LOCK-4**: Heartbeat каждые 60 с (П2), только владельцем.
- **AC-LOCK-5**: Heartbeat продлевает `expires_at = now + TTL` (от текущего момента).
- **AC-LOCK-6** (v5): commit-lock и per-task guard удерживаются до конца Apply; lease
  не может измениться между проверкой owner/TTL и завершением мутации.
- **AC-LOCK-7** (v5): lease операции сериализуются постоянным per-task guard с OS-level
  interprocess lock; rename/re-read сами по себе не являются арбитражем.
- **AC-LOCK-8**: Истечение собственной блокировки → `LOCK_EXPIRED` (не
  `LOCK_OWNER`, не `LOCK_HELD`); владелец повторно захватывает.
- **AC-LOCK-9**: `ls` → `{id, locked}` для чужой заблокированной (без содержимого)
  (П7).
- **AC-LOCK-10** (v5): команды соблюдают таблицу §4.7.2 и порядок §4.7.3; UUIDv4
  валидируется по формату, version и variant bits.

### 8.4 Soft-delete и restore

- **AC-DEL-1**: `delete` → `deleted: true`, не удаляет файл/историю.
- **AC-DEL-2**: Soft-delete не меняет статус (П4).
- **AC-DEL-3**: Задача с `deleted: true` видна в `see`/истории, скрыта из `ls`.
- **AC-DEL-4**: `restore` → `deleted: false`, создаёт новую версию (`event:
  "restore"`), статус и `control_version` не меняются, задача снова в `ls`.
- **AC-DEL-5**: Восстановление не переиспользует ID.
- **AC-DEL-6**: Физическое удаление никогда не выполняется.
- **AC-DEL-7** (v4): `restore` задачи, чей `openspec_change` уже активно привязан
  к другой задаче → `BINDING_CONFLICT` (инвариант 1:1).

### 8.5 Контрольная версия

- **AC-VER-1**: `control_version` устанавливается только `approve`.
- **AC-VER-2**: `approve` создаёт версию-снимок (`event: "approve"`),
  `control_version = current_version + 1`.
- **AC-VER-3**: Повторный `approve` — только вперёд (П3).
- **AC-VER-4**: Контрольное состояние восстанавливается как запись с
  `version == control_version` (полный снимок).
- **AC-VER-5**: Мутации после `approve` не сдвигают `control_version`.

### 8.6 OpenSpec

- **AC-OS-1**: `openspec_change` валидируется только по формату (П8).
- **AC-OS-2**: Todoing не читает `openspec/`, не зависит от OpenSpec (П8, D3).
- **AC-OS-3**: `bind` 1:1; две задачи с одной **активной** привязкой →
  `BINDING_CONFLICT`.
- **AC-OS-4**: После soft-delete привязка неактивна; `<name>` можно привязать к
  другой задаче.
- **AC-OS-5** (v5): Manifest проверяет успешный OpenSpec Archive; только после этого
  вызывает `unbind`. `unbind` само по себе ничего не подтверждает.
- **AC-OS-6** (v4): `unbind` — самостоятельная операция (D5): снимает
  `openspec_change` → `null`, создаёт новую версию (`event: "unbind"`), дописывает
  историю, **не меняет** статус/`control_version`/`deleted`; требует активной
  блокировки (D4).
- **AC-OS-7** (v4): `final-commit` — отдельная явная операция (П5, D2), не
  ограничивает `commits`.

### 8.7 Project ID

- **AC-PRJ-1**: `init --project` создаёт `project.json`.
- **AC-PRJ-2**: `project_id` неизменяем.
- **AC-PRJ-3**: Несовпадение → `INVALID_PROJECT`; нет `project.json` → `NO_PROJECT`.
- **AC-PRJ-4**: Standalone → `project_id: null`.
- **AC-PRJ-5**: Повреждённый `project.json` → `CONFIG_CORRUPT`.

### 8.8 Совместимость

- **AC-CMP-1**: `contract` → версия + capabilities.
- **AC-CMP-2**: Major-несовпадение → `CONTRACT_MISMATCH`.
- **AC-CMP-3**: Отсутствие capability → `CAPABILITY_MISSING`.
- **AC-CMP-4**: Потребитель игнорирует неизвестные поля.

### 8.9 Тестовые сценарии конкурентности, гонок и аварий

Для каждого сценария указаны исходные условия, действия, ожидаемый результат.

**SC-1. Конкурентные мутации разных задач (потерянные обновления индекса)**
- *Исходные условия*: задачи 7 и 8 существуют; `index.json` содержит обе; два
  клиента A и B.
- *Действия*: A выполняет `status 7 done`, B одновременно выполняет `status 8 done`.
  Оба проходят Prepare параллельно, затем конкурируют за commit-lock.
- *Ожидаемый результат*: обе мутации зафиксированы; `index.json` содержит обновлённые
  статусы **и** 7, **и** 8 (нет потерянного обновления); `seq` у транзакции A и B
  различны; история каждой задачи содержит свою версию.

**SC-2. Конкурентное создание задач (v4 — безопасная выдача ID)**
- *Исходные условия*: `counter.json` = `{"next_id": 10}`; два клиента A и B
  одновременно выполняют `add`.
- *Действия*: A и B параллельно проходят Prepare (без конкретного ID), затем
  конкурируют за commit-lock. Первый (A) под commit-lock берёт `next_id = 10`,
  вычисляет артефакты с ID 10, записывает `counter.json = 11`. Второй (B) под
  commit-lock видит `counter.json = 11`, берёт `next_id = 11`, вычисляет артефакты
  с ID 11, записывает `counter.json = 12`.
- *Ожидаемый результат*: A получил ID 10, B получил ID 11 (или наоборот);
  `counter.json` = `{"next_id": 12}`; нет двух задач с одним ID; нет пропущенного
  ID; файлы `tasks/10.md` и `tasks/11.md`, записи истории `history/10.jsonl` и
  `history/11.jsonl`, записи в `index.json` (ключи 10 и 11) согласованы с
  фактическими ID.

**SC-3. Гонка захвата истёкшего lease через per-task guard (v5)**
- *Исходные условия*: lease задачи 7 истёк; A и B одновременно выполняют lock.
- *Действия*: оба открывают постоянный `7.guard` и запрашивают OS-exclusive lock.
- *Ожидаемый результат*: guard последовательно получает только один процесс.
  Победитель заменяет lease; второй после получения guard перечитывает новый lease
  и получает `LOCK_HELD`. Rename/re-read без guard не считается арбитражем.

**SC-4. Истечение собственной блокировки**
- *Исходные условия*: клиент A владеет замком задачи 7, `expires_at` прошёл (A не
  слал heartbeat); A выполняет `status 7 done`.
- *Действия*: A пытается мутацию без повторного захвата.
- *Ожидаемый результат*: ошибка `LOCK_EXPIRED`; мутация не применена; A должен
  выполнить `lock 7 --owner A` повторно, затем мутацию.

**SC-5. Аварийное завершение в середине Apply (forward-recovery)**
- *Исходные условия*: задача 7; клиент A выполняет `status 7 done`; процесс убит
  (SIGKILL) после замены `tasks/7.md`, но до обновления `index.json` (точка W3).
- *Действия*: перезапуск Todoing (запускается recovery).
- *Ожидаемый результат*: recovery находит журнал с `seq`, `state: "applying"`;
  идемпотентно доводит: `tasks/7.md` заменён, `index.json` обновлён, журнал
  помечен `committed` и удалён; итоговое состояние согласовано; нет дубликата
  версии в истории (идемпотентная проверка по номеру версии).

**SC-6. Аварийное завершение до commit-lock (журнал без `seq`)**
- *Исходные условия*: задача 7; клиент A выполняет `status 7 done`; процесс убит
  после создания журнала (`state: "prepared"`, точка W1); commit-lock удерживается до аварии.
- *Действия*: перезапуск Todoing.
- *Ожидаемый результат*: recovery находит журнал без `seq`; он изолируется в
  quarantine; артефакты **не** применяются (Apply не начинался); состояние задачи 7
  не изменилось; транзакция не завершена; пользователю нужно повторить команду.

**SC-7. Повреждённый журнал**
- *Исходные условия*: в `.todoing/journal/` лежит нечитаемый файл `bad.json`
  (обрезанный JSON); также есть валидный незавершённый журнал с `seq`.
- *Действия*: перезапуск Todoing.
- *Ожидаемый результат*: `bad.json` изолируется в quarantine (не парсится);
  валидный журнал восстановлен; `bad.json` не блокировал восстановление;
  повреждённая транзакция не считается завершённой.

**SC-8. Rebase при изменении base**
- *Исходные условия*: задача 7; клиент A в Prepare читает `index.json` (hash H1);
  клиент B успевает зафиксировать мутацию, изменив `index.json` (hash H2), до того
  как A захватил commit-lock.
- *Действия*: A захватывает commit-lock, сверяет base (H1 ≠ H2).
- *Ожидаемый результат*: A выполняет rebase — пере-вычисляет индекс из текущего
  (H2) + свою дельту; применяет; обе мутации (B и A) сохранены в индексе; A не
  получил `CONCURRENT_MODIFICATION` (rebase устранил конфликт).

**SC-9. `CONCURRENT_MODIFICATION` при несовместимой дельте**
- *Исходные условия*: задача 7, статус `todo`; клиент A в Prepare читает статус
  `todo` и готовит переход в `done`; клиент B успевает сменить статус в `cancelled`
  и зафиксировать; A захватывает commit-lock.
- *Действия*: A при rebase обнаруживает, что его дельта (переход из `todo`) не
  применима к текущему состоянию (`cancelled`).
- *Ожидаемый результат*: A получает `CONCURRENT_MODIFICATION`; его журнал удалён;
  состояние задачи = `cancelled` (результат B); A должен повторить операцию от
  текущего состояния.

**SC-10. Эксклюзивность чтения при блокировке**
- *Исходные условия*: задача 7 заблокирована владельцем A; клиент B выполняет
  `see 7` и `ls`.
- *Действия*: B читает заблокированную задачу.
- *Ожидаемый результат*: `see 7` → `LOCK_HELD`; `ls` → для задачи 7 только
  `{"id": 7, "locked": true}` (без содержимого); весь список не отклоняется.

**SC-11. Интеграционный сценарий (v4 — вынесен, исправлена ссылка §6)**
- *Исходные условия*: пустое хранилище; клиент A с UUID `a1b2…`.
- *Действия* (последовательность):
  1. `init --project manifest` → хранилище создано.
  2. `add "Задача" --owner a1b2…` → задача 1, заблокирована A.
  3. `status 1 in_progress --owner a1b2…` → статус изменён.
  4. `bind 1 --change add-todoing-contract --owner a1b2…` → привязка.
  5. `commit 1 a1b2c3d --owner a1b2…` → commit-ref.
  6. `approve 1 --owner a1b2…` → контрольная версия.
  7. `final-commit 1 e4f5a6b --owner a1b2…` → итоговая ссылка.
  8. `unbind 1 --owner a1b2…` → привязка снята.
  9. `unlock 1 --owner a1b2…` → замок освобождён.
- *Ожидаемый результат*: все команды успешны (`ok: true`); задача 1 имеет
  `control_version` (от `approve`), `final_commit = e4f5a6b`,
  `openspec_change = null` (после `unbind`); история содержит версии для каждого
  шага; замок освобождён.

**SC-12. Параллельные `add` с rebase ID (v4)**
- *Исходные условия*: `counter.json` = `{"next_id": 5}`; два клиента A и B
  одновременно выполняют `add`; A успевает в Prepare, B тоже.
- *Действия*: A под commit-lock берёт ID 5, записывает `counter.json = 6`. B под
  commit-lock видит `counter.json = 6`, берёт ID 6, записывает `counter.json = 7`.
- *Ожидаемый результат*: A → ID 5, B → ID 6; `counter.json = {"next_id": 7}`;
  файлы `tasks/5.md`, `tasks/6.md`; история `history/5.jsonl`, `history/6.jsonl`;
  `index.json` содержит ключи 5 и 6; нет дубликата ID, нет пропущенного ID.

**SC-13. Сбой между записью журнала `applying`+`seq` и записью `seq`-файла (v5, точка W2)**
- *Исходные условия*: задача 7; клиент A выполняет `status 7 done`; процесс убит
  после шага WAL.7 (журнал `applying` + `seq` записан), но до записи `.todoing/seq`
  (`.todoing/seq` не обновлён).
- *Действия*: перезапуск Todoing.
- *Ожидаемый результат*: recovery находит журнал с `seq`, `state: applying`;
  артефакты применяются идемпотентно; `last_seq` пересчитан как
  `max(файл, max seq журналов)` — счётчик `seq` не откатился и не потерял значение;
  состояние согласовано.

**SC-14. `unbind` и повторная `bind` (v5)**
- *Исходные условия*: задача 7 с `openspec_change = "change-x"`; владелец A.
- *Действия*: Manifest сначала успешно архивирует change штатным OpenSpec Archive,
  затем вызывает `unbind 7 --owner A`; после этого выполняется `bind 8 --change
  change-x --owner A` (задача 8 существует, не привязана).
- *Ожидаемый результат*: `unbind` успешен (новая версия `event: "unbind"`,
  `openspec_change: null`, статус не изменился); `bind 8` успешен (change-x теперь
  активен для задачи 8); инвариант 1:1 не нарушен (одна активная привязка).

**SC-15. `restore` при занятой привязке (v4)**
- *Исходные условия*: задача 7 soft-deleted (`deleted: true`) с
  `openspec_change = "change-x"`; задача 8 активна (`deleted: false`) с
  `openspec_change = "change-x"`.
- *Действия*: владелец A выполняет `restore 7 --owner A`.
- *Ожидаемый результат*: `restore` отклонён кодом `BINDING_CONFLICT` (change-x уже
  активно привязан к задаче 8); задача 7 остаётся `deleted: true`; инвариант 1:1
  сохранён. Чтобы восстановить задачу 7, сначала нужно `unbind 8`.

**SC-16. Атомарность `state: applying` + `seq` (v5)**
- *Исходные условия*: задача 7; клиент A выполняет `status 7 done`.
- *Действия*: инспекция журнала в фазе Apply после шага Apply.1.
- *Ожидаемый результат*: журнал содержит **либо** `state: prepared` и `seq: null`,
  **либо** `state: applying` и `seq: <N>` — состояния «`applying` без `seq`» или
  «`seq` без `applying`» **не существует** (одна атомарная запись).

**SC-17. Lease не меняется в середине защищённой мутации (v5)
- *Исходные условия*: A владеет активным lease задачи 7; B одновременно вызывает
  heartbeat или unlock.
- *Действия*: A получает commit-lock и per-task guard, проверяет lease и начинает
  Apply; B запрашивает тот же guard.
- *Ожидаемый результат*: B ожидает до завершения Apply A. Lease не продлевается,
  не заменяется и не удаляется между проверкой и фиксацией мутации.

**SC-18. Recovery не изолирует активный prepared-журнал (v5)
- *Исходные условия*: A получил commit-lock и создал prepared-журнал; B запускает
  команду, требующую recovery.
- *Действия*: B ожидает commit-lock; A завершает транзакцию либо аварийно завершается.
- *Ожидаемый результат*: в первом случае B видит только committed/удалённый журнал;
  во втором — orphan prepared изолируется только после получения lock. Активный
  журнал не может быть ошибочно помещён в quarantine.

**SC-19. Удаление статуса конкурентно с мутацией (v5)
- *Исходные условия*: статус review используется задачей 7; A меняет статус задачи,
  B вызывает status-remove review.
- *Действия*: обе операции конкурируют за commit-lock.
- *Ожидаемый результат*: операции выполняются последовательно. Удаление отклоняется,
  если статус всё ещё используется; последующая мутация не может установить уже
  удалённый статус.

**SC-20. UUIDv4 validation (v5)
- *Исходные условия*: передаются корректный UUIDv4, UUIDv1, UUID с неверными
  version/variant bits и произвольная непустая строка.
- *Ожидаемый результат*: принимается только корректный UUIDv4; остальные значения
  отклоняются с VALIDATION до доступа к lease-файлам.

## Итог

v5 устраняет замечания аудита v4:

1. **Lease locking:** постоянный per-task guard с OS-level interprocess lock
   сериализует acquire, heartbeat, unlock и защищённые мутации. Rename/re-read не
   используется как механизм арбитража.
2. **TOCTOU:** мутация удерживает commit-lock и per-task guard до конца Apply;
   lease не может измениться между проверкой и фиксацией.
3. **WAL/recovery:** prepared-журнал создаётся только под commit-lock после recovery
   gate; recovery не может изолировать активный журнал. Точки W0–W7 покрывают сбои;
   история записывается атомарной заменой полного JSONL-файла.
4. **Статусы:** add/remove реестра сериализуются с мутациями через commit-lock.
5. **UUID:** принимается только корректный UUIDv4.
6. **OpenSpec:** Manifest проверяет успешный штатный Archive; `unbind` только
   снимает связь и не подтверждает завершение.
7. **Решения:** `restore` при занятой привязке → `BINDING_CONFLICT`; `add --owner`
   опционален, но если передан, задача и lease создаются атомарно.

Архивирование как функция Todoing, экспорт/импорт, GUI и SQLite остаются вне MVP.
