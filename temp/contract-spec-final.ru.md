## 1. Принятые решения пользователя (финальные)

Решения, данные пользователем в ходе финализации. Они дополняют и уточняют
архитектурные решения Manifest, не отменяя их.

| # | Решение | Содержание |
|---|---------|------------|
| П1 | Владелец блокировки | `--owner` **обязателен** для `lock`, `heartbeat`, `unlock`. Идентификатор генерируется **клиентской сессией** и сохраняется на весь срок блокировки. Todoing хранит его как непрозрачную строку. |
| П2 | TTL и heartbeat | TTL по умолчанию — **300 секунд**. Heartbeat — каждые **60 секунд** (клиент обязан продлевать). |
| П3 | Повторный `approve` | **Разрешён**. Контрольная версия может быть **передвинута вперёд** (только к более высокому номеру) только явной операцией `approve`. |
| П4 | Soft-delete и статус | `deleted` и `status` **независимы**. Soft-delete **не меняет** статус. Физическое удаление запрещено. |
| П5 | `final_commit` | Устанавливается **отдельной явной операцией** (не автоматически при `done`). |
| П6 | Standalone | Standalone-режим **допустим** (без `init`). При **интеграции с Manifest** `init` и Project ID **обязательны**. |
| П7 | `ls` и блокировка | `ls` может показывать **ID и признак `locked`** для чужой заблокированной задачи, но **не её содержимое и остальные поля**. |
| П8 | `openspec_change` | Проверяется **только по формату**. Todoing **не проверяет** наличие OpenSpec-каталога и **не зависит от OpenSpec**. |

**Дополнительные уточнения (принятые):**

- **Счётчик ID** обновляется **атомарно** при создании задачи. Восстановление счётчика
  **не допускает повторного использования ID** после soft-delete.
- **WAL**: порядок фиксации транзакции определён; восстановление после аварийного
  завершения — forward-recovery; обработка повреждённой записи журнала — изоляция и
  повторный анализ. **Транзакция не считается завершённой до фиксации всех частей.**
- **Проверка владельца и TTL** выполняется **непосредственно перед каждой операцией**
  над заблокированной задачей.
- **Soft-delete** сохраняет **полную историю**; восстановление не переиспользует ID.
- **`final_commit`** поддерживает итоговую ссылку на **commit или merge** и **не
  ограничивает** существующий список `commits`.

## 2. Контракт CLI/JSON

### 2.1 Версия контракта и совместимость

- Версия контракта — semver, например `1.0.0`.
- Носители:
  - `todoing contract` → `{"contract_version":"1.0.0","capabilities":[...]}`;
  - поле `contract_version` в **каждом** JSON-ответе;
  - `todoing version` дополняется строкой `contract: 1.0.0`.
- **Capabilities** — список поддерживаемых возможностей:
  `project_id, history, versions, control_version, locks, atomicity,
  configurable_statuses, openspec_change`. Потребитель определяет поддерживаемые
  возможности по списку, а не только по номеру версии.
- **Правила совместимости**:
  - **major** — ломающее: удаление/переименование поля, изменение семантики.
  - **minor/patch** — аддитивное: только добавление полей.
  - Потребитель обязан **игнорировать неизвестные поля**.
- **Поведение при несовместимом major**:
  - Потребитель (Manifest) читает `contract_version` **до доверия любому полю**.
  - Если major не совпадает с поддерживаемым → операция отклонена кодом
    `CONTRACT_MISMATCH`; поля ответа не используются.
  - Если major совпадает, но требуется capability, которого нет в списке →
    операция отклонена кодом `CAPABILITY_MISSING`.

### 2.2 Минимальный набор команд

Сохраняем существующие команды (соевимость), добавляем новые операции.

| Команда | Назначение | Флаги |
|---------|-----------|-------|
| `todoing --project <id> <cmd>` | Глобальный флаг Project ID (обязателен при интеграции) | — |
| `init --project <id>` | Создать хранилище с Project ID | `--project` (обязателен) |
| `add` / `ls` / `see` / `status` / `label` / `body` / `append` / `commit` | Существующие мутации/чтения | получают версию + Project ID + блокировку |
| `contract` | Версия контракта + capabilities | — |
| `lock <id>` | Захват эксклюзивной блокировки | `--owner <id>` (обязателен), `--ttl <sec>` (по умолч. 300) |
| `heartbeat <id>` | Продление блокировки | `--owner <id>` (обязателен), `--ttl <sec>` |
| `unlock <id>` | Освобождение блокировки | `--owner <id>` (обязателен) |
| `approve <id>` | Поставить текущую версию как контрольную | — |
| `bind <id> --change <name>` | Привязать задачу к OpenSpec change | `--change` (обязателен) |
| `final-commit <id> <ref>` | Установить итоговую ссылку (commit или merge) | — |
| `delete <id>` | Soft-delete (физическое удаление запрещено) | — |

> `delete` **не удаляет физически** (решение 9, П4). См. §3.6.
> `final-commit` — **отдельная явная операция** (П5), не зависит от статуса.

### 2.3 Формат ответа (успех)

Каждый JSON-ответ обёрнут в оверлей с метаданными контракта:

```json
{
  "contract_version": "1.0.0",
  "project_id": "manifest",
  "ok": true,
  "data": { /* payload команды */ }
}
```

**Задача** (расширенная модель, `data` для `see`/`add`):

```json
{
  "id": 7,
  "title": "Минимальный контракт Todoing",
  "status": "in_progress",
  "labels": ["mvp", "integration"],
  "body": "Спецификация контракта",
  "commits": ["a1b2c3d", "e4f5a6b"],
  "final_commit": "e4f5a6b",
  "openspec_change": "add-todoing-contract",
  "deleted": false,
  "added_at": "2026-11-23T10:00:00",
  "current_version": 4,
  "control_version": 3,
  "versions": [
    {"version": 1, "status": "todo",        "created_at": "2026-11-23T10:00:00", "event": "create"},
    {"version": 2, "status": "in_progress", "created_at": "2026-11-23T11:00:00", "event": "status"},
    {"version": 3, "status": "in_progress", "created_at": "2026-11-23T12:00:00", "event": "commit"},
    {"version": 4, "status": "in_progress", "created_at": "2026-11-23T13:00:00", "event": "final-commit"}
  ]
}
```

**`ls` (список)**: для чужой заблокированной задачи показывает только `id` и
`locked: true` (П7), без содержимого и остальных полей:

```json
{"id": 9, "locked": true}
```

### 2.4 Формат ошибки

Ошибки — на stderr, код выхода ≠ 0, JSON-структура:

```json
{
  "contract_version": "1.0.0",
  "project_id": "manifest",
  "ok": false,
  "error": {"code": "LOCK_HELD", "message": "task 7 is locked by 'sess-a1b2' until 2026-11-23T12:05:00"}
}
```

**Каталог кодов ошибок**:

| code | Смысл |
|------|-------|
| `INVALID_PROJECT` | `--project` не совпадает с Project ID хранилища |
| `NO_PROJECT` | Хранилище не инициализировано (нет `project.json`) при интеграции |
| `UNKNOWN_TASK` | Задача с таким ID не существует |
| `LOCK_HELD` | Задача заблокирована другим клиентом (или чужой замок активен) |
| `LOCK_OWNER` | Операция над чужим замком (не владелец) |
| `CONTRACT_MISMATCH` | Major-версия контракта несовместима |
| `CAPABILITY_MISSING` | Требуемая capability отсутствует |
| `VALIDATION` | Нарушение валидации (пустой title, неизвестный статус, формат `openspec_change`) |
| `HOOK_REJECTED` | Хук отклонил операцию (exit ≠ 0) |

### 2.5 Пример сессии интеграции

```bash
# 0. Инициализация хранилища (один раз, при интеграции)
todoing init --project manifest

# 1. Клиентская сессия генерирует owner-id и захватывает задачу (TTL 300 с)
todoing --project manifest lock 7 --owner sess-a1b2 --ttl 300
# → {"contract_version":"1.0.0","project_id":"manifest","ok":true,
#    "data":{"owner":"sess-a1b2","expires_at":"..."}}

# 2. Heartbeat каждые 60 с (пока идёт работа)
todoing --project manifest heartbeat 7 --owner sess-a1b2 --ttl 300

# 3. Перевод статуса (создаёт версию)
todoing --project manifest status 7 in_progress --json

# 4. Связывание с OpenSpec change и commit
todoing --project manifest bind 7 --change add-todoing-contract
todoing --project manifest commit 7 HEAD --json

# 5. Итоговая ссылка (отдельная явная операция)
todoing --project manifest final-commit 7 e4f5a6b --json

# 6. Завершение → текущая версия становится контрольной
todoing --project manifest approve 7 --json
todoing --project manifest unlock 7 --owner sess-a1b2 --json
```

## 3. Модель

### 3.1 Статусы

- **Базовый набор** (встроен, всегда валиден, не удаляется): `todo`, `in_progress`,
  `done`, `cancelled`.
- **Расширение**: `.todoing/statuses.json` хранит **только кастомные** статусы:
  ```json
  {"custom_statuses": ["review", "blocked"]}
  ```
  Базовые 4 не записываются — они всегда валидны. Валидный набор = базовые ∪ кастомные.
- **Валидация**: целевой статус должен быть в валидном наборе → иначе `VALIDATION`.
- **Переходы**: встроенных ограничений переходов нет (свободные переходы между
  валидными статусами). Внутренние этапы Manifest — не статусы Todoing.
- **Manifest** предоставляет **рекомендуемую** конфигурацию, не навязывая её.
- Статусы — простые строки в JSON (нет enum в контракте).

### 3.2 Project ID

- **Создание**: `todoing init --project <id>` создаёт `.todoing/project.json`:
  ```json
  {"project_id": "manifest", "contract_version": "1.0.0"}
  ```
- **Источник истины**: `.todoing/project.json`.
- **Неизменяемость**: после создания `project_id` не меняется. Любая операция с
  несовпадающим `--project` → `INVALID_PROJECT`.
- **Обработка несовпадения**:
  - `--project` задан и не совпадает с `project.json` → `INVALID_PROJECT`.
  - `--project` задан, но `project.json` отсутствует → `NO_PROJECT`.
  - `--project` не задан (standalone) → Project ID не требуется (П6).
- **Обязательность при интеграции**: при интеграции с Manifest `init` и Project ID
  **обязательны** (П6). Standalone-режим без `init` допустим.
- **Граница**: механизм передачи `--project` из AI-harness — **вне Manifest**
  (решение §4). Контракт определяет только, что CLI принимает флаг и JSON несёт ID.

### 3.3 История и версии

- **Append-only журнал**: `.todoing/history/{id}.jsonl` — по одной неизменяемой записи
  на строку. Каждая строка = версия:
  `{version, status, title, labels, body, commits, final_commit, openspec_change,
  deleted, created_at, event}`.
- **Аддитивность/неизменяемость**: записи только дописываются, никогда не
  переписываются и не удаляются. Текущее состояние задачи = последняя версия.
- **Триггер версии**: каждое успешное сохранение (`add`, `status`, `label`, `body`,
  `append`, `commit`, `bind`, `final-commit`, `approve`, `delete`) дописывает новую
  версию.
- **Контрольная версия**: поле `control_version` — **указатель на номер версии**,
  устанавливается **только явной операцией `approve`** (не связана с терминальным
  статусом).
  - `approve <id>` → `control_version = current_version`.
  - **Повторный `approve` разрешён** (П3): указатель **передвигается вперёд**
    (только к более высокому номеру версии) только явной операцией.
  - До `approve` `control_version = null`; «текущая» версия — последняя.
  - **Контрольная версия хранится отдельно от текущей**: `current_version` растёт с
    каждой мутацией, `control_version` — замороженный указатель. Содержимое
    контрольной версии извлекается из истории (append-only, неизменяема).

### 3.4 ID задач

- **Проблема**: «max по существующим файлам + 1» недостаточен — при soft-delete/
  повреждении/перемещении файлов max может уменьшиться → ID переиспользуется.
- **Решение**: **монотонный счётчик** `.todoing/counter.json`:
  ```json
  {"next_id": 8}
  ```
  Счётчик — **источник истины** для выдачи ID, а не список файлов.
- **Выдача**: при создании задачи читается счётчик, выдаётся `next_id`, счётчик
  увеличивается на 1 и **записывается атомарно** (часть транзакции создания).
- **Монотонность**: счётчик только растёт, никогда не уменьшается. Даже если файлы
  задач удалены/повреждены/soft-deleted, счётчик сохранён → ID не переиспользуются.
- **Восстановление** (если счётчик повреждён/отсутствует): пересчитывается как
  `max(счётчик, max ID по файлам) + 1`. **Восстановление не допускает повторного
  использования ID** после soft-delete: soft-delete сохраняет файл задачи
  (`deleted: true`), поэтому max по файлам учитывает soft-deleted задачи.

### 3.5 Атомарность и восстановление (WAL)

- **Проблема**: сейчас `write_task` и `sync_mutation` идут раздельно → задача,
  история и индекс не меняются как единое целое.
- **Решение**: **WAL-журнал (write-ahead log) + forward-recovery**.

  **Структура транзакции** (одна успешная мутация):
  1. **Prepare**: вычислить в памяти все новые артефакты — новую версию (для
     истории), новое содержимое файла задачи, новый индекс, (для создания) новый
     счётчик ID.
  2. **Journal**: атомарно записать журнал `.todoing/journal/{txn_id}.json` с
     описанием намеренного состояния:
     `{txn_id, task_id, version_record, task_content, index_content, counter,
     state: "prepared"}`.
  3. **Apply** (каждый шаг атомен, порядок фиксирован):
     - дописать `version_record` в `history/{id}.jsonl`;
     - заменить `tasks/{id}.md` (`atomic_write`);
     - заменить `index.json` (`atomic_write`);
     - (для создания) заменить `counter.json` (`atomic_write`);
     - обновить журнал: `state: "committed"`.
  4. **Cleanup**: удалить журнал.

  **Порядок фиксации**: транзакция **не считается завершённой до фиксации всех
  частей** (история + файл + индекс + счётчик + пометка `committed`).

  **Восстановление после аварийного завершения** (forward-recovery):
  - При старте / перед каждой операцией сканируется `.todoing/journal/` на
    незавершённые транзакции.
  - Для каждого незавершённого журнала выполняется **идемпотентное** приведение
    каждого артефакта к намеренному состоянию из журнала:
    - история: дописать `version_record`, **если** последняя строка ещё не равна ей
      (идемпотентность — не дублировать);
    - файл задачи: заменить на `task_content` (идемпотентно);
    - индекс: заменить на `index_content` (идемпотентно);
    - счётчик: заменить на `counter` (идемпотентно);
    - пометить `committed`, удалить журнал.
  - Семантика: успешная мутация **всегда доводится до завершённого состояния**
    (all-or-nothing на уровне согласованности всех частей).

  **Обработка повреждённой записи журнала**:
  - Если журнал не читается/не парсится (повреждён) → он **изолируется**
    (перемещается в `.todoing/journal/quarantine/`) и **не** применяется автоматически.
  - Повреждённый журнал **не блокирует** восстановление остальных транзакций.
  - Повреждённая транзакция **не считается завершённой**; требуется ручной анализ
    (или повторный запуск операции, если она идемпотентна).

  **Хуки** выполняются **до** создания журнала, поэтому отклонённая мутация не
  оставляет артефактов.

### 3.6 Удаление (soft-delete)

- **Физическое удаление запрещено** (решение 9, П4).
- **Безопасное поведение `delete`**: команда переопределена как **soft-delete**:
  - `delete <id>` устанавливает флаг `deleted: true` на задаче (не статус, а
    отдельное поле), создаёт новую версию, **не удаляет** файл задачи и не
    удаляет записи истории.
  - `deleted` и `status` **независимы** (П4): soft-delete **не меняет** статус.
  - Задача с `deleted: true` исключается из доски по умолчанию (`ls`), но
    **доступна для чтения** через `see` и в истории.
  - `ls --include-deleted` показывает удалённые задачи.
  - Физическое удаление файла/истории **никогда** не выполняется.
- **Сохранение истории**: soft-delete сохраняет **полную историю** (все версии,
  включая версию с `deleted: true`).
- **Восстановление**: задача с `deleted: true` может быть восстановлена
  (сброс `deleted: false`), **не переиспользуя ID** (ID неизменяемы, счётчик
  монотонен).
- **Связь со статусом**: `delete` и `status cancelled` — разные механизмы.
  `cancelled` — статус результата; `deleted` — флаг видимости. Они независимы (П4).

### 3.7 Блокировки

- **Файл-замок**: `.todoing/locks/{id}.lock`:
  ```json
  {"owner": "sess-a1b2", "acquired_at": "2026-11-23T12:00:00", "expires_at": "2026-11-23T12:05:00"}
  ```
- **Захват (acquire)**: `lock <id> --owner <id> --ttl <sec>` создаёт файл атомарно
  (create-new). `--owner` **обязателен** (П1). Если файл существует и не истёк →
  `LOCK_HELD`. Захват — операцией захвата (решение §4).
- **Идентификатор владельца** (П1): генерируется **клиентской сессией** и сохраняется
  на весь срок блокировки. Todoing хранит его как **непрозрачную строку** (не
  валидирует формат, не интерпретирует).
- **Продление (heartbeat)**: `heartbeat <id> --owner <id> --ttl <sec>` обновляет
  `expires_at` (только владельцем). **TTL по умолчанию — 300 секунд** (П2).
  **Heartbeat — каждые 60 секунд** (П2): клиент обязан продлевать, чтобы удержать
  замок активным при длительной работе.
- **Освобождение (release)**: `unlock <id> --owner <id>` удаляет файл (только
  владельцем). `--owner` **обязателен** (П1).
- **TTL + crash recovery**: `expires_at = acquired_at + TTL`. При истечении замок
  считается освобождённым — новый клиент может захватить. Покрывает аварийное
  завершение агента без явного `unlock`.
- **Проверка владельца и TTL** (уточнение): выполняется **непосредственно перед
  каждой операцией** над заблокированной задачей (мутациями и `heartbeat`/`unlock`).
  Несовпадение владельца → `LOCK_OWNER`; истёкший чужой замок → захват разрешён.
- **Эксклюзивность чтения** (принятое требование): пока задача заблокирована,
  **другие клиенты не могут её читать или изменять**.
  - `see <id>` заблокированной задачи не владельцем → `LOCK_HELD`.
  - `ls` (список) (П7): для чужой заблокированной задачи показывает только **ID и
    признак `locked`**, без содержимого и остальных полей. Весь список не отклоняется.
  - Владелец читает заблокированную задачу без ограничений.

### 3.8 Системные операции автоматически

- Версионирование, запись в историю, метаданные (`control_version`, `added_at`,
  `deleted`, счётчик ID) выполняются **внутри мутации автоматически**, а не по
  усмотрению агента. Агент вызывает только высокоуровневую команду (`status`,
  `commit`, …); системная часть (WAL, версия, история, индекс, счётчик) прозрачна.

### 3.9 OpenSpec

- **Поле** `openspec_change` на задаче: формат — имя OpenSpec change
  (например, `add-todoing-contract`). **Валидация только по формату** (П8):
  непустая строка, валидный идентификатор (без пробелов/специальных символов).
  Todoing **не проверяет** наличие OpenSpec-каталога и **не зависит от OpenSpec** (П8).
- **Правила привязки**:
  - **Одна глобальная задача Todoing = одна глобальная задача OpenSpec** (1:1).
  - Привязка: `bind <id> --change <name>` (или при `add`).
  - Задача имеет **не более одной** активной привязки.
  - Повторная привязка разрешена только если предыдущий change завершён/архивирован
    (иначе `VALIDATION`).
- **Жизненный цикл связи**:
  - **Bind**: задача ↔ change связаны.
  - **Работа**: задача хранит ссылку на change; коммиты связываются через
    `commit <id> <sha>` (поле `commits`).
  - **Завершение**: `final_commit` (итоговый commit/merge) устанавливается **отдельной
    явной операцией** `final-commit <id> <ref>` (П5). Change архивируется
    **механизмом OpenSpec** (это задача Manifest, не Todoing). Todoing лишь хранит
    ссылку.
- **`final_commit`** (уточнение): поддерживает итоговую ссылку на **commit или
  merge** и **не ограничивает** существующий список `commits` — `commits` остаётся
  полным списком связанных коммитов, `final_commit` — отдельное поле с итоговой
  ссылкой.
- **Независимость**: Todoing **не зависит от OpenSpec** — хранит имя change как
  строку и валидирует только формат. Не читает `openspec/` и не проверяет
  содержимое (это задача опционального хука `before-done-openspec`).

## 8. Критерии приёмки (проверяющие механизмы)

Проверяемые механизмы и их критерии приёмки.

### 8.1 Счётчик ID

- **AC-ID-1**: При создании задачи счётчик `counter.json` обновляется **атомарно**
  (часть транзакции создания).
- **AC-ID-2**: ID выдаются монотонно (только растут).
- **AC-ID-3**: После soft-delete ID **не переиспользуются**: soft-delete сохраняет
  файл задачи (`deleted: true`), max по файлам учитывает soft-deleted задачи.
- **AC-ID-4**: Восстановление счётчика (`max(счётчик, max ID по файлам) + 1`) не
  допускает повторного использования ID после soft-delete.

### 8.2 WAL и атомарность

- **AC-WAL-1**: Порядок фиксации транзакции: журнал → история → файл → индекс →
  счётчик → `committed` → cleanup.
- **AC-WAL-2**: Транзакция **не считается завершённой** до фиксации всех частей.
- **AC-WAL-3**: При аварийном завершении процесса forward-recovery доводит все
  части до намеренного состояния (идемпотентно).
- **AC-WAL-4**: Повреждённая запись журнала изолируется в `.todoing/journal/
  quarantine/` и **не блокирует** восстановление остальных транзакций.
- **AC-WAL-5**: Повреждённая транзакция не считается завершённой; требуется ручной
  анализ.

### 8.3 Блокировки

- **AC-LOCK-1**: `lock`, `heartbeat`, `unlock` требуют `--owner` (П1).
- **AC-LOCK-2**: Захват эксклюзивен: второй клиент → `LOCK_HELD`.
- **AC-LOCK-3**: TTL по умолчанию — 300 секунд (П2).
- **AC-LOCK-4**: Heartbeat каждые 60 секунд (П2), только владельцем.
- **AC-LOCK-5**: Проверка владельца и TTL выполняется **непосредственно перед
  каждой операцией** над заблокированной задачей.
- **AC-LOCK-6**: Несовпадение владельца → `LOCK_OWNER`.
- **AC-LOCK-7**: По истечении TTL замок освобождается (crash recovery), новый
  клиент может захватить.
- **AC-LOCK-8**: `ls` показывает только ID и признак `locked` для чужой
  заблокированной задачи, без содержимого и остальных полей (П7).

### 8.4 Soft-delete

- **AC-DEL-1**: `delete` устанавливает `deleted: true`, **не удаляет** файл задачи
  и не удаляет записи истории.
- **AC-DEL-2**: Soft-delete **не меняет** статус (независимость `deleted`/`status`)
  (П4).
- **AC-DEL-3**: Задача с `deleted: true` доступна для чтения через `see` и в
  истории, скрыта из `ls` по умолчанию.
- **AC-DEL-4**: Восстановление задачи не переиспользует ID.
- **AC-DEL-5**: Физическое удаление файла/истории **никогда** не выполняется.

### 8.5 Контрольная версия

- **AC-VER-1**: `control_version` устанавливается только явной операцией `approve`.
- **AC-VER-2**: Повторный `approve` разрешён, указатель передвигается **только
  вперёд** (к более высокому номеру версии) (П3).
- **AC-VER-3**: `control_version` хранится отдельно от `current_version`; мутации
  после `approve` не сдвигают `control_version`.

### 8.6 OpenSpec

- **AC-OS-1**: `openspec_change` валидируется **только по формату** (П8).
- **AC-OS-2**: Todoing **не проверяет** наличие OpenSpec-каталога и **не зависит
  от OpenSpec** (П8).
- **AC-OS-3**: `bind` привязывает задачу к change (1:1).
- **AC-OS-4**: `final-commit` устанавливает `final_commit` **отдельной явной
  операцией** (П5), не ограничивает список `commits`.

### 8.7 Project ID

- **AC-PRJ-1**: `init --project` создаёт `project.json` (источник истины).
- **AC-PRJ-2**: `project_id` неизменяем после создания.
- **AC-PRJ-3**: Несовпадение `--project` → `INVALID_PROJECT`; нет `project.json`
  при интеграции → `NO_PROJECT`.
- **AC-PRJ-4**: Standalone-режим без `init` допустим (П6).

### 8.8 Совместимость

- **AC-CMP-1**: `contract` возвращает `contract_version` + capabilities.
- **AC-CMP-2**: Major-несовпадение → `CONTRACT_MISMATCH`; поля ответа не

- **AC-CMP-3**: Отсутствие capability → `CAPABILITY_MISSING`.
- **AC-CMP-4**: Потребитель игнорирует неизвестные поля.

## Итог

Финальная редакция v2 закрывает все 8 решений пользователя (П1–П8) и дополнительные
уточнения (счётчик ID, WAL, проверка владельца, soft-delete, `final_commit`).
Ключевые механизмы: монотонный счётчик ID с атомарным обновлением, WAL-журнал с
forward-recovery и изоляцией повреждённых записей, контрольная версия только через
`approve` (повторный — только вперёд), soft-delete с независимостью от статуса,
блокировки с `--owner`, TTL 300 с, heartbeat 60 с, Project ID с `init` и
неизменяемостью, capabilities для совместимости, `openspec_change` с `bind` и
`final-commit` (отдельная явная операция). Архивирование и SQLite намеренно
исключены. 5 оставшихся открытых вопросов (О1–О5) — детали реализации, не
влияющие на принятые архитектурные решения.
