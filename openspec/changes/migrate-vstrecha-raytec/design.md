## Решения

### D1. Повторный аудит

Предоставленный аудит — исходная точка, но не разрешение на изменение проекта. Перед реализацией повторно проверить Git, файлы, ignore rules, OpenSpec, installer и Todoing. При существенном расхождении остановиться и обновить план.

### D2. Git-история и remote

Существующий commit graph сохраняется. Запрещены переписывание истории, reset, squash, force-push и несанкционированная смена ветки.

Remote/upstream отсутствуют. До публикации пользователь выбирает стратегию резервирования и синхронизации. Без отдельного разрешения нельзя создавать hosting repository, добавлять remote, настраивать upstream или выполнять push. При выборе local-only миграция может продолжаться, но отчёт обязан отметить отсутствие удалённой копии и remote CI/PR workflow.

### D3. OpenSpec как пользовательские данные

До изменения `.gitignore` проверить точные ignore rules, `git check-ignore -v`, полный перечень tracked/untracked/ignored файлов OpenSpec и содержимое changes/specs. Подготовить перечень путей для Git и исключений; проверить секреты, generated и local-only данные.

Не выполнять слепой `git add -f openspec/`. Добавлять OpenSpec в Git можно только после согласования точного состава файлов.

Завершённые changes автоматически не архивировать. Для каждого проверить delta specs, зависимости и предусловия archive. Блокировку `fix-run-59-defects` вынести в отдельную задачу; не обходить её удалением ссылок или созданием фиктивных specs.

### D4. Manifest-файлы без перезаписи

До установки подтвердить авторитетную версию Manifest и проверить installer distribution, validation script и hooks. Несовпадение версий должно быть разрешено.

Для каждого целевого файла выполнить сравнение. `commit-rules.md` v1.0.0 нельзя автоматически заменить на v1.0.1: нужен diff, сохранение проектных правил и согласование результата. По умолчанию сохраняются `AGENTS.md`, `llms.txt`, `.llmignore`, README, LICENSE, THIRD-PARTY, tests, pipeline и остальные файлы проекта.

Hooks устанавливать и активировать только после проверки содержимого и отдельного разрешения пользователя. `core.hooksPath=.manifest/hooks` задавать после успешной проверки обоих hooks.

### D5. Project ID

Создавать `.manifest/project-id` только после подтверждения целевого проекта и только при отсутствии файла. Использовать UUIDv4 и атомарную запись. Существующий валидный ID повторно использовать; автоматически не заменять.

### D6. Todoing

Todoing устанавливает пользователь либо отдельная согласованная процедура. Manifest вызывает JSON API через локальную команду `todoing api --json` (stdin/stdout); сетевого endpoint нет.

Перед bootstrap проверить бинарный файл и версию Todoing, контракт API, наличие config/database/legacy Markdown. Не перезаписывать данные. Создавать `.todoing/config.toml` без overwrite и инициализировать store только при отсутствии store и legacy-данных. Если Todoing недоступен, остановиться и сообщить точную причину.

### D7. Этапы и разрешения

1. Read-only повторный аудит.
2. Решения пользователя: Git remote, состав OpenSpec для Git, конфликты файлов.
3. Согласованные изменения Git hygiene и OpenSpec tracking.
4. Сверка и установка Manifest; отдельное подтверждение активации hooks.
5. Project Identity и Todoing bootstrap.
6. Проверка результата и сверка registry.

Одобрение этой спецификации разрешает только подготовку плана. Оно не разрешает изменения целевого проекта, создание remote, push, активацию hooks, замену файлов, OpenSpec archive или установку Todoing.

### D8. Статус registry

Проект нельзя считать fully active, пока обязательные артефакты Manifest и hooks не прошли проверку, а состояние OpenSpec/Todoing не отражено достоверно. Использовать промежуточный статус, если он поддерживается; иначе не менять запись до итоговой проверки и отдельного согласования.

### D9. Финальная проверка

Отчёт содержит branch/HEAD/status, remote/upstream, сохранность истории, Project ID, версии Manifest-файлов, состояние hooks и `core.hooksPath`, OpenSpec tracking/validation, Todoing binary/API/config/store и блокеры.

Запускать только проверки, необходимые для миграции. Полный набор тестов приложения не запускать без отдельного решения. Пропущенные и неуспешные проверки явно отразить.

## Риски

Основные риски: отсутствие удалённой копии Git-истории; попадание локальных данных в Git при подключении OpenSpec; потеря проектных правил при обновлении файлов; активация непроверенных hooks; замена Project ID или перезапись Todoing-данных; преждевременный статус active. Меры контроля: отдельные согласования, инвентаризация, diff, запрет overwrite и доказательная финальная проверка.
