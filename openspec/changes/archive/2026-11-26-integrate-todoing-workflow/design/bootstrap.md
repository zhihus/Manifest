# Design — Bootstrap хранилища

## Назначение

Определяет процедуру инициализации Todoing хранилища для проекта Manifest:
установку бинарного файла, генерацию Project ID, запись конфигурации и
вызов `store.init` с защитой от перезаписи.

## Границы

- Установка Todoing (бинарный файл) выполняется **пользователем**. Manifest не
  скачивает, не обновляет и не устанавливает бинарный файл Todoing.
- Manifest управляет только: Project ID, конфигурацией `.todoing/config.toml`
  и вызовом `store.init` через API.
- Bootstrap не привязывается к `scripts/manifest-init.sh`, пока не подтверждено,
  что это штатная точка установки для пользователей, а не dev-инфраструктура.

## Процедура bootstrap

1. **Проверка доступности Todoing.** Manifest проверяет, что бинарный файл
   `todoing` доступен в PATH и что `todoing api --json` отвечает. При
   недоступности — остановка с диагностикой; установка выполняется
   пользователем отдельно.
2. **Project ID.** Если `.manifest/project-id` отсутствует — генерация UUIDv4
   и атомарная запись файла. Если файл существует — его значение
   используется; при существующем store сверяется с `store.info`.
3. **Конфигурация.** Manifest создаёт `.todoing/` и записывает рекомендуемый
   `config.toml` атомарно только если файла ещё нет. Существующий файл не
   перезаписывается: Manifest проверяет наличие необходимых статусов, outcome
   mapping и переходов; при несовместимости останавливает bootstrap с
   диагностикой.
4. **store.init.** Manifest вызывает `store.init` с Project ID из
   `.manifest/project-id`. Операция создаёт новое хранилище только когда БД
   не существует.
5. **Проверка.** Manifest проверяет результат через `store.info` и
   `store.verify`.

## Поведение store.init (подтверждено по исходникам)

- Создаёт `.todoing/` и новую БД только когда `todoing.db` не существует.
- Существующая БД → ошибка `store_already_initialized` (exit 6); повторная
  инициализация не выполняется.
- Legacy Markdown задачи (`.todoing/tasks/*.md`) или `index.json` → ошибка
  `migration_required` (exit 2); требуется `store.migrate`, а не `store.init`.
- Существующий `config.toml` валидируется и сохраняется; при отсутствии
  создаётся generic default конфигурация атомарной записью (temp file +
  persist_noclobber).
- Project ID из envelope используется как есть; CLI генерирует `p-<hex>`
  только при отсутствии `--project-id`, но JSON API вызовы обязаны передавать
  `project_id` в envelope.

## Запреты

- Не вызывать `store.init` поверх существующего store или legacy Markdown
  данных.
- Не перезаписывать существующий `config.toml`.
- Не скачивать и не обновлять бинарный файл Todoing.
- Не выполнять автоматическую миграцию legacy данных в MVP: возможная
  миграция — отдельная non-destructive процедура с dry-run
  (`store.migrate --dry-run`) и подтверждением пользователя.

## Ожидаемые ошибки и их обработка

| Ошибка | Значение | Поведение Manifest |
|---|---|---|
| `store_already_initialized` | БД уже существует | Сверить Project ID через `store.info`; при совпадении — продолжить, при несовпадении — остановить с `project_id_mismatch` |
| `migration_required` | Legacy Markdown/index.json | Не выполнять `store.init`; предложить пользователю отдельную процедуру миграции |
| `config_invalid` | Некорректный config.toml | Остановить bootstrap; показать диагностику; не перезаписывать файл |
| `project_id_mismatch` | ID не совпадает с метаданными store | Остановить интеграцию; не переинициализировать store |
