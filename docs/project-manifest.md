# МАНИФЕСТ-ПРОЕКТА.md

## Статус

Манифест находится на начальной стадии разработки. Описанные ниже решения фиксируют
текущее состояние проекта. Замороженные решения нельзя изменять, сокращать или
переопределять без отдельного решения владельца проекта.

## Замороженные решения

### 1. Обязательные файлы контекста

Проект включает строго ограниченный список обязательных файлов контекста. При инициации
проекта определяется полный состав этих файлов. Принадлежность файла к обязательному
контексту определяется явным списком, хранимым плагином защиты контекста.

### 2. Инициализация обязательного контекста

Обязательные файлы контекста создаются при инициации проекта по утверждённой структуре.
Для каждого файла заранее определяются назначение, состав, допустимое и недопустимое
содержимое. Перед созданием модель проводит структурированный опрос пользователя, а
ответы преобразуются в соответствующие записи по утверждённым правилам.

Уже определённые файлы:

**`AGENTS.md`** — основные правила работы агента: проект, назначение, контекст, доступ
к файлам, границы задачи и изменений, тест до кода и ссылки на специализированные правила.
Не дублирует специализированные правила.

**`LLM.txt`** — минимальная навигационная карта: проект, каталоги, сборка и ссылки на
правила, необходимые на соответствующих этапах. Не содержит рабочих правил и не
дублирует другие обязательные файлы контекста.

**`VERSIONING.md`** — формат версии, источник истины, правила изменения версии,
pre-release, потребители версии и платформенные метаданные. Не определяет релизы,
коммиты или тестирование.

**`releases.md`** — процесс выпуска: ветки, build, verification, merge, tag и ограничения
релиза. Не определяет версионирование, коммиты или тестирование.

**`LOG_RULES.md`** — правила логирования: формат записи, диагностическая ценность,
уровни, контекст, обработка ошибок, безопасность, производительность и согласованность.
Не определяет другие правила проекта.

**`CODE_RULES.md`** — правила разработки кода: простота, явность, ответственность и
локальность, читаемость, слабая связанность, существующие паттерны, дисциплина изменений,
обработка ошибок, верификация и сопровождаемость. Ссылается на специализированные
правила тестирования и логирования, не дублируя их.

**`TEST_RULES.md`** — правила тестирования: TDD, изоляция, покрытие критических путей,
coverage, regression tests, проверка поведения, структура и именование тестов, а также
требования перед commit. Не определяет общие правила разработки или commit-процесс.

**`commit-rules.md`** — формат и правила commit: тип, scope, subject, body, footer,
breaking changes, проверки перед commit и ограничения Git. Не определяет версионирование,
релизы или тестирование.

**`VERSION`** — единственный источник текущей версии; содержит одну версию на строку
без комментариев.

**`.llmignore`** — перечень путей, которые модель не должна читать или использовать
без явного разрешения. Определяет границы доступа к проектным файлам, но не содержит
рабочих правил разработки.

Ответственность файлов не должна дублироваться: специализированное правило определяется
в соответствующем файле, а другие файлы только ссылаются на него при необходимости.

### 3. Защита обязательного контекста

Обязательные файлы контекста защищены от несанкционированных изменений. Плагин защиты
содержит их список и правила изменения и не позволяет модели или другим инструментам
изменять их иначе, чем предусмотрено протоколом.

### 4. Дополнительные файлы и формат содержимого

Новые файлы проекта создаются только при необходимости. Дополнительные файлы контекста
и другие рабочие файлы должны содержать только минимально необходимую информацию без
лишних слов, символов и дублирования; для отдельных типов файлов могут быть определены
дополнительные ограничения.

Механизм изменения дополнительных файлов контекста пока не определён и является
открытым вопросом проекта.

### 5. OpenSpec

OpenSpec является дополнительным слоем проекта. OpenSpec работает в собственной области
проекта (`openspec/`) и не должен изменять обязательные файлы контекста; его файлы и
допустимые области изменений определяются отдельно от контекста проекта.

### 6. Поэтапное чтение контекста

Требуется выяснить, позволяет ли DeepS Harnes технически предоставлять модели обязательные
и дополнительные файлы контекста по мере необходимости, а не передавать весь доступный
контекст при запуске.

Желаемая модель работы: при старте модель получает только необходимую начальную информацию;
по мере перехода к этапу она читает связанные с этим этапом обязательные или дополнительные
файлы контекста. Ссылка на файл означает возможность перейти к нему при необходимости,
а не требование немедленного чтения.

Этот пункт пока является **открытым техническим вопросом**, а не утверждённым требованием
к реализации. Необходимо исследовать фактический механизм формирования context в
DeepS Harnes и определить, в какой точке Protected Governance Files Plugin может
контролировать предоставление файлов модели.

## Текущее состояние

Определены и согласованы состав и ответственность `AGENTS.md`, `LLM.txt`,
`VERSIONING.md`, `releases.md`, `LOG_RULES.md`, `CODE_RULES.md`, `TEST_RULES.md`,
`commit-rules.md`, `VERSION` и `.llmignore`. Их утверждённое содержимое не пересматривается
без отдельного решения владельца.

Дополнительные файлы контекста пока отдельно не определены.

Механизм изменения дополнительных файлов контекста не определён.

Следующий этап — определить состав и правила следующего обязательного файла контекста,
не изменяя замороженные решения.
