# Аудит интеграции Todoing и Manifest

**Источники:** brief v0.2.0; audit; decisions v0.1.0; факт: todoing-x.
Выводы по коду — «факт».

## 1. Итоговая оценка
Совместимы с Brief, закрывают C-1 первого аудита. Не готово к проектированию:
(1) статусы несовместимы — Brief: 6, факт: 4, отображения нет; (2) нарушено
«не зашивать правила Manifest» (before-done проверяет openspec/git); (3)
контракт не специфицирован. База: Markdown-задачи + перестраиваемый индекс +
атомарная запись.

## 2. Карта ответственности
Todoing: хранение, механизм статусов, CLI+JSON, конкурентность, экспорт,
механизм ограничений. Manifest: модель статусов, политика, роли, барьеры,
семантика связей, резервирование. После T-1 дублирования нет: Manifest —
политика, Todoing — механизм и данные.

**T-1** (существ., высокая; decisions §2.5,3.3; факт). Правила Manifest
зашиты в `before-done`: без Manifest завершение невозможно, смена правил —
правка кода. Решение: перенести в конфигурируемые hooks. Требуется решение.
**T-2** (существ., высокая; decisions §3.4; факт). `delete --force`
противоречит запрету удаления: история уничтожается мимо барьеров. Варианты:
(а) убрать команду — против автономности; (б) политика + confirm.
Предпочтителен (б). Требуется решение.

## 3. Модель взаимодействия
**T-3** (существ., высокая; Brief §7,11). Контракт без полей: версия/статус,
связи `openspec_change`, `branch` (commit есть), утверждённая версия,
счётчик ревизий. Пример: pre-commit сверяет ветку с задачей — поля нет.
Решение: минимальный состав контракта — архитектурное требование.
**T-4** (уточнение, средняя). В JSON нет версии контракта (только версия
приложения). Решение: поле версии контракта + сверка в Preflight.
**T-5** (уточнение, высокая; audit E-1). Смены статуса — только через CLI;
hooks Todoing вызывают контрольные скрипты Manifest. Единственный технически
перехватываемый вариант; мимо CLI — процедурный контроль.
**T-6** (рекомендация). Файл политики для hooks; формат связать с
«Конфигурация проекта» (§13).

## 4. Согласованность Todoing ↔ OpenSpec ↔ Git
**T-7** (существ., высокая). Отображение не определено; кандидат:
Backlog/К выполнению→todo; Выполняется→in_progress; Завершено→done;
«На проверке»/«Проверено» не выражаются — потеря двух барьеров. Варианты:
(а) расширить статусы (нарушает Python-совместимость); (б) подстатус в поле.
Предпочтителен (а). Требуется решение.
**T-8** (существ., высокая; Brief §8; факт). Связь с OpenSpec change не
поддержана. Решение: поля связей в контракте (T-3), заполняет оркестратор.
**T-9** (уточнение, высокая). Источник истины: задачи/статусы/история —
Todoing; требования — OpenSpec; код — Git. Инвариант: индекс — кеш, истина —
Markdown; восстановление = `reindex`. Зафиксировать.
**T-10** (существ., средняя; decisions §3.8). Резервирование назначено
«инфраструктуре Manifest», которой в Brief нет. Варианты: (а) минимальный
скрипт; (б) отложить реализацию, зафиксировав требования; `.todoing/` в Git
даёт базу. Предпочтителен (б). Требуется решение.
**T-11** (уточнение, средняя). Копии `.todoing/`, openspec, Git
рассинхронизированы. Правило: точка согласования — коммит, триггеры
резервирования привязать к коммитам.

## 5. Изоляция проектов
**T-12** (рекомендация, высокая). Видение «отдельное хранилище на проект»
реализовано лучше, чем задумано: `.todoing/` внутри проекта и в его Git —
изоляция и версионирование бесплатно. Утвердить. Требуется подтверждение.
**T-13** (уточнение, средняя). Единый обзор: read-only CLI-опрос `--json ls`
по реестру проектов. Центральная реплика не рекомендуется (нарушает
источник истины).
**T-14** (существ., высокая). Межпроектная защита конвенциональная: агент
может писать в чужой проект. Усиление: запись только в cwd («факт») +
`.llmignore`. Полной технической защиты нет — модель доверия (audit E-2).

## 6. История, версии, конкурентный доступ
**T-15** (существ., высокая; decisions §3.4,3.6; факт). История и версии
«согласовано», но не реализованы; критично для `revision_count` и истории
замечаний (Brief §7). Решение: append-история (автор, время, поле,
старое/новое) и версии — в MVP Todoing. Требуется решение.
**T-16** (существ., средняя; decisions §3.7; факт). Общий `index.json`,
блокировок нет: две одновременные записи — вторая затирает первую
(lost update). Минимум MVP: optimistic concurrency (версия записи в команде).
Требуется решение.
**T-17** (уточнение, средняя). Пара «задача+индекс» не атомарна; закрывается
инвариантом T-9. Hooks выполняются до записи «факт» — зафиксировать.

## 7. Резервирование и переносимость
**T-18** (рекомендация): экспорт — полный дамп состояния (задачи+история+
версии+связи) с проверкой целостности. Удалённое хранилище — отложить:
хранилище уже «каталог», переносим.

## 8. Сводка
Критических нет. Приоритеты указаны при каждом замечании (§2–7): 9
существенных, 5 уточнений, 3 рекомендации.

## 9. Вопросы к пользователю

2. T-2: delete --force — политика+confirm (предпочтительно) или удаление?
3. T-7: расширить статусы (предпочтительно) или подстатус в поле?
4. T-10: отложить реализацию резервирования?
5. T-12: утвердить хранилище в проекте (`.todoing/` в Git)?
6. T-16: optimistic concurrency как минимум MVP?
7. T-15: история и версии — в MVP Todoing?

## 10. MVP
Обязательно: контракт с полями T-3 и версией контракта; отображение статусов
и политика переходов; история + минимальные версии; минимум конкурентности;
поля связей; hooks как точка политики. Позже: единый обзор (T-13); стратегия
резервирования; развитый экспорт/импорт; полные блокировки. Отложить:
удалённое хранилище; оптимизация производительности; сравнение версий.

## 11. Предлагаемые изменения Brief (не вносить)
1. §7: карта статусов Todoing, работа через CLI (T-7, T-5).
2. §11: какие точки контроля — hooks Todoing, какие — постфактум-сверки.
3. §12: «минимальный контракт Todoing» как предусловие MVP.
4. §13: «отображение статусов», «минимум конкурентности», «политика
   удаления», «версия контракта», резервирование (T-10).
5. Preflight: проверка наличия и совместимости Todoing.

## 12. Итоговое заключение
Todoing — точка деградации, не отказа: барьеры статусов останавливаются,
данные восстановимы, Git-контроль работает. Дублирования нет (после T-1);
циклов нет: Manifest→политика→hooks→OpenSpec/Git однонаправленно.
Заменяемость — через контракт (T-4) без зашитых правил; нужны контрактные
тесты (два порта существуют). Восстановление — T-9; изоляция — read-only
обзор (T-13); сложность MVP приемлема при составе §10.

До техпроектирования: решить 7 вопросов §9, согласовать правки §11.
