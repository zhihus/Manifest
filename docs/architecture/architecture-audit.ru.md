## 1. Итоговая оценка
Принципы согласованы, §14 не противоречив. Два дефекта: (1) из 8 точек
контроля (§11) hooks перехватывают только коммиты и слияние; (2) Todoing —
несущая конструкция MVP — не имеет интерфейса и не существует как
инструмент («факт»: нет в llms.txt). Остальное уточнимо без смены
архитектуры.

## 2. Критические
**C-1** (высокая; §2,7,8,11,12). Todoing не определён: нет формата
хранения, ID, смены статусов, API для скриптов; согласованность
«Todoing ↔ OpenSpec ↔ Git» предполагает чтение его скриптами — нечего
читать. Сценарий: pre-commit должен проверить статус задачи — нечем.
Следствие: MVP п. 8–9 нереализуемы. Решение: минимальный контракт Todoing
до проектирования.

## 3. Существенные
**E-1** (высокая; §11,13). «Барьеры» наполовину процедурные: статусы
Todoing/OpenSpec, передача на проверку, приёмка — вне Git. Сценарий:
агент переводит задачу в «Проверено» без проверки — увидит только
итоговая приёмка, что §11 запрещает. Решение: разделить контроль на
технический и процедурный (постфактум-сверки).

**E-2** (высокая; §11,14). Модель доверия не задана: hooks, скрипты,
guard — файлы проекта с правами записи агента; возможны правка скриптов
и `--no-verify` («факт»: есть change add-no-verify-permission-flow).
Решение: явная модель доверия — контроль против ошибок, не обхода.

**E-3** (высокая; §11). Hooks не перехватывают checkout/branch — точка
«создание и переключение веток» нереализуема штатно. Решение:
переформулировать как «коммит в ветке задачи» (pre-commit).

**E-4** (высокая; §4; факт). Имена набора не совпадают с репозиторием:
Brief требует `COMMIT_RULES.md`, `RELEASES.md`, фактически
`commit-rules.md`, `releases.md`. Сценарий: конфликт имён на проекте
с существующими файлами. Решение: зафиксировать имена или маппинг в MVP.

**E-5** (средняя; §9; факт). В Brief нет роли Tester, workflow-README её
имеет; TEST FIRST (§10) без носителя: кто пишет тесты до кода? Решение:
включить Tester (и Analyst/Planner) в §9, определить совмещения.

**E-6** (средняя; §6,7). §6 допускает параллельные ветки, §7 требует
порядок по нумерации. Параллелизм задач не определён: разрешён ли, кто
разрешает, условие отсутствия пересечений.

**E-7** (высокая; §5,13). Конфликт с hook-менеджерами (husky): установка
перезатирается, контроль исчезает тихо. Решение: делегирование chain-call
или периодическая сверка; зафиксировать до manifest-init.

**E-8** (средняя; §4,5). Повторный запуск manifest-init не определён:
«не перезаписывать» не различает файлы Manifest и пользователя. Сценарий:
обновлённый validate.sh не установится. Решение: классы владения файлами.

**E-9** (средняя; §1,9; факт). Независимость ролей требует возможностей
harness (изолированные сессии); минимальный набор не назван. Без подагентов
§14 п. 5 невыполним молча. Решение: раздел «требования к harness» +
поведение при деградации.

## 4. Уточнения
**U-1** (§7,8): «глобальная задача» не определена — критерий одна/несколько.
**U-2** (§7,8,11): нет отображения статусов Todoing ↔ OpenSpec ↔ Git,
владельца переходов, источника истины.
**U-3** (§7): кто вносит замечания, где история, инкремент
`revision_count`, предел ревизий/эскалация.
**U-4** (§7,9): эскалация при разногласии Оркестратор/Reviewer.
**U-5** (§2,12): compress-context — компонент §2, но нет в MVP и цикле:
внутри MVP или нет?
**U-6** (§4): архив — алгоритм восстановления не предусмотрен; конфликт
с «не перезаписывать». Достаточно: в MVP восстановление вручную/по задаче.
**U-7** (§6): кто разрешает конфликты слияния, ревью после, merge/rebase.
**U-8** (§6,7,11): состояние в трёх местах; восстановление после сбоя
не описано — нужен источник истины и сверка при старте.
**U-9** (§7): создание задач пользователем vs нумерация и дубли —
создание через агента?
**U-10** (§13): версионирование шаблонов — обязательные метаданные MVP,
иначе отложенные обновления невозможны.

## 5. Рекомендации
**R-1**: раздел «Модель доверия» — технические vs процедурные гарантии.
**R-2**: глоссарий статусов с английскими идентификаторами для скриптов.
**R-3**: контракт Todoing — предусловийный пункт MVP.
**R-4**: отчёт о неактивных гарантиях при частичной установке.

## 6. Реализуемость MVP
Реализуемо: Core/шаблоны, manifest-init (анализ, интервью, Preflight,
установка), архив, context-files-guard («факт»: скрипты и parser уже в
scripts/). Требует уточнения: контракт Todoing (C-1), синхронизация (U-2),
стратегия hooks (E-7), имена файлов (E-4). Риски: контроль статусов
(C-1, E-1); обход hooks; зависимость от harness (E-9).

## 7. Сквозные сценарии
- **Полный цикл** — трасса прослеживается; разрывы: статусы (U-2), Tester (E-5).
- **Сбой агента** — Git самосогласован, Todoing/OpenSpec нет; сверка
  при старте (U-8).
- **Прерывание между компонентами** — то же; закрывается постфактум-сверкой.
- **Конфликт изменений** — файлов при установке: корректно (§4); слияния:
  исполнитель не определён (U-7).
- **Ошибка hook/скрипта** — тихое снятие гарантий (E-1); закрывается R-4.
- **Повторный запуск** — manifest-init не определён (E-8); задача — U-8.
- **Ручное вмешательство** — легитимизировать в модели доверия (E-2).
