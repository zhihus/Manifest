# Description
Уточняет ранее неполно зафиксированные правила статусов и полномочий при работе с Todoing.

## 1. Причина уточнения

В контракте Todoing для Manifest и связанных архитектурных материалах жизненный цикл задач был описан неполно. Часть договорённостей не была явно зафиксирована, а некоторые положения были истолкованы неверно.

В частности, не были однозначно определены отображаемые названия всех состояний, полномочия на переходы и технический запрет самостоятельного допуска задачи к выполнению агентом.

Этот документ фиксирует уточнения, сообщённые пользователем 24.11.2026. При дальнейшей доработке контракта и реализации Manifest эти правила имеют приоритет над прежними неоднозначными формулировками о жизненном цикле задач.

## 2. Состояния задачи

Для пользователя жизненный цикл задачи состоит из следующих состояний:

| Внутренний идентификатор | Название | Значение |
|---|---|---|
| `backlog` | Черновик | Задача обсуждается с пользователем и подготавливается. Выполнение ещё не разрешено. |
| `ready` | К выполнению | Пользователь разрешил приступить к задаче. |
| `in_progress` | Выполняется | Оркестратор передал задачу агенту, и работа началась. |
| `review` | На проверке | Исполнитель закончил работу и передал результат на независимую проверку. |
| `verified` | Проверено | Другой агент проверил результат и подтвердил его соответствие требованиям. |
| `completed` | Завершена | Оркестратор провёл итоговую проверку и подтвердил успешное выполнение. |
| — | Отменена | Пользователь решил, что задачу выполнять не нужно; оркестратор зафиксировал отмену. |

«Черновик» — пользовательское название состояния Todoing `backlog`. Это не отдельное состояние.

«Отменена» — конечное состояние, отображаемое пользователю. На уровне Todoing отмена фиксируется как `outcome=cancelled`; исходный workflow status при этом не переписывается. Поэтому в истории сохраняются последнее рабочее состояние задачи и отдельный факт отмены.

## 3. Порядок переходов

Основной путь выполнения:

1. `backlog` → `ready`: пользователь разрешает выполнение.
2. `ready` → `in_progress`: оркестратор назначает исполнителя и запускает работу.
3. `in_progress` → `review`: исполнитель завершает свой этап и передаёт результат на проверку.
4. `review` → `verified`: независимый проверяющий подтверждает результат.
5. `verified` → `completed`: оркестратор проводит итоговую проверку и завершает задачу.

Если проверяющий находит замечания, задача возвращается из `review` в `in_progress`. Оркестратор организует исправление; исполнитель не проверяет собственную работу.

Отмена может быть инициирована пользователем до завершения задачи. Оркестратор фиксирует `outcome=cancelled` и выполняет предусмотренные действия по отмене связанного OpenSpec change.

## 4. Полномочия на изменение состояний

### 4.1. Разрешение на выполнение

Только пользователь вправе перевести задачу из «Черновика» (`backlog`) в «К выполнению» (`ready`).

Ни один агент, включая Analyst и Оркестратора, не вправе самостоятельно выполнять этот переход или считать задачу разрешённой к выполнению без явного решения пользователя.

Именно этот переход является пользовательским разрешением на начало работы. В момент перехода оркестратор фиксирует утверждённую пользователем текущую версию задачи как baseline через Todoing `task.version.approve`.

### 4.2. Начало и передача работы

Переход из `ready` в `in_progress` выполняет оркестратор при назначении исполнителя и фактическом запуске работы. Агент не должен самостоятельно менять статус, чтобы объявить задачу начатой.

Переход из `in_progress` в `review` выполняется при передаче результата исполнителем. Оркестратор проверяет, что работа действительно передана на проверку, и фиксирует переход.

Переход из `review` в `verified` выполняется только после результата независимого проверяющего. Исполнитель не может подтвердить собственную работу.

Переход из `verified` в `completed` выполняет только оркестратор после итоговых проверок и подтверждения успешного выполнения.

### 4.3. Техническое ограничение полномочий

Запрет на самостоятельный перевод задачи в `ready` должен обеспечиваться технически, а не только инструкциями в запросах к агентам.

Единственным компонентом, который выполняет изменяющие вызовы Todoing от имени Manifest, должен быть оркестратор. Ролевые агенты не получают прямого доступа к Todoing CLI/API и не получают средства аутентификации или полномочия, позволяющие менять статусы напрямую.

Оркестратор предоставляет агентам только ограниченные действия, необходимые для их роли: передать результат на проверку или представить результат проверки. Перед каждым изменением оркестратор проверяет допустимость перехода и источник события.

Если используемая среда не позволяет технически закрыть агентам прямой доступ к Todoing, такую интеграцию нельзя считать обеспечивающей данное требование. Одних инструкций агентам недостаточно.

## 5. Отмена по решению пользователя

Агент может только рекомендовать отмену и привести обоснование. Он не может отменить задачу самостоятельно.

Решение об отмене всегда принадлежит пользователю. Пользователь сообщает оркестратору о принятом решении; оркестратор выполняет отмену через Todoing и штатно архивирует связанный OpenSpec change.

В истории Todoing должно быть однозначно видно, что:

- инициатор и источник решения об отмене — пользователь;
- оркестратор выполнил отмену по этому решению;
- агент, если он предлагал отмену, был только автором рекомендации, а не лицом, принявшим решение.

Технический `actor_id` вызова оркестратора сам по себе не доказывает, кто принял решение. Manifest должен отдельно сохранять подтверждённого инициатора отмены и связь с пользовательским подтверждением.

## 6. Условия завершения

Статус «Проверено» ещё не означает, что задача завершена.

Оркестратор переводит задачу в «Завершена» только после итоговой проверки: результат соответствует требованиям, обязательные проверки пройдены, а связанные действия OpenSpec и Git выполнены в установленном порядке.

Только после этого Todoing получает outcome `completed`. Наличие коммита или положительного заключения одного агента само по себе не является достаточным основанием для завершения.

## 7. Что уточняется относительно прежних документов

1. Ранее предложенная конфигурация из шести состояний не отражала полностью согласованный пользователем жизненный цикл и не закрепляла все русские названия.
2. Право пользователя разрешать выполнение переходом `backlog` → `ready` было упомянуто, но техническая исключительность этого права не была описана достаточно строго.
3. Не было явно определено, что начало работы, передача на проверку, подтверждение проверки и завершение выполняются разными участниками с разными полномочиями.
4. Отмена ранее описывалась только как outcome `cancelled`. Уточнение закрепляет также пользовательское конечное состояние «Отменена» и обязательную фиксацию того, что решение принял пользователь. При этом техническое представление Todoing остаётся отдельным outcome и не переписывает последний workflow status.
5. Утверждение baseline привязывается непосредственно к пользовательскому переходу из «Черновика» в «К выполнению».

## 8. Дальнейшее применение

Этот документ является отдельным архитектурным уточнением и не переписывает задним числом историю прежних решений.

При следующем обновлении `todoing-contract.ru.md`, конфигурации статусов и runbook Manifest необходимо привести их в соответствие с этим документом. До этого реализация не должна трактовать отсутствие явного технического ограничения как разрешение агентам менять статус `ready`.
