# Todoing — архитектурные решения

**Версия:** 0.2.0
**Статус:** рабочая редакция, синхронизирована с целевыми документами Todoing (21.11.2026)
**Назначение:** зафиксировать согласованные архитектурные решения по Todoing
перед техническим проектированием интеграции Todoing и Manifest.

Документ фиксирует только то, что было согласовано в обсуждении с пользователем.
Непринятые решения не восстанавливаются догадками.

**Целевые документы Todoing** (открытый PR #1 репозитория todoing-x,
ветка `docs/product-and-architecture-baseline`, не слитая реализация):
- PRODUCT.md — продуктовое видение и границы;
- docs/architecture/decisions.md — реестр решений Todoing.

Эти документы уточняют и развивают решения ниже; расхождений по существу
не выявлено. Принятие решений не означает их реализацию: история, версии,
зависимости, блокировки, архивирование, версионируемый API и Project ID
в текущем прототипе todoing-x не реализованы.

## 1. Назначение и границы Todoing

Todoing — самостоятельный инструмент управления задачами и Kanban.

Границы:

- Todoing не является внутренней частью Manifest.
- Todoing сохраняет автономный функционал и остаётся полезным без Manifest.
- Для удобной интеграции с Manifest допускаются специальные возможности,
  но они не делают Todoing зависимым от Manifest.
- Документ фиксирует архитектурные решения; он не является техническим
  проектированием и не определяет конкретную реализацию.

## 2. Принципы взаимодействия Todoing и Manifest

1. Взаимодействие осуществляется только через CLI и формализованный
   машинный JSON-интерфейс.
2. Manifest не читает и не изменяет внутреннее хранилище Todoing напрямую.
3. Todoing предоставляет механизмы выполнения операций; Manifest определяет
   ограничения, полномочия и правила использования этих механизмов.
4. Интерфейс должен быть предсказуемым: коды завершения, структурированные
   ошибки, версионирование интерфейса.
5. Todoing не содержит жёстко зашитых правил Manifest: правила определяются
   конфигурацией и политикой Manifest, а не кодом Todoing.

## 3. Согласованные архитектурные решения

Статусы:

- **Согласовано** — пользователь явно подтвердил решение.
- **Предварительное видение** — пользователь обозначил направление, решение
  не утверждено.
- **Отложено** — вопрос намеренно оставлен для последующего исследования.

### 3.1. Самостоятельность

**Согласовано.**

- Todoing — самостоятельный инструмент со своим автономным функционалом.
- Todoing не является внутренней частью Manifest.
- Допускаются специальные возможности для удобной интеграции с Manifest.
- Todoing должен оставаться полезным без Manifest.

### 3.2. Взаимодействие с Manifest

**Согласовано.**

- Взаимодействие — только через CLI и формализованный машинный JSON-интерфейс.
- Manifest не читает и не изменяет внутреннее хранилище Todoing напрямую.
- Todoing предоставляет механизмы выполнения операций.
- Manifest определяет ограничения, полномочия и правила использования
  этих механизмов.
- Необходимы предсказуемые коды завершения, структурированные ошибки и
  версионирование интерфейса.

### 3.3. Полномочия и ограничения

**Согласовано.**

- Todoing предоставляет универсальные механизмы разграничения прав.
- Поддерживаются ограничения на смену статусов и редактирование отдельных
  полей.
- Manifest определяет, какие роли и при каких условиях могут выполнять
  соответствующие операции.
- Todoing не содержит жёстко зашитых правил Manifest.
- Блокировка эксклюзивная на всё время работы агента, включая запрет чтения
  задачи другими клиентами; предусматриваются heartbeat, освобождение и
  восстановление после аварийного завершения.
- Статусы настраиваются пользователем; Manifest предоставляет рекомендуемую
  конфигурацию, не навязывая её; завершение и отмена моделируются отдельно
  от статусов.
- Архивирование — отдельная операция с восстановлением; архивные задачи
  остаются доступны для чтения.
- Hooks/events — универсальные и необязательные; отсутствие обработчика
  не ломает операцию.
- Project ID обязателен на границе интеграции с Manifest; механизм
  привязки — предмет интеграционного проектирования.
- Backup — ответственность потребителя (Manifest); Git не является
  резервной копией.

### 3.4. История изменений

**Согласовано.**

- Todoing ведёт полную историю изменений задач.
- История включает: автора операции, время, изменённое поле, предыдущее и
  новое значение, результат операции.
- История неизменяема штатными средствами Todoing.
- Исправление ошибки оформляется новой операцией, а не правкой истории.
- Физическое удаление задач не предусматривается: неактуальные задачи
  сохраняются с соответствующим статусом.

### 3.5. Жизненный цикл и утверждение задач

**Согласовано.**

- Детальная проработка задачи выполняется в Backlog: определяются
  требования, критерии приёмки, зависимости и другие необходимые детали.
- После утверждения пользователем задача переводится в «К выполнению».
- После утверждения исполнение и дальнейшая обработка задачи автоматизируются
  в соответствии с ролями и полномочиями Manifest.
- Не требуется повторное ручное согласование пользователем каждого
  последующего действия агентов.

### 3.6. Версионирование

**Согласовано** (требования); **Отложено** (способ реализации).

- Todoing поддерживает версии задач.
- Версии можно сравнивать.
- Утверждённая версия задачи сохраняется и доступна для сравнения
  с последующими изменениями.
- Способ реализации версионирования не выбран (см. раздел 4, вопрос 2).

### 3.7. Параллельная работа

**Согласовано.**

- Несколько агентов могут одновременно работать с Todoing.
- Необходима защита от конфликтующих изменений одной задачи.
- Предусматриваются обнаружение устаревших версий, атомарность операций
  и сохранение истории без потери событий.
- Конкретный механизм конкурентного доступа отложен (см. раздел 4, вопрос 4).

### 3.8. Резервное копирование

**Согласовано** (требования); **Отложено** (стратегия).

- Резервирование — общая обязанность инфраструктуры Manifest.
- Резервирование распространяется на Todoing, хранилище задач, историю
  и связанные данные.
- Git не считается полноценной заменой резервному копированию.
- Минимальное требование — хранение резервных копий на отдельном диске.
- Архитектура допускает подключение удалённого хранилища.
- Предусмотрены регулярное резервирование и дополнительные события-триггеры
  (например, завершение работ или сессии).
- Необходима проверка возможности восстановления данных.
- Оптимальная стратегия, периодичность, триггеры и ротация копий отложены
  (см. раздел 4, вопрос 5).

### 3.9. Экспорт и импорт

**Согласовано.**

- Todoing поддерживает экспорт и импорт задач.
- Перенос сохраняет задачи, версии, историю, зависимости, связи и метаданные.
- При импорте выполняется проверка целостности данных.
- Перенос не зависит от конкретного компьютера или типа хранилища.
- Формат экспорта и импорта отложен (см. раздел 4, вопрос 8).

### 3.10. Изоляция проектов

**Согласовано** (требования); **Предварительное видение** (разделение
хранилищ); **Отложено** (архитектура единого обзора).

- Необходима изоляция задач разных проектов.
- **Предварительное видение:** отдельное хранилище и список задач
  для каждого проекта. Решение не утверждено.
- Необходим единый обзорный список задач из разных проектов.
  Архитектура единого обзора не определена (см. раздел 4, вопрос 7).
- Недопустимо, чтобы агент одного проекта случайно изменял задачи
  другого проекта.

## 4. Вопросы, отложенные до технического проектирования

Следующие вопросы намеренно не решаются на данном этапе. Они являются
предметом отдельного технического исследования с сопоставлением
альтернатив и лучших практик.

1. Формат и технология хранения данных.
2. Конкретная реализация версионирования.
3. Архитектура неизменяемого журнала истории и оперативного состояния.
4. Механизм конкурентного доступа, блокировок и разрешения конфликтов.
5. Оптимальная стратегия резервирования, периодичность, триггеры
   и ротация копий.
6. Механизм восстановления после сбоев.
7. Архитектура единого обзора задач нескольких проектов.
8. Формат экспорта и импорта.
9. Производительность при большом количестве задач и частых изменениях.
10. Конкретная структура CLI и JSON-контракта.

## 5. Сводка принятых решений

- **Согласовано:** 10 областей решений (разделы 3.1–3.10).
- **Предварительное видение:** 1 (отдельное хранилище и список задач
  для каждого проекта, раздел 3.10).
- **Отложено:** 10 вопросов (раздел 4).

Ключевые инварианты:

1. Todoing самостоятелен и полезен без Manifest.
2. Взаимодействие — только через CLI и JSON-интерфейс; прямое чтение
   хранилища запрещено.
3. Полномочия определяются Manifest, а не зашиты в Todoing.
4. История полная, неизменяема штатными средствами; удаление задач
   не предусмотрено.
5. Утверждение задачи пользователем — единственная ручная точка
   согласования; далее процесс автоматизирован.
