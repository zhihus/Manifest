# Описание
Историческая фиксация архитектурных решений, принятых пользователем
в обсуждении 22.11.2026. Документ не заменяет
`architecture-decisions.ru.md` и `architecture-brief.ru.md`: реестр
решений остаётся основным источником. Существующие архитектурные
документы этим документом не изменяются. Синхронизацию реестра и
brief с этими решениями выполняет отдельная задача после явного
разрешения пользователя. Документ содержит только подтверждённые
решения; неподтверждённые вопросы в него не включены.

## 1. Git и рабочие ветки

- Основная рабочая ветка — `develop`.
- Каждая задача выполняется в отдельной ветке.
- Одновременно выполняется одна глобальная задача.
- Оркестратор управляет очередностью работы агентов.
- Для одной задачи действует эксклюзивная блокировка.
- Другой агент не может работать с занятой задачей.
- При сбое блокировка автоматически истекает.
- При завершении работы блокировка снимается.

## 2. Конфликты Git

- Конфликт разрешает назначенный оркестратором Исполнитель.
- После разрешения обязательны автоматические тесты и проверки.
- Дополнительно проводится независимое ревью агентом с чистым
  контекстом.
- Исполнитель не подтверждает правильность собственного решения.
- Оркестратор контролирует результат и выполняет слияние.

## 3. Hooks

- Используются существующие механизмы Git и AI-harness.
- Собственный менеджер Hooks в Manifest не разрабатывается.
- Hooks запускают контрольные скрипты Manifest.
- Отдельные реализации для каждого AI-harness не входят в MVP без
  необходимости.

## 4. Инициализация проекта

- Рабочий каталог — `.manifest` в корне проекта.
- Настройки хранятся в отдельном файле конфигурации.
- Конфигурация стабильна и не перезаписывается автоматически.
- Повторная инициализация не предусмотрена.
- Обязателен механизм защиты от случайной перезаписи.

## 5. Шаблоны проектов

- Для MVP используется один общий шаблон.
- Специализированные шаблоны для разных типов проектов отложены на
  Roadmap.

## 6. Обновление Manifest

- Должен существовать отдельный утверждаемый процесс обновления
  файлов Manifest в подключённых проектах.
- Обновление не является повторной инициализацией.
- Детали механизма требуют отдельной проработки.

## 7. Todoing и статусы

- Todoing — единственный источник статуса задачи.
- Manifest не дублирует статусы Todoing.
- Manifest управляет последовательностью этапов и назначением
  агентов.
- Отдельное сопоставление статусов не требуется.

## 8. Создание и отмена задач

- Задачи создаёт пользователь либо Analyst предлагает их создание.
- Включение задачи в работу утверждает пользователь.
- Любой агент может рекомендовать отмену задачи с обоснованием.
- Отмену подтверждает только пользователь.
- После подтверждения оркестратор меняет статус задачи в Todoing и
  архивирует связанное изменение OpenSpec штатным механизмом Archive.
- При отмене основные спецификации OpenSpec не обновляются.

## 9. Контроль процесса

- Оркестратор управляет последовательностью работы агентов.
- Технические ограничения обеспечиваются контрольными скриптами и
  Hooks, а не только инструкциями агентам.
- Manifest контролирует согласованность Todoing, OpenSpec и Git.
- При обнаружении несоответствий процесс не должен переходить к
  следующему этапу до устранения проблемы и повторной проверки.

## 10. Разделение MVP и Roadmap

- MVP содержит только необходимый согласованный функционал.
- Остальные идеи и возможности сохраняются в Roadmap.
- Не следует расширять MVP без необходимости.
- Неопределённые технические детали не превращать автоматически в
  новые архитектурные требования.
