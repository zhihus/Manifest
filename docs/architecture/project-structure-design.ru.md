# Description
Предлагаемая минимальная структура репозитория Manifest и проектов, подключённых к нему.

## 1. Цель и границы

Документ предлагает единый порядок размещения файлов для Manifest и подключённых проектов. Цель — сделать структуру простой для человека и предсказуемой для агентов и проверяющих скриптов.

Документ является проектным предложением. Он не переносит файлы и не меняет действующие шаблоны, конфигурацию или правила. Такие изменения выполняются после утверждения структуры.

Manifest остаётся источником общих правил. Каждый подключённый проект хранит собственные требования, архитектурные решения, задачи и код. Todoing и OpenSpec остаются самостоятельными инструментами.

## 2. Принципы

1. **Один файл — одна ответственность.** Не копировать одно правило в несколько документов.
2. **Корень — только для основных файлов.** Не размещать там обычную документацию и рабочие материалы.
3. **Отдельные каталоги для отдельных систем.** Настройки Manifest, данные Todoing и материалы OpenSpec не смешиваются.
4. **Необязательные компоненты не создают пустых каталогов.** Если OpenSpec или Todoing не подключён, соответствующий каталог отсутствует.
5. **Не создавать архив вручную без необходимости.** История изменений хранится в Git; архив OpenSpec — в штатном каталоге OpenSpec.
6. **Не перезаписывать существующие файлы при подключении.** Конфликты показываются пользователю.
7. **Не дублировать спецификации.** OpenSpec хранит требования к изменениям; архитектурные документы — устойчивые решения и устройство проекта.

## 3. Предлагаемая структура подключённого проекта

```text
project/
├── AGENTS.md
├── llms.txt
├── COMMIT_RULES.md
├── VERSION
├── VERSIONING.md
├── RELEASES.md
├── .llmignore
│
├── .manifest/
│   ├── <project-config>
│   ├── project-id
│   ├── validate.sh
│   └── hooks/
│       ├── pre-commit
│       └── commit-msg
│
├── docs/
│   ├── architecture/
│   └── plans/
│
├── openspec/             # только если OpenSpec подключён
│   ├── config.yaml
│   ├── specs/
│   └── changes/
│
└── .todoing/             # только если Todoing подключён;
                         # содержимое принадлежит Todoing
```

Это целевая схема, а не утверждение, что все перечисленные файлы уже входят в текущую поставку Manifest.

### 3.1. Корневые файлы

| Файл | Единственная ответственность |
|---|---|
| `AGENTS.md` | Краткие обязательные правила агента и границы полномочий. |
| `llms.txt` | Навигация по проекту: назначение, каталоги, сборка и ссылки на документы. |
| `COMMIT_RULES.md` | Формат и ограничения коммитов. |
| `VERSION` | Текущая версия проекта. |
| `VERSIONING.md` | Правила изменения версии. |
| `RELEASES.md` | Подготовка и выпуск релизов. |
| `.llmignore` | Ограничения чтения файлов агентами. |

Специализированные правила разработки, тестирования и логирования добавляются только тогда, когда соответствующие шаблоны утверждены и нужны проекту. Они не должны дублировать `AGENTS.md`.

### 3.2. Каталог .manifest

Каталог принадлежит Manifest и содержит только данные и механизмы подключения:

- файл конфигурации проекта;
- постоянный Project ID;
- скрипт проверки;
- установленные Git Hooks.

Внутри него не хранятся архитектурные документы, планы, задачи или спецификации.

Имя и формат файла конфигурации должны соответствовать отдельному утверждённому контракту. Этот документ не выбирает формат вместо ещё не принятого решения.

### 3.3. Каталог docs

- `docs/architecture/` — архитектура проекта, принятые решения, контракты и обоснования.
- `docs/plans/` — долгосрочные планы, которые не являются активными задачами.

Другие каталоги создаются только при появлении устойчивой потребности. Временные заметки и материалы выполнения не должны автоматически становиться постоянной документацией.

### 3.4. Каталог openspec

OpenSpec является необязательным компонентом. Если он используется, его собственная структура не изменяется Manifest:

- `specs/` — действующие требования;
- `changes/` — активные изменения и архив изменений.

Не следует создавать параллельные копии OpenSpec-спецификаций в `docs/`.

### 3.5. Каталог .todoing

Каталог и его содержимое принадлежат Todoing. Manifest взаимодействует с Todoing только через публичный CLI/JSON API и не редактирует внутренние файлы или базу данных напрямую.

Если Todoing не подключён, каталог не создаётся.

## 4. Разделение источников истины

| Данные | Единственный источник истины |
|---|---|
| Общие правила Manifest | Репозиторий Manifest |
| Настройки подключения Manifest | `.manifest/` |
| Требования и сценарии изменений | OpenSpec, если подключён |
| Задачи, статусы и история | Todoing, если подключён |
| Код и история изменений | Git |
| Архитектурные решения проекта | `docs/architecture/` |
| Долгосрочные планы | `docs/plans/` |

Если компонент не подключён, его функции не должны незаметно дублироваться в другом каталоге.

## 5. Структура самого репозитория Manifest

В репозитории Manifest следует сохранить существующие основные каталоги:

- `docs/architecture/` — архитектура самого Manifest и интеграционные контракты;
- `docs/plans/` — планы развития;
- `docs/templates/` — исходные шаблоны для подключения проектов;
- `workflow/` — процессы и правила работы;
- `openspec/` — спецификации разработки самого Manifest;
- `scripts/` — проверочные и служебные скрипты Manifest.

Внутри `docs/architecture/` предлагается постепенно разделить материалы по назначению:

- основные документы и актуальные решения оставить на верхнем уровне;
- проверки и аудиты перенести в `audits/`;
- контракты интеграций — в `contracts/`;
- протоколы и заменённые редакции — в `history/`.

Переносить документы следует только после инвентаризации ссылок. Исторические документы не удалять; при переносе сохранять Git-историю и обновлять все ссылки. Новый документ не должен создавать второй источник истины.

## 6. Несогласованности, которые нужно устранить до изменения шаблонов

В текущих документах Manifest обнаружено расхождение в составе обязательных файлов подключённого проекта:

- `docs/project-manifest.md` содержит замороженный базовый набор из десяти файлов;
- `docs/architecture/architecture-brief.ru.md` описывает более короткий набор для MVP и отдельно указывает, что некоторые шаблоны ещё отсутствуют;
- `AGENTS.md` и `llms.txt` задают собственные правила навигации и состава контекста.

Нельзя молча выбрать один из этих списков. До изменения шаблонов нужно сверить их с последними решениями пользователя и привести документы к одному источнику истины.

Также требуется уточнить, какие из `AGENTS.md`, `llms.txt`, `VERSION`, `VERSIONING.md`, `RELEASES.md` и правил коммитов устанавливаются всегда, а какие зависят от типа проекта или подключённых возможностей.

## 7. Порядок внедрения

1. Утвердить целевую структуру и состав обязательных файлов.
2. Сверить и согласовать противоречащие друг другу архитектурные документы.
3. Обновить спецификацию и правила `manifest-init`.
4. Обновить шаблоны и проверки структуры.
5. Проверить установку на тестовом проекте каждого поддерживаемого типа.
6. После успешной проверки применять структуру к новым проектам.

Существующие подключённые проекты не перемещать и не перестраивать автоматически. Их миграция должна быть отдельной, проверяемой операцией с отчётом и сохранением пользовательских файлов.
