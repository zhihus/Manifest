# Manifest — Architecture Brief

**Версия:** 0.4.2  
**Статус:** рабочая редакция, синхронизирована с решениями обсуждений
20–21.11.2026 и протоколом 22.11.2026
(`architecture-session-2026-11-22.ru.md`)  
**Назначение:** зафиксировать архитектуру Manifest и границы MVP перед техническим проектированием.

## 1. Назначение

Manifest — система управления работой LLM-агентов в Git-проектах.

Основные цели:

- ограничить самостоятельные решения и действия агентов;
- обеспечить выполнение изменений только в рамках согласованных задач;
- стандартизировать работу с OpenSpec;
- разделить исполнение и независимую проверку;
- защитить контекстные файлы;
- автоматизировать контроль процессов;
- обеспечить прослеживаемость от задачи до коммита и релиза.

Manifest не привязан к конкретному AI-harness. Настройка ZCode и других harness остаётся ответственностью пользователя.

## 2. Архитектура и компоненты

Manifest представляет собой экосистему из самостоятельных компонентов.

| Компонент | Назначение |
| --- | --- |
| **Manifest Core** | Архитектура, стандарты, правила, конфигурация и шаблоны |
| **manifest-init** | Анализ, инициализация и подключение Manifest к проектам |
| **Todoing** | Управление задачами и Kanban |
| **OpenSpec** | Спецификации, декомпозиция и выполнение задач |
| **compress-context** | Управление объёмом контекста |
| **context-files-guard** | Защита контекстных файлов |

Git Hooks и контрольные скрипты — механизмы реализации Manifest, а не отдельные самостоятельные компоненты экосистемы.

`manifest-init` и скилл инициализации проекта — один компонент, а не два.

Todoing, OpenSpec, compress-context и context-files-guard сохраняют самостоятельность. Manifest определяет правила их совместной работы.

## 3. Типы проектов

Manifest поддерживает три направления:

- **Code** — проекты с программным кодом.
- **Documentation** — документационные проекты.
- **Mixed** — проекты обоих типов.

Это не три разные архитектуры Manifest, а варианты конфигурации единой системы.

### Определение направления

Для нового проекта модель проводит интервью с пользователем.

Для существующего проекта модель:

1. Изучает структуру, документы и код.
2. Формирует представление о проекте.
3. Определяет предполагаемые направления.
4. Уточняет неоднозначности у пользователя.
5. Предлагает конфигурацию.

Модель не должна угадывать при недостатке информации.

Конфигурацию формирует модель, а её полноту и допустимость проверяют скрипты Manifest.

### Развитие проекта

Модель может обнаружить новое направление и предложить изменить конфигурацию.

После изменения утверждённых пользователем флагов `manifest-init` синхронизирует набор подключённых шаблонов.

Установка уже утверждённого шаблона не требует отдельной задачи Todoing/OpenSpec.

## 4. Шаблоны и контекстные файлы

### Источник шаблонов

Эталонные шаблоны хранятся в специальной папке репозитория Manifest.

Все проекты получают файлы из единого утверждённого набора. Повторное согласование каждого шаблона при установке не требуется.

Для MVP используется **один общий шаблон** проекта
(решено 22.11.2026). Специализированные шаблоны для разных типов
проектов отложены на Roadmap.

### Обязательный базовый набор

Для всех проектов:

- `AGENTS.md` — основные правила работы агента.
- `llms.txt` — описание проекта и дополнительный контекст.
- `COMMIT_RULES.md` — правила коммитов.
- `VERSION` — текущая версия.
- `VERSIONING.md` — правила версионирования.
- `RELEASES.md` — правила подготовки и выпуска релизов.

`VERSIONING.md` и `RELEASES.md` — самостоятельные документы с разными назначениями.

> Примечание (2026-11-22): шаблон `RELEASES.md` пока не существует,
> поэтому `manifest-init` в MVP устанавливает пять файлов базового
> набора (без `RELEASES.md`); файл добавляется в проект вручную после
> появления шаблона.

### Условные шаблоны

Условные наборы правил для кодовых и документационных проектов
(ниже) в MVP не устанавливаются: действует один общий шаблон.
Раздел сохраняется как основа для специализированных шаблонов на
этапе Roadmap.

Для проектов с кодом подключаются правила:

- кодирования;
- разработки;
- тестирования;
- логирования.

Для документационных проектов подключаются правила:

- создания и оформления документации;
- проверки документации.

Смешанные проекты получают оба набора.

TEST FIRST — общий принцип для всех направлений. Методы проверки различаются в зависимости от типа результата.

### Язык

Контекстные файлы и правила Manifest ведутся на английском языке.

Агент общается с пользователем на языке пользователя.

### Работа с существующими файлами

При установке:

- отсутствующие файлы добавляются;
- существующие файлы не перезаписываются;
- конфликты имён фиксируются и сообщаются пользователю;
- автоматическое объединение существующих файлов с шаблонами не выполняется.

Полная миграция уже существующей системы контекстных файлов отложена за пределы MVP.

### Архив

Отключённые шаблоны не удаляются, а перемещаются в архивную папку.

Архив:

- исключается из контекста LLM через `.llmignore`;
- дополнительно защищается механизмами `context-files-guard` и Git Hooks;
- не требует отдельного журнала подключений и отключений.

Автоматическое восстановление архивных файлов допускается только при наличии предусмотренного алгоритма.

## 5. Инициализация: manifest-init

`manifest-init` отвечает за полный цикл подключения Manifest к проекту:

1. Анализ проекта.
2. Интервью и формирование конфигурации.
3. Preflight.
4. Установка утверждённых шаблонов.
5. Установка контрольных скриптов.
6. Установка Git Hooks.
7. Итоговая проверка установки.
8. Выдача понятного отчёта.

### Рабочий каталог и конфигурация

Рабочий каталог Manifest — `.manifest` в корне проекта
(решено 22.11.2026). Настройки хранятся в отдельном файле
конфигурации. Конфигурация стабильна и не перезаписывается
автоматически. Повторная инициализация не предусмотрена. Обязателен
механизм защиты от случайной перезаписи. Формат конфигурационного
файла и схема флагов остаются открытыми вопросами (§13).

### Preflight

До начала изменений проверяются необходимые условия:

- наличие Git;
- структура проекта;
- права доступа;
- возможность записи;
- необходимые инструменты и зависимости;
- условия установки контрольных механизмов.

При провале Preflight установка не начинается.

Manifest должен сообщить причину ошибки и необходимые действия.

Автоматическое исправление выявленных проблем пока не определено.

## 6. Git

Git обязателен для всех проектов Manifest.

Поддерживаются локальные и удалённые репозитории. Работа с удалённым репозиторием выполняется через его рабочую копию.

Основная ветка — `develop`.

Для каждой глобальной задачи создаётся отдельная ветка от `develop`. Исполнители работают в ней.

Последовательное выполнение — обязательное правило Manifest. Агенты запускаются последовательно; параллельный запуск не допускается, включая анализ, реализацию и проверку. В рамках одного проекта одновременно выполняется только одна глобальная задача. При блокировке задачи переход к следующей допускается только при отсутствии зависимости от заблокированной; при наличии зависимости выполнение ожидает разблокировки. Оркестратор запускает следующего агента только после завершения предыдущего.

После успешного ревью и итоговой проверки оркестратор:

1. Сливает ветку задачи в `develop`.
2. Обеспечивает сохранение связей с Todoing и OpenSpec.
3. Закрывает задачу.

Промежуточные коммиты разрешены. Один коммит не обязан соответствовать одной задаче.

### Конфликт слияния

Конфликт разрешает назначенный оркестратором Исполнитель
(решено 22.11.2026). После разрешения обязательны автоматические
тесты и проверки. Дополнительно проводится независимое ревью агентом
с чистым контекстом. Исполнитель не подтверждает правильность
собственного решения. Оркестратор контролирует результат и выполняет
слияние.

В Todoing сохраняются ссылки на OpenSpec change и итоговый commit/merge через универсальные external references и final commit reference; Todoing не интерпретирует OpenSpec.

## 7. Управление задачами: Todoing

Todoing — самостоятельный инструмент управления задачами и Kanban.

Любое изменение проекта выполняется через задачу, за исключением явно предусмотренных автоматических операций Manifest, например установки утверждённого шаблона.

### Создание задач

- Задачу подготавливает Analyst совместно с пользователем на этапе Backlog.
- Analyst анализирует контекст проекта, предыдущие задачи, их зависимости и спецификации; создаёт задачу в Todoing. Это согласовано с правилом «агент создаёт задачи только по разрешению пользователя»: разрешение реализуется через совместную работу в Backlog.
- Пользователь обсуждает предложения Analyst, корректирует их и при необходимости поручает доработку.
- Пользователь утверждает задачу, самостоятельно переводя её в статус «К выполнению». После этого работу над задачей продолжает оркестратор.
- Каждая задача имеет утверждённый формат, шаблон наименования и строгую нумерацию.
- Перед созданием проверяется наличие аналогичной задачи.
- Каждая задача содержит критерии приёмки и проверки.
- Зависимости между задачами определяются при участии Analyst; новая задача становится последней в списке и анализирует уже обновлённый список.

### Подготовка задачи

В Backlog пользователь и агент:

- уточняют содержание;
- устраняют дубли;
- прорабатывают решение;
- формируют критерии приёмки;
- определяют необходимые проверки.

Только после утверждения пользователя задача переводится в «К выполнению».

### Статусы Kanban

Todoing — единственный источник статуса задачи; Manifest не дублирует
статусы Todoing и не ведёт отдельную карту соответствия статусов
(решено 22.11.2026). Внутренние этапы Manifest при этом сохраняются.
Manifest управляет последовательностью этапов и назначением агентов.

| Статус | Назначение |
| --- | --- |
| Backlog | Обсуждение и детализация |
| К выполнению | Задача утверждена |
| Выполняется | Реализация |
| На проверке | Передача независимому Reviewer |
| Проверено | Reviewer подтвердил результат |
| Завершено | Оркестратор выполнил итоговую проверку и закрыл задачу |

При замечаниях Reviewer задача возвращается в статус «Выполняется».

Отдельные статусы повторных исправлений не вводятся. Todoing хранит Review history и `revision_count`: счётчик увеличивается ровно на один для каждого Review с outcome `changes_requested`, независимо от числа комментариев и версий задачи.

Пользователь определяет приоритет и порядок задач. По умолчанию задачи выполняются в порядке нумерации, если пользователь не указал иное.

Пользователь не выполняет техническую приёмку и не закрывает задачи.

### Отмена задачи

Любой агент может рекомендовать отмену задачи с обоснованием
(решено 22.11.2026). Отмену подтверждает только пользователь. После
подтверждения оркестратор фиксирует в Todoing outcome `cancelled`
через `task.cancel` (workflow status при этом не меняется) и архивирует
связанное изменение OpenSpec штатным механизмом Archive.
Основные спецификации OpenSpec при этом не обновляются. Архивирование
OpenSpec change — это механизм OpenSpec Archive, не связанный с
архивом отключённых шаблонов (§4).

### Интеграция с Todoing

Todoing — самостоятельный Rust CLI, не зависящий от Manifest; управляет только задачами. Manifest отвечает за интеграционную политику и согласованность Todoing, OpenSpec и Git.

- Взаимодействие — только через CLI и стабильный версионируемый JSON API; прямое чтение хранилища запрещено.
- Статусы настраиваются пользователем; Manifest предоставляет рекомендуемую конфигурацию, не навязывая её.
- Зависимости, история операций, версии, Review history с `revision_count`, универсальные внешние ссылки и эксклюзивные блокировки задач обязательны.
- История неизменяема и дополняема; каждое успешное сохранение создаёт версию задачи. Новая Review record создаёт версию и history event атомарно; повтор того же `review_id` с тем же содержимым идемпотентен.
- Блокировка эксклюзивная на всё время работы агента, включая запрет чтения другими клиентами; предусматривается автоматическое истечение при аварийном завершении.
- Физическое удаление задач не допускается; идентификаторы не переиспользуются.
- Архивирование — отдельная функция, не статус: архивные задачи доступны для чтения и восстановления.
- Hooks/events — универсальные и необязательные; Todoing не содержит знаний о Manifest или OpenSpec.
- Текущая реализация Todoing использует SQLite. Это внутренняя реализация Todoing; Manifest зависит только от CLI и JSON API и не диктует движок хранения.
- Импорт/экспорт и резервирование — последующие задачи; резервирование обеспечивает Manifest, Git не является резервной копией.
- Project ID обязателен на границе интеграции; Manifest создаёт стабильный UUIDv4 один раз, хранит его в собственной конфигурации и передаёт в каждом API request envelope. Project ID не является credential.

## 8. OpenSpec

OpenSpec обязателен для всех изменений, кроме отдельно предусмотренных автоматических операций Manifest.

Связь между Todoing и OpenSpec:

**Одна глобальная задача Todoing = одна глобальная задача OpenSpec.**

Связь Task ID ↔ OpenSpec change хранится в Todoing как generic external reference; формат namespace и relation не содержит OpenSpec-specific логики.

OpenSpec обеспечивает внутреннюю проработку задачи:

- спецификации;
- требования;
- дизайн, когда он необходим;
- декомпозицию;
- подзадачи;
- проверки;
- фиксацию выполнения в `tasks.md`.

Глубина декомпозиции зависит от сложности задачи. Обязательность OpenSpec не зависит от её размера.

Todoing остаётся внешним источником задачи. OpenSpec не заменяет Todoing.

Состояние задачи Todoing и состояние OpenSpec должны оставаться согласованными.

## 9. Роли агентов

Manifest определяет роли и полномочия независимо от используемого harness.

Обязательные роли:

| Роль | Ответственность |
| --- | --- |
| Оркестратор | Управление процессом, координация и итоговая приёмка; использует модель GLM-5.3 Flash |
| Исполнитель/разработчик | Реализация программного кода |
| Code Reviewer | Независимая проверка кода |
| Автор документации | Создание и изменение документации |
| Documentation Reviewer | Независимая проверка документации |
| Tester | Подготовка тестов до реализации по TEST FIRST |
| Analyst | Подготовка задач совместно с пользователем в Backlog |

Исполнитель не проверяет собственную работу. Оркестратор не подменяет Analyst на этапе подготовки задач и не принимает за пользователя решения об утверждении задач.

Reviewer:

- независим от исполнителя;
- имеет отдельный контекст и инструкции;
- проверяет результат по критериям задачи;
- принимает работу либо возвращает её на исправление.

Оркестратор:

- управляет выполнением;
- контролирует OpenSpec;
- организует независимые проверки;
- выполняет итоговую проверку;
- сливает ветку;
- закрывает задачу.

Отдельный аудит поведения агентов не требуется: контроль обеспечивается задачами, полномочиями, OpenSpec, Reviewer и автоматизированными проверками.

Замечания Reviewer передаются оркестратору; оркестратор повторно запускает исполнителя до полного устранения замечаний. При блокирующей ошибке оркестратор эскалирует проблему пользователю.

Для каждой роли создаётся отдельный агент со своей задачей, контекстом и инструкциями; одна и та же модель может использоваться для разных ролей. Распределение моделей по ролям не закреплено и отложено; настройка агентов и их прав в конкретном AI-harness — ответственность пользователя.

## 10. TEST FIRST и качество

TEST FIRST применяется ко всем типам проектов.

### Программный код

Используются TDD и SDD:

- требования и спецификация формируются до реализации;
- тесты разрабатываются до соответствующего кода;
- результат проходит независимое Code Review.

Тестирование программного кода обязательно. Требование 100% должно быть отражено в правилах тестирования с однозначным определением критерия.

### Документация

Предусматриваются автоматические проверки:

- структуры и обязательных разделов;
- наличия файлов;
- корректности ссылок;
- Markdown и YAML;
- соответствия шаблонам Manifest;
- соответствия документации фактическому состоянию проекта.

Структурные проверки выполняются скриптами. Содержательная проверка выполняется Documentation Reviewer.

## 11. Автоматизированный контроль

Контрольные скрипты Manifest едины для всех подключённых проектов.

Git Hooks и контрольные скрипты устанавливаются автоматически через
`manifest-init`. Используются существующие механизмы Git и
AI-harness; собственный менеджер hooks в Manifest не разрабатывается
(решено 22.11.2026). Hooks запускают контрольные скрипты Manifest.
Отдельные реализации для каждого AI-harness не входят в MVP без
необходимости.

Контроль осуществляется на всех этапах, а не только перед завершением задачи.

Обязательные точки контроля:

- создание и переключение веток;
- коммиты;
- изменение статусов Todoing;
- изменение состояния OpenSpec;
- передача на проверку;
- результаты Reviewer;
- слияние веток;
- закрытие задачи.

Главная задача контроля — обеспечить согласованность:

**Todoing ↔ OpenSpec ↔ Git.**

Проверки должны работать как последовательность барьеров. Недопустимо полагаться только на итоговую проверку.

### Защита контекстных файлов

- Приоритет — универсальные механизмы Git; второй уровень — механизмы конкретного harness (например, ZCode); для остальных harness фиксируются принципы и пример реализации.
- Защищённые файлы определяются централизованным списком.
- Технический запрет имеет приоритет над инструкциями агента.
- Controlled File Update: агент формирует заявку на изменение защищённого файла; пользователь утверждает заявку и отдельно запускает применение; Manifest самостоятельно проверяет и применяет изменения. Агент никогда не получает прямого разрешения на запись защищённого файла.

## 12. Состав MVP

### Входит в MVP

1. Manifest Core.
2. Структура и набор утверждённых шаблонов (для MVP — один общий
   шаблон, решено 22.11.2026).
3. `manifest-init`.
4. Конфигурация типов и направлений проектов.
5. Preflight.
6. Установка контекстных файлов с защитой от перезаписи.
7. Установка Git Hooks и контрольных скриптов.
8. Интеграция процессов Todoing и OpenSpec.
9. Контроль согласованности Todoing, OpenSpec и Git.
10. Подключение `context-files-guard`.
11. Архивирование отключённых шаблонов (функция согласована; включение
    в MVP не решено — см. `architecture-decisions.ru.md` §11).
12. Поддержка новых и существующих Git-проектов с отсутствующим или частичным набором контекстных файлов.

### За пределами MVP

- Специализированные шаблоны для разных типов проектов
  (решено 22.11.2026).
- Отдельный утверждаемый процесс обновления файлов Manifest в
  подключённых проектах; обновление не является повторной
  инициализацией, детали процесса открыты (решено 22.11.2026).
- Автоматическое объединение существующих контекстных файлов с шаблонами Manifest.
- Полная миграция проектов с собственной развитой системой контекста.
- Автоматическое обновление шаблонов во всех ранее подключённых проектах.
- Автоматическое исправление любых проблем, обнаруженных Preflight.

При этом возможность дальнейшего развития должна учитываться в архитектуре.

## 14. Архитектурные ограничения

Следующие принципы обязательны:

1. Git — обязательная основа работы.
2. Агент не получает полномочий самостоятельно создавать задачи без разрешения пользователя.
3. Изменения выполняются в рамках утверждённых задач.
4. OpenSpec обязателен для изменений.
5. Исполнитель не проверяет собственную работу.
6. Контекстные файлы защищены от самостоятельного изменения.
7. Существующие файлы проекта не перезаписываются при первоначальном подключении.
8. Контроль выполняется на всех этапах жизненного цикла задачи.
9. Manifest не управляет настройками конкретного AI-harness.
10. Все эталонные шаблоны хранятся централизованно в репозитории Manifest.

## 15. Автономность и переносимость

Принципы утверждены 22.11.2026 (change `add-portability-principles`):

1. Публичные файлы Manifest не содержат машинно-зависимых абсолютных
   путей, персональных данных, упоминаний посторонних проектов и
   инструкций, привязанных к конкретной модели или AI-harness.
2. Инфраструктура — переносимые Bash-скрипты без зависимостей от
   GNU-специфичных утилит; каждый используемый внешний бинарный
   инструмент объявлен в реестре внешних зависимостей
   (`external-dependencies.ru.md`).
3. Шаблоны ссылаются на контекстные файлы только по каноническим
   именам, которые Manifest устанавливает.
4. Переводы строк нормализованы через `.gitattributes`; байты
   скриптов и шаблонов стабильны между платформами.
5. Автоматические проверки автономности выполняются при каждой
   верификации репозитория и касаются только файлов самого Manifest;
   они не накладывают требований на проекты, использующие Manifest.

---

**Итоговая концепция:** Manifest превращает работу LLM-агентов из набора самостоятельных действий в контролируемый процесс с формализованными задачами, спецификациями, ролями, независимой проверкой и автоматическими барьерами.
