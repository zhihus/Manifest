# Description
Утверждённая минимальная структура репозитория Manifest и проектов, подключённых к нему.

## 1. Назначение

Документ фиксирует согласованную структуру самого Manifest и проектов, которые подключаются к нему.

Это архитектурное решение определяет расположение основных файлов и границы ответственности каталогов. Оно не означает, что все компоненты должны быть установлены в каждом проекте: OpenSpec и Todoing подключаются по необходимости.

Manifest предоставляет общие правила и механизмы подключения. Подключённый проект хранит собственный код, требования, архитектурные решения и планы. Todoing, OpenSpec и Git сохраняют каждый свою область ответственности.

## 2. Основные принципы

1. Один файл отвечает за одну область и не дублирует другие документы.
2. В корне находятся только основные файлы проекта.
3. Документы, настройки Manifest, задачи и требования хранятся раздельно.
4. Необязательные компоненты не создают пустых каталогов.
5. История изменений хранится в Git; изменения OpenSpec архивируются штатными средствами OpenSpec.
6. При подключении Manifest существующие файлы не перезаписываются. Конфликты показываются пользователю.
7. Не создаются копии требований OpenSpec или задач Todoing в документации проекта.

## 3. Структура подключённого проекта

```text
project/
├── AGENTS.md
├── llms.txt
├── COMMIT_RULES.md
├── VERSION
├── VERSIONING.md
├── RELEASES.md
├── .llmignore
│
├── .manifest/
│   ├── <project-config>
│   ├── project-id
│   ├── validate.sh
│   └── hooks/
│       ├── pre-commit
│       └── commit-msg
│
├── docs/
│   ├── architecture/
│   └── plans/
│
├── openspec/             # если OpenSpec подключён
│   ├── config.yaml
│   ├── specs/
│   └── changes/
│
└── .todoing/             # если Todoing подключён
```

### 3.1. Основные файлы в корне

| Файл | Назначение |
|---|---|
| AGENTS.md | Основные правила работы агентов и границы их полномочий. |
| llms.txt | Краткая карта проекта и ссылки на документы. |
| COMMIT_RULES.md | Правила оформления и выполнения коммитов. |
| VERSION | Текущая версия проекта. |
| VERSIONING.md | Правила изменения версии. |
| RELEASES.md | Правила подготовки и выпуска версий. |
| .llmignore | Ограничения на чтение файлов агентами. |

Эти файлы образуют базовый набор структуры. Их содержимое и шаблоны должны соответствовать отдельным правилам Manifest. Специализированные правила разработки, тестирования и логирования добавляются только при необходимости и не дублируют AGENTS.md.

### 3.2. Каталог .manifest

Каталог принадлежит Manifest. В нём находятся только данные и механизмы подключения:

- конфигурация подключённого проекта;
- постоянный идентификатор проекта;
- скрипт проверки структуры и настроек;
- установленные Git Hooks.

Архитектурные документы, планы, задачи и требования в .manifest не хранятся.

Точное имя и формат файла конфигурации определяются отдельным контрактом Manifest.

### 3.3. Каталог docs

- docs/architecture/ — устройство проекта, архитектурные решения, контракты и их обоснования.
- docs/plans/ — долгосрочные планы, не являющиеся активными задачами.

Другие постоянные каталоги документации создаются только при устойчивой необходимости.

### 3.4. Каталог openspec

OpenSpec подключается по необходимости и сохраняет собственную структуру:

- specs/ — действующие требования;
- changes/ — активные изменения и архив изменений.

Manifest не создаёт параллельные копии спецификаций OpenSpec в docs/.

### 3.5. Каталог .todoing

Каталог принадлежит Todoing. Задачи, их статусы и история ведутся Todoing. Manifest взаимодействует с ним через публичный интерфейс Todoing и не редактирует внутренние данные напрямую.

Если Todoing не подключён, каталог отсутствует.

## 4. Источники истины

| Информация | Источник истины |
|---|---|
| Общие правила и механизмы подключения | Репозиторий Manifest |
| Настройки подключения проекта | .manifest/ |
| Требования и сценарии изменений | OpenSpec, если подключён |
| Задачи, статусы и история | Todoing, если подключён |
| Код и история изменений | Git |
| Архитектурные решения проекта | docs/architecture/ |
| Долгосрочные планы | docs/plans/ |

Одна и та же информация не должна независимо поддерживаться в нескольких местах.

## 5. Структура репозитория Manifest

В репозитории самого Manifest сохраняются следующие основные каталоги:

- docs/architecture/ — архитектура Manifest, решения и контракты интеграций;
- docs/plans/ — планы развития Manifest;
- docs/templates/ — шаблоны файлов для подключаемых проектов;
- workflow/ — правила и процессы работы;
- openspec/ — требования и изменения самого Manifest;
- scripts/ — служебные и проверочные скрипты Manifest.

### 5.1. Организация архитектурных документов

Внутри docs/architecture/ применяется следующее разделение:

```text
docs/architecture/
├── основные документы и актуальные решения
├── audits/       # проверки и аудиты
├── contracts/   # контракты интеграций
└── history/     # протоколы и заменённые редакции
```

Основные архитектурные документы остаются на верхнем уровне. Аудиты, контракты и исторические материалы размещаются в соответствующих каталогах.

Перемещение уже существующих документов выполняется отдельно: после проверки ссылок, с сохранением истории Git и обновлением всех ссылок. Исторические документы не удаляются.

## 6. Правила применения

1. Эта структура является целевой для новых проектов, подключаемых к Manifest.
2. Отсутствие OpenSpec или Todoing не требует создания соответствующего каталога.
3. Подключение Manifest не перезаписывает пользовательские файлы.
4. Существующие проекты не перестраиваются автоматически. Их перенос на новую структуру выполняется отдельной проверяемой миграцией с отчётом и сохранением пользовательских файлов.
5. Шаблоны, правила и проверочные скрипты Manifest должны соответствовать этой структуре.
6. При обнаружении противоречий в документах Manifest приоритет имеет это утверждённое архитектурное решение. Зависимые документы и шаблоны приводятся в соответствие отдельными изменениями.

## 7. Следующие действия по внедрению

1. Сверить существующий перечень обязательных файлов и шаблонов с этой структурой.
2. Привести спецификацию и правила manifest-init в соответствие.
3. Обновить шаблоны и проверку структуры.
4. Проверить подключение на тестовых проектах.
5. Подготовить отдельную процедуру миграции существующих проектов.

Утверждение структуры не означает автоматического выполнения этих изменений. Каждый этап внедрения должен быть проверяемым и сохранять существующие данные пользователя.
