# Architecture Decisions — Manifest

**Статусы:** **Принято** (П), **Предварительно** (ПП), **Отложено** (О),
**Не решено** (Н), **Выполнено** (В — аналитическая/документальная работа),
**Не реализовано** (НР). Источники: brief v0.4.0, протокол 22.11.2026
(`architecture-session-2026-11-22.ru.md`), аудиты, решения по Todoing
(PR #1 todoing-x: PRODUCT.md, docs/architecture/decisions.md), обсуждения
20–21.11.2026. Рекомендации аудиторов — не решения. Принятие решения ≠
реализация функции: реализация помечается «НР».

**В — выполненная аналитическая работа:** architecture-audit.ru.md;
todoing-manifest-integration-audit.ru.md; architecture-decisions.ru.md;
role-model-decisions.ru.md; целевые документы Todoing в PR #1.

## 1. Принципы

- П: Git — обязательная основа; изменения в рамках утверждённых задач;
  OpenSpec обязателен (кроме автоматических операций Manifest).
- П (22.11.2026, change `add-portability-principles`, подтверждено
  пользователем в ревью 2026-11-22): автономность и
  переносимость. Публичные файлы Manifest не содержат машинных путей,
  персональных данных, упоминаний посторонних проектов и привязок к
  конкретной модели или AI-harness (записи в `docs/architecture/` —
  исторические решения, вне проверки). Инфраструктура — переносимые
  Bash-скрипты без зависимостей от GNU-специфичных утилит; каждый
  внешний бинарный инструмент объявлен в реестре
  (`external-dependencies.ru.md`; Perl рендеринга шаблонов
  задокументирован, Python удалён). SHA-256 детектируется
  (`sha256sum` или `shasum -a 256`). Шаблоны ссылаются только на
  канонические имена установленных файлов. Переводы строк
  нормализованы `.gitattributes`. Проверки автономности
  автоматизированы в verify.sh и касаются только файлов самого
  Manifest.
- П: Manifest ↔ Todoing — только CLI и версионируемый JSON-контракт, без
  прямого чтения хранилища.
- П: Todoing даёт универсальные механизмы и Hooks без правил Manifest;
  полномочия определяет Manifest.
- П: Источники истины: Todoing — задачи и история; OpenSpec — требования;
  Git — код.
- П: Контроль — барьеры на всех этапах; шаблоны — централизованно; настройки
  AI-harness — вне Manifest.
- Н: Модель доверия (технические гарантии vs процедурные правила).

## 3. manifest-init

- П: Preflight обязателен; при провале установка не начинается.
- П: Существующие файлы не перезаписываются; конфликты имён фиксируются;
  автослияния нет; отключённые шаблоны — в архив.
- Н: Повторный запуск manifest-init: классы владения файлами.
  Решено 22.11.2026: повторная инициализация не предусмотрена; рабочий
  каталог — `.manifest` в корне проекта, настройки — в отдельном
  стабильном конфигурационном файле, не перезаписывается
  автоматически; обязателен механизм защиты от случайной перезаписи.
- Н: Стратегия hooks при существующих hook-менеджерах.
  Решено 22.11.2026: используются существующие механизмы Git и
  AI-harness, собственный менеджер hooks не разрабатывается;
  совместимость установки остаётся открытым вопросом.
- Н: Канонические имена файлов набора (Brief vs репозиторий расходятся).

## 4. Todoing

- П: Каждому проекту — отдельное хранилище задач. Общий обзор — О.
- П: Результаты завершения и отмены — отдельные terminal outcomes (`completed`, `cancelled`), не функции архивирования. Workflow status и outcome независимы; явная отмена не меняет workflow status.
- П: Идентификатор проекта: при интеграции обязателен, CLI должен его
  получать. Н: способ передачи/закрепления/защиты в AI-harness не определён;
  настройка AI-harness — вне Manifest.
- П: Статусы расширяемые, настраиваемые пользователем; Manifest предоставляет
  рекомендуемую конфигурацию, не навязывая её.
- П: История полная, неизменяемая, дополняемая; каждое успешное сохранение
  создаёт новую версию; утверждённая версия — контрольная.
- П: Физическое удаление запрещено; ID задач не переиспользуются.
- П: Архивирование — отдельная функция, не следствие статусов результата;
  архивировать можно независимо от статуса. Архивные исключены из доски,
  доступны в отдельном списке; восстановление предусмотрено. Агентам
  разрешено читать незаблокированные архивные задачи при проработке задач
  в Backlog; заблокированная архивная задача подчиняется эксклюзивной
  блокировке. Причина отмены необязательна.
- П: Параллельная работа — эксклюзивная блокировка на всё время работы
  агента, включая запрет чтения другими клиентами; захват операцией захвата;
  действует до явного освобождения или автоистечения; механизм истечения
  должен учитывать аварийное завершение агента.
- П: Изменение задачи, истории и состояния — атомарно.
- П: Системные операции (версионирование, история, метаданные) — автоматически
  по событиям, не по усмотрению агента.
- П: Hooks/events — универсальные, необязательные; отсутствие обработчика не
  ломает операцию. Todoing не содержит знаний о Manifest или OpenSpec.
- П: Самостоятельное использование Todoing не требует интеграции; ограничения
  Manifest — только при интеграции.
- П: Полный экспорт/импорт согласован архитектурно; О: реализация — вне MVP.
- Факт реализации Todoing на актуальном HEAD: SQLite project store. Это выбор реализации Todoing, а не ограничение для потребителя; Manifest использует только публичный CLI/JSON API.
- О: GUI, общий обзор задач.
- Н: Карта статусов Manifest (6) ↔ Todoing. Решено 22.11.2026:
  Todoing — единственный источник статуса задачи; Manifest статусы не
  дублирует, отдельная карта соответствия не требуется; внутренние
  этапы Manifest сохраняются.
- Решено 22.11.2026, отмена задач: любой агент может рекомендовать
  отмену с обоснованием; отмену подтверждает только пользователь;
  после подтверждения оркестратор фиксирует outcome `cancelled` через
  `task.cancel` (workflow status не меняется) и архивирует связанное OpenSpec
  change штатным механизмом Archive;
  основные спецификации OpenSpec не обновляются.
- В (реализовано в todoing-x на HEAD 947048d): SQLite JSON API v1, Project ID,
  task CRUD/status/outcome, immutable versions, append-only operation history,
  approval baseline, dependencies, exclusive locks/fencing, archive/restore,
  Git SHA references, verify/migrate/snapshot.
- НР (требуется универсальное расширение Todoing по целевому контракту): generic
  external references, structured Review records + revision_count, final commit
  marker. Эти механизмы не должны содержать Manifest/OpenSpec-specific semantics.

## 5. OpenSpec и Todoing

- П: Одна глобальная задача Todoing = одна глобальная задача OpenSpec;
  Todoing хранит связь через generic external reference и итоговый commit/merge
  через generic final commit marker. Todoing не парсит OpenSpec и не определяет
  Git workflow. Требуемые external-reference/final-commit API отсутствуют в
  текущем Todoing API v1 и должны быть реализованы универсально.
- П: Todoing — единственный источник workflow status и outcome задачи;
  отдельная карта статусов не требуется. Manifest управляет переходами по
  утверждённой политике и обеспечивает согласованность OpenSpec/Git.
- П: Reviewer remarks/history и `revision_count` — универсальные данные задачи
  в Todoing. `revision_count` увеличивается ровно на один на каждую новую
  запись Review с outcome `changes_requested`; несколько комментариев в одной
  записи дают одно увеличение. API v1 extension пока не реализован.

## 6. Роли и полномочия

- П: Роли (7): Оркестратор, Исполнитель, Code Reviewer, Автор документации,
  Documentation Reviewer, Tester, Analyst; исполнитель не проверяет свою
  работу. Tester готовит тесты до реализации (TEST FIRST). Решено
  21.11.2026 (role-model-decisions.ru.md).
- П: Analyst работает с пользователем в Backlog, анализирует контекст,
  зависимости, спецификации, создаёт задачу в Todoing (разрешение — через
  совместную работу в Backlog); пользователь сам переводит задачу
  в «К выполнению».
- П: Оркестратор организует выполнение утверждённой задачи; всегда
  использует модель GLM-5.3 Flash; не подменяет Analyst и не утверждает
  задачи за пользователя. Остальным ролям модели не закреплены; распределение
  моделей — О.
- П: Замечания Reviewer передаются оркестратору; он повторно запускает
  исполнителя до устранения замечаний; блокирующие ошибки эскалируются
  пользователю.
- П: Одна модель может использоваться для разных ролей; каждой роли —
  отдельный агент со своим контекстом и инструкциями.
- Н: Общая эскалация при разногласии Оркестратор/Reviewer вне цикла
  исправлений; статус ролей Architect/Planner workflow-README.

## 7. Git, ветвление, релизы

- П: Основная ветка — develop; задача — отдельная ветка; слияние и закрытие —
  оркестратор. Промежуточные коммиты разрешены. VERSIONING.md, RELEASES.md —
  самостоятельные документы.
- П: Последовательное выполнение — обязательное правило: агенты запускаются
  последовательно, параллельный запуск запрещён (анализ, реализация,
  проверка); в проекте одновременно одна глобальная задача; переход при
  блокировке — только без зависимости от заблокированной. Решено
  21.11.2026 (role-model-decisions.ru.md).
- ПП: Техническая блокировка параллельного запуска — механизмами harness
  (например, hooks ZCode); Н: универсальная гарантия для всех harness.
- Н: Кто разрешает конфликты слияния и нужна ли ревью после.
  Решено 22.11.2026: конфликт разрешает назначенный оркестратором
  Исполнитель; после разрешения обязательны автоматические проверки;
  дополнительно проводится независимое ревью агентом с чистым
  контекстом; исполнитель не подтверждает правильность собственного
  решения; оркестратор контролирует результат и выполняет слияние.

## 8. Контроль и безопасность

- П: Контрольные точки: ветки, коммиты, статусы Todoing, состояние OpenSpec,
  передача на проверку, ревью, слияние, закрытие.
- П: Правило «смены статусов — только через CLI Todoing» относится к
  интеграции с Manifest. Автономное использование им не ограничивается:
  Todoing даёт универсальные механизмы, обязательную политику определяет
  интегрирующая система.
- П: Контекстные файлы защищены: приоритет — универсальные механизмы Git,
  второй уровень — механизмы harness (например, ZCode); для остальных harness
  — принципы и пример реализации. Защищённые файлы — централизованный список.
  Технический запрет выше инструкций агента.
- П: Controlled File Update: агент формирует заявку; пользователь утверждает
  её и отдельно запускает применение; Manifest проверяет и применяет
  изменения. Агент никогда не получает прямого разрешения на запись
  защищённого файла.
- НР: механизм Controlled File Update и централизованный список не реализованы.
- Н: Технические гарантии vs процедурные не разделены.
- Н: Hooks не перехватывают ветки; Preflight-проверки Todoing.

## 9. Резервирование и переносимость

- П: Резервирование обеспечивает Manifest — обязательное требование; Git не
  является резервной копией; реализация отложена; минимум — отдельный
  физический диск; удалённое хранилище допускается.
- О: Стратегия, периодичность, триггеры, ротация, восстановление, формат
  экспорта/импорта — отдельное проектирование.

## 10. Типы проектов

- П: Code / Documentation / Mixed — конфигурации единой системы; направление
  определяет модель, полноту проверяют скрипты.
- Н: Формат конфигурации (имя, расположение, флаги) — Brief §13.
  Решено 22.11.2026: рабочим каталогом служит `.manifest` в корне
  проекта, настройки — в отдельном файле; формат файла и схема флагов
  остаются открытыми.
- Решено 22.11.2026, шаблоны: для MVP один общий шаблон;
  специализированные шаблоны для типов проектов отложены на Roadmap.
- Решено 22.11.2026, обновление Manifest: для подключённых проектов
  предусматривается отдельный утверждаемый процесс обновления файлов
  Manifest; обновление не является повторной инициализацией; детали
  процесса открыты.

## 11. MVP

Входит (П): Manifest Core; шаблоны; manifest-init; Preflight; установка
файлов с защитой от перезаписи; hooks и контрольные скрипты; интеграция
Todoing и OpenSpec; контроль согласованности трёх систем; context-files-guard;
Git-проекты. Архивирование как функция согласовано; включение в MVP не
решено.
Решено 22.11.2026: MVP использует один общий шаблон; отмена задач
входит в интеграцию Todoing/OpenSpec; для обновления Manifest-файлов
в подключённых проектах процесс определяется вне MVP.
Предусловие MVP (ПП): минимальный контракт Todoing — поля связей, версия
контракта, история, версии, блокировки.
За пределами MVP (О): автослияние контекстных файлов; миграция развитых
систем контекста; автообновление шаблонов; автоисправление Preflight; GUI;
общий обзор; реализация экспорта/импорта, резервирования; удалённое
хранилище.
22.11.2026: brief v0.3.1 приведён в соответствие с этим разделом —
пункт архивирования в §12 brief помечен «включение в MVP не решено»;
решение по включению остаётся за пользователем.
