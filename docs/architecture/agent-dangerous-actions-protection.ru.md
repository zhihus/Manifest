# Защита от опасных действий агентов

# Metadata
> **Status: draft**

> **Updated: 2026-11-27**  

# Description
Перспективный архитектурный план защиты проектов Manifest от опасных
действий, которые AI-агент может выполнить через инструменты. Документ
описывает цель и границы защиты, предварительный набор категорий
опасных действий, механизм перехвата и полный жизненный цикл решений
`allow` / `ask` / `deny`, взаимодействие с агентами и инструментами,
ограничения, сценарии отказа и требования безопасности. Защита
рассматривается как самостоятельная способность Manifest: конкретный
способ принудительного исполнения (универсальные механизмы Git,
механизмы конкретного AI-harness) — предмет отдельного проектирования
и в документе не привязан к конкретному harness.

## 1. Цель и границы

### 1.1. Цель

Защитить проект от опасных действий, которые AI-агент выполняет через
инструменты. Механизм принимает решение по каждому вызову: разрешить
автоматически по утверждённой политике (`allow`), запросить
подтверждение пользователя (`ask`) или отклонить (`deny`).

Механизм не выполняет опасное действие сам и не принимает решений
за пользователя там, где требуется его подтверждение: он прерывает
вызов, передаёт запрос на подтверждение и доносит ответ пользователя
до агента. Автоматические решения (`allow` и `deny`) принимаются по
заранее утверждённой политике, а не пользователем в момент вызова.

### 1.2. Границы

- Защита действует на уровне вызовов инструментов (до их выполнения),
  а не только на этапе коммита.
- Основной объём функции — защита вызовов инструментов. Перехват
  пользовательских промптов и сообщений агента — отдельные будущие
  направления (см. §7).
- Механизм не заменяет согласование задач, роли и гейты workflow: он
  дополняет их на уровне исполнения инструментов.
- Механизм не изменяет архитектуру других компонентов Manifest.

### 1.3. Место в архитектуре Manifest

Защита от опасных действий — самостоятельная перспективная способность
Manifest, а не функция отдельного компонента.

`context-files-guard` — связанный существующий механизм и частный
случай этой защиты: он защищает конкретный класс объектов —
контекстные файлы (см. `architecture-brief.ru.md`, раздел «Защита
контекстных файлов»). Способность защиты от опасных действий
покрывает более широкий класс действий; `context-files-guard` — один
из её частников, а не компонент, который автоматически отвечает за
все опасные действия.

Принцип «технический запрет имеет приоритет над инструкциями агента»
применяется и к опасным действиям: запрет настраивается пользователем
и не отменяется промптом.

## 2. Категории опасных действий

Категории определяются по `tool_input` вызова, а не по семантике
намерения. Ниже — предварительный набор категорий: это исходная точка
для проектирования, а не утверждённые настройки по умолчанию.

- разрушительные файловые операции (`rm -rf` и аналоги);
- запись в системные и защищённые пути;
- выполнение внешнего кода (`curl … | sh`, загрузка и запуск);
- отправка данных наружу (сеть, API);
- переписывание Git-истории (`reset --hard`, `rebase`, force-push);
- изменение защищённых контекстных файлов.

Точный состав категорий, их пороги и решения по каждой — предмет
проектирования (см. §9).

## 3. Механизм перехвата

### 3.1. Точка перехвата

Перехват происходит до выполнения вызова инструмента. Механизм
получает полный вход вызова (имя инструмента и его аргументы) и
принимает решение: разрешить (`allow`), запросить подтверждение
(`ask`) или отклонить (`deny`).

### 3.2. Определение «опасности»

«Опасность» определяется набором правил по `tool_input` (паттерны),
а не семантическим анализом намерения. Для типовых случаев этого
достаточно; расширение на семантику — возможное развитие (см. §9).

### 3.3. Политика и механизмы принудительного исполнения

Универсальная политика безопасности (что считается опасным, какое
решение по каждой категории) отделена от конкретных механизмов её
принудительного исполнения. Политика не зависит от harness;
механизмы исполнения — зависят.

Приоритет механизмов исполнения согласован с решением Manifest
(см. `architecture-brief.ru.md`, раздел «Автоматизированный
контроль»):

- первый уровень — универсальные механизмы Git (Git Hooks и
  контрольные скрипты, устанавливаемые `manifest-init`);
- второй уровень — механизмы конкретного AI-harness (например, ZCode);
  для остальных harness фиксируются принципы и пример реализации.

Manifest не разрабатывает собственный менеджер hooks и не управляет
настройками конкретного AI-harness. Поведение защиты не гарантировано
одинаковым на всех harness: оно одинаково там, где действует
универсальный уровень (Git), и зависит от возможностей конкретного
harness на втором уровне.

### 3.4. Жизненный цикл решений `allow` / `ask` / `deny`

Для каждого вызова механизм выдаёт одно из трёх решений.

`allow`:

- вызов разрешён автоматически по утверждённой политике;
- вызов возвращается исполнителю и выполняется без участия
  пользователя;
- подтверждение пользователя не требуется.

`ask`:

- механизм прерывает выполнение и передаёт пользователю запрос на
  подтверждение с описанием действия (инструмент и аргументы);
- пользователь подтверждает или отклоняет;
- при подтверждении вызов возвращается исполнителю и выполняется;
- при отклонении вызов не выполняется и агенту передаётся причина;
- подтверждение привязано к конкретному вызову: повторное
  выполнение того же вызова и применение подтверждения к другому
  вызову исключаются. Конкретный способ привязки (идентификатор
  вызова, одноразовый токен, контроль повторного срабатывания) —
  открытое архитектурное решение (см. §9).

`deny`:

- вызов отклоняется по утверждённой политике;
- агенту передаётся причина отклонения;
- вызов не выполняется и пользователю не передаётся.

## 4. Передача запроса пользователю

При решении `ask` механизм прерывает выполнение и передаёт
пользователю запрос на подтверждение.

Канал передачи (интерфейс, поле ввода, уведомление) — предмет
проектирования. Требование: пользователь получает описание действия
(инструмент и аргументы) и может задать ответ — подтвердить или
отклонить.

## 5. Обработка ответа пользователя

Ответ пользователя на решение `ask` доходит до агента двумя путями:

- как причина отклонения (агент видит, почему действие не выполнено);
- как дополнительный контекст (агент видит заданный пользователем
  ответ).

При пустом ответе поведение определяется политикой (см. §9):
по умолчанию — отклонить с системным сообщением.

## 6. Взаимодействие с агентами и инструментами

- Механизм работает на границе «агент → инструмент»: он видит вход
  вызова и возвращает решение исполнителю.
- Агент не получает прямого разрешения на действие, требующее
  подтверждения: решение принимает пользователь.
- Автоматические решения (`allow` и `deny`) принимаются по утверждённой
  политике, без участия пользователя в момент вызова.
- Механизм не переписывает намерение агента: он может только
  отклонить, запросить подтверждение или пропустить. Переписать вход
  вызова (например, заменить опасный путь) — возможное развитие
  (см. §9).

## 7. Ограничения и сценарии отказа

1. Определение «опасности» по паттернам, а не по семантике: возможны
   ложные срабатывания и пропуски.
2. Перехват синхронный: механизм должен быть быстрым, чтобы не
   блокировать работу агента.
3. Поведение защиты не одинаково на всех harness: универсальный
   уровень (Git) действует одинаково, второй уровень зависит от
   возможностей конкретного harness.
4. При недоступности канала подтверждения (пользователь не ответил)
   действие не выполняется: безопасное поведение по умолчанию —
   отклонить.

Перехват пользовательских промптов и сообщений самого агента выходит
за границы текущей функции (защита вызовов инструментов) и
рассматривается как отдельные будущие направления: для промпта точка
перехвата иная (до обработки промпта), для вывода агента прямого
перехвата текста нет.

## 8. Требования безопасности

Требования разделены по классам данных:

- Секреты и чувствительные данные: не пишутся в Git, логи и аргументы
  командной строки.
- Содержимое перехваченных вызовов: запись в Git, логи и аргументы
  командной строки запрещена по умолчанию; вопрос о допустимости
  записи в журнал — открытое решение (см. §9).
- Безопасные метаданные аудита: могут записываться для аудита;
  состав аудита не принят и определяется решением пользователя
  (см. §9).

Дополнительно:

- Запрет настраивается пользователем и не отменяется инструкциями
  агента или промптом.
- Механизм не хранит секретов: он передаёт только описание действия
  и ответ пользователя.
- Отказ по умолчанию безопасен: при ошибке или таймауте действие
  отклоняется, а не выполняется.

## 9. Открытые вопросы (требуют проектирования)

1. Точный набор категорий «опасных» действий, их пороги и решения по
   каждой категории.
2. Канал передачи запроса пользователю (интерфейс, поле,
   уведомление).
3. Поведение при пустом ответе: отклонить или пропустить.
4. Состав аудита: записываются ли события перехвата, какие метаданные
   и где хранятся.
5. Расширение на семантический анализ намерения (сверх паттернов).
6. Переписывание входа вызова (замена опасного пути на безопасный).
7. Локализация интерфейса (en/ru).
8. Способ привязки подтверждения к конкретному вызову: исключение
   повторного выполнения и применения подтверждения к другому вызову.

## 10. Возможные этапы реализации

1. Фиксация категорий и политики (этот документ → решение).
2. Прототип перехвата на конкретном harness (см. Приложение А).
3. Канал передачи запроса и обработки ответа.
4. Интеграция с `context-files-guard` и Git Hooks.
5. Журнал аудита (по решению).

## Приложение А. Прототип на ZCode (референс)

ZCode поддерживает события хуков, которые могут использоваться как
прототип механизма перехвата. Это один из возможных способов
реализации, а не архитектурная зависимость Manifest.

### А.1. События и точка перехвата

ZCode поддерживает события хуков, среди которых `PreToolUse` — точка
перехвата до выполнения инструмента. Matcher — регэксп по имени
инструмента (регистрозависимый), например `Bash|Write|Edit`; без
matcher срабатывает на все инструменты.

### А.2. Вход и выход хука

Хук получает на stdin JSON с полным входом вызова (`tool_name`,
`tool_input` и др.) и возвращает JSON-решение. Для `PreToolUse`
поддерживаются поля:

| Поле | Значение |
|---|---|
| `permissionDecision` | `deny` — запретить; `ask` — запросить подтверждение; `allow` — пропустить. |
| `permissionDecisionReason` | Текст причины; попадает агенту как причина отказа. |
| `additionalContext` | Дополнительный контекст; инжектится в разговор. |
| `updatedInput` | Переписанный вход (дополнительная возможность). |

Коды выхода: `0` — пропустить, `2` — блокировать (deny), другое
ненулевое — ошибка. Схема выхода строгая: лишний ключ отбрасывает
эффект хука.

### А.3. Канал передачи ответа

В прототипе ответ пользователя хранится в файле данных плагина:
интерфейс (панель) записывает файл, хук читает его при перехвате.
Альтернативный канал — `userConfig` манифеста, но подстановка
`${user_config.<key>}` работает только в конфигурации MCP-серверов, а
не в командах хуков, поэтому панель выбран как основной канал.

### А.4. Примитивы ZCode

| Примитив | Назначение |
|---|---|
| События хуков (`PreToolUse` и др.) | Точки перехвата до выполнения инструмента. |
| `createCompatibleHookStdin` | Передача входа вызова хук-скрипту через stdin (JSON). |
| `processHookOutput` | Разбор вывода хука: `permissionDecision`, `permissionDecisionReason`, `additionalContext`, `updatedInput`. |
| Инжекция контекста | Ответ хука доходит до агента как `hook additional context` и причина отказа. |
| `ui.surfaces` в манифесте | Постоянная панель интерфейса с HTML-страницей. |
| `ZCODE_PLUGIN_DATA` | Общая директория данных для хука и MCP-сервера. |

### А.5. Оценка объёма прототипа

| Файл | Оценка |
|---|---|
| `plugin.json` (манифест) | ~20 строк |
| `hooks.json` (регистрация хука) | ~10 строк |
| `check.mjs` (скрипт перехвата) | 60–100 строк |
| `server.mjs` (MCP-сервер) | 100–150 строк |
| `panel.html` (страница панели) | 50–80 строк |

Каркас генерируется скиллом `plugin-creator`; страница панели — по
образцу `zcode-mcp-app-dev`. Установка — через локальный marketplace
и Settings → Plugin Management.
