# Манифест управления проектом (сжатая версия)

## 1. Назначение

Манифест — человекочитаемый документ. Определяет архитектуру файлов инструкций для LLM, правила организации и распределение ответственности (пользователь / модель / скрипты). Не входит в контекст модели.

## 2. Принципы

1. Минимальный объём информации при однозначности.
2. Общие правила — в одном месте. Специализированные ссылаются, не копируют.
3. Модель анализирует и создаёт; скрипты выполняют формализуемое; пользователь определяет правила.
4. Модель изменяет файлы только в разрешённых пределах.
5. Ссылки соответствуют фактической структуре.
6. Набор процессов определяется конфигурацией проекта.
7. Новые технологии не требуют дублирования общих правил.

## 3. Конфигурация проекта

Признаки проекта (сочетаемые):

- `source_code` — разработка кода
- `documentation` — документация
- `build` — сборка
- `testing` — тестирование
- `release` — выпуск версий

Конфигурация определяет применимые инструкции, скрипты и процессы. Неиспользуемые не создаются.

## 4. Архитектура файлов инструкций

### 4.1. Маршруты агентов

Отдельные маршруты для кода и документации. Каждый определяет последовательность чтения и подключает только необходимые файлы.

### 4.2. Общие инструкции

Правила, не зависящие от технологий: версионирование, коммиты, релизы, безопасность, навигация.

### 4.3. Специализированные инструкции

Правила, зависящие от технологий: код, документация, сборка, тесты. Не дублируют общие.

### 4.4. Скрипты

Формализуемые операции и проверки. Состав — по конфигурации.

## 5. Процессы

1. Структура и навигация — карта проекта, маршруты.
2. AGENTS.md — спецификация: см. §10.
3. Разработка — правила изменения кода, документации, конфигураций.
4. Версионирование — источники версий, автообновление, проверки.
5. Логирование — журналирование, обработка ошибок.
6. Тестирование — тесты кода, проверки документации.
7. Проверка документации — ссылки, пути, структура, терминология.
8. Сборка — получение и проверка артефактов.
9. Коммиты — формат, подготовка, проверки.
10. Целостность — согласованность файлов и рабочего состояния.
11. Релизы — подготовка, проверка, фиксация.
12. Управление изменениями — анализ влияния, актуализация.
13. Безопасность — секреты, права, чувствительные данные.
14. Автоматизация — скрипты, условия запуска, сбои.
15. Завершение — критерии готовности, результаты, незакрытые вопросы.

Для каждого: применимость, инструкции, скрипты, связи, полномочия, критерии завершения.

## 6. Правила изменения файлов

1. Модель определяет необходимые связи.
2. Новые ссылки — по шаблонам, в разрешённые разделы.
3. Содержимое за пределами разрешённых изменений сохраняется.
4. Формализуемые операции — скриптами.
5. Скрипты проверяют соответствие правилам.
6. Решения с участием пользователя — не автоматически.

## 7. Ответственность

- Манифест — архитектура, принципы, правила.
- Модель — анализ, создание, изменение в границах.
- Скрипты — однозначные операции, проверки.
- Пользователь — требования, утверждение решений.

## 8. Поддержание

Изменяется при пересмотре архитектуры, принципов или распределения ответственности. Описывает ключевые файлы, но не обязан перечислять все.

## 9. Язык и правила ведения

1. Манифест — на русском.
2. Требования — краткие, конкретные, проверяемые.
3. Минимальное содержимое без потери смысла.
4. Общие правила — в одном месте.
5. Не удалять/ослаблять без основания и согласования.
6. Не выдумывать неизвестные значения.
7. Перед изменением — проверить фактическую структуру.
8. Сохранять утверждённые требования, статусы, идентификаторы, доказательства, риски, критерии, ограничения.

## 10. Спецификация AGENTS.md

Манифест задаёт контракт `AGENTS.md`, не заменяет файл и не переписывает шаблон. Изменения шаблона — отдельной задачей.

### 10.1. Параметры

Каждый параметр: назначение, формат/тип, обязательность, допустимые значения, макс. длина, язык, размещение, ссылки, извлечение скриптом, проверки, ограничения.

### 10.2. Лимиты длины

| Параметр | Максимум |
|---|---:|
| `PROJECT_NAME` | 80 |
| `PROJECT_PURPOSE` | 300 |
| `ENTRY_POINT` | 200 |
| `PROJECT_CONTEXT` | 1 000 |
| Правило в `Files` | 200 |
| Блок `Files` | 800 |
| Правило в `Rules` | 200 |
| Блок `Rules` | 1 200 |
| Блок `Git` | 300 |
| Блок `Versioning` | 200 |
| Блок `Testing` | 200 |
| `AGENTS.md` целиком | 4 000 |

Лимиты действуют одновременно. Превышение = ошибка.

Подсчёт: символы Unicode (вкл. пробелы, пунктуацию, перенос = 1). В лимит файла входят заголовки и разметка. Метод — одинаков во всех проверках. Вложенные элементы: лимит одного + общий.

### 10.3. Язык

Проектные файлы инструкций — английский. Манифест — русский.

### 10.4. Проверки

Автоматически выявлять: отсутствие обязательных параметров, некорректный формат, превышение лимитов, отсутствие ссылок, ссылки на несуществующие файлы, несогласованность с конфигурацией, дублирование, несоответствие спецификации.

## 11. Экономика контекста

Оптимизируется суммарный объём фактически используемого контекста, не размер одного файла.

### 11.1. Символы и токены

Символы — для жёстких ограничений. Токены — расчётные (зависят от токенизатора).

Ориентиры (29.10.2026):

| Тип | На 1 000 символов |
|---|---:|
| Англ. связный текст | ~200 |
| Англ. тех. Markdown | 250–350 |
| Русский текст | 300–450 |
| Код/пути/данные | 300–450 |

### 11.2. Бюджет AGENTS.md (4 000 символов)

- Англ. связный: ~800 токенов
- Тех. Markdown: 1 000–1 400
- Консервативный: до 1 800

Без системных инструкций, истории, других файлов.

### 11.3. Целевые показатели

1. Минимизировать объём без потери требований.
2. Минимизировать число файлов на задачу.
3. Исключить повторную передачу правил.
4. Измерять токены штатным токенизатором.
5. Если точный подсчёт недоступен — оценка + коэффициент.
6. Сравнивать по совокупному контексту.
7. Не сокращать обязательные требования ради токенов.

### 11.4. Проверка экономики

При существенных изменениях фиксировать: символы до/после, токены до/после, измеренные токены, файлы для типовых задач, дублирование, изменение бюджета. Экономия полезна только при сохранении полноты.
