# OpenSpec Workflow: протокол взаимодействия пользователя и агентов

> **Статус: черновик — в разработке.** Протокол предварительный и может
> меняться; он ещё не является постоянным правилом проекта.

Универсальный процесс производства спецификаций и результатов работы с
помощью LLM-агентов, построенный на пайплайне изменений OpenSpec
(`proposal → specs → design → tasks → apply → verify → archive`).
Применяется к любому проекту; детали, специфичные для проекта (стек,
тест-раннеры, именование), делегируются собственным контекстным файлам
этого проекта.

Сопутствующие правила: `openspec-rules.md` (именование задач, волны,
калибровка размера) и `openspec/config.yaml` (правила по артефактам,
контекст).

## 1. Роли

Пайплайн существует внутри контекста **Оркестратора** (основная сессия /
дирижёр). Он никогда не выполняет работу специалиста: восстанавливает
состояние пайплайна, запускает нужного субагента на каждом шаге, проверяет
отчёт агента и гейтит переход к следующему шагу. Это сохраняет ключевую
инварианту: **никто никогда не проверяет свою собственную работу.**

| Шаг | Документ / артефакт | Агент | Вход → Выход |
|---|---|---|---|
| — | Состояние пайплайна, гейты, маршрутизация | **Оркестратор** | запускает шаги, проверяет отчёты, переходы/возвраты |
| 1 | `proposal.md` | **Аналитик** | слова пользователя → «зачем / что» |
| 2 | `specs/<capability>/spec.md` | **Аналитик** | proposal → user stories, сценарии GIVEN/WHEN/THEN, граничные случаи, свойства для property-based тестов |
| 3 | `design.md` | **Архитектор** | proposal + spec → техническое решение (опционально для небольших изменений) |
| 4 | `tasks.md` | **Планировщик** | spec + design → атомарный чек-лист задач |
| 5.1 | тесты | **Тестировщик** — отдельная роль, до реализации, пишет только из `spec.md` | свойства спецификации → исполняемые тесты |
| 5.2 | код **или** документ | **Реализатор** / **Документатор** (`doc-only`) | `tasks.md` + `spec.md` → реализация под тесты, либо документ по спецификации |
| 6 | `verify.md` | **Ревьюэр** | артефакты + тесты (если есть) + spec + tasks → отчёт ✅/❌ с маршрутизацией |
| 7 | архив | **Оркестратор / автоматизация** | verify весь ✅ → спецификации обновлены |

Каждая роль работает в собственной сессии агента (отдельный запуск
субагента). Оркестратор может совмещать роли на разных изменениях, но
никогда — в рамках одного результата работы (deliverable).

## 2. Семь шагов и гейты

### Шаг 1 — Proposal (Аналитик)
Отвечает на вопросы *зачем* и *что* меняется, без деталей поведения и
технических решений. Разделы: `Why`, `What Changes`, `Capabilities`
(ADDED/MODIFIED/REMOVED).

**Гейт:** `Why` присутствует, `What Changes` непустой, список capability
явно указан. Провал → возврат к Аналитику.

### Шаг 2 — Spec (Аналитик)
Поведенческий контракт: каждое требование proposal развёрнуто в user
stories, варианты использования, проверяемые сценарии `GIVEN / WHEN /
THEN`, граничные случаи и — там, где ожидается исполняемое поведение —
выведенные **свойства для property-based тестов (P1, P2, …)**. Источник
истины для Тестировщика — спецификация, а не код. Если поведение не
описано в спеке — его не существует.

**Гейт:** у каждого требования ≥1 сценария; граничные случаи перечислены;
свойства PBT выведены (для кодовых изменений). Провал → возврат к
Аналитику.

### Шаг 3 — Design (Архитектор)
Технический план: структуры данных, алгоритмы, компромиссы. Не может
противоречить спеке; при конфликте спека правится осознанно (Аналитиком),
а не обходится молча. Опционален для небольших изменений, обязателен, когда
есть выбор между решениями.

**Гейт:** design ссылается на спеку и не вводит требований, отсутствующих
в ней. Провал → возврат к Аналитику (пересмотр спеки), а не молчаливая
правка design.

### Шаг 4 — Tasks (Планировщик)
Атомарные, по отдельности проверяемые задачи, каждая трассируема к сценарию
или свойству. Следует `openspec-rules.md`: нумерация FR, волновые группы,
калибровка размера (одна задача = один запуск исполнителя, < 10 минут,
механический критерий останова), строка `Maps to scenarios:`.

**Гейт:** каждая задача — чекбокс и трассируется к сценарию/свойству;
волновая структура валидна. Провал → возврат к Планировщику.

### Шаг 5 — Apply (Тестировщик → Реализатор / Документатор)
Две различные роли, именно в этом порядке:

**5.1 Тестировщик пишет тесты ДО реализации** — только из `spec.md`
(свойства P1–P3 …), никогда из кода. Благодаря этому тесты проверяют
требования, а не подгоняются под реализацию.

**5.2 Реализатор пишет реализацию под эти тесты.** Вход: `tasks.md` +
`spec.md`. Реализатор никогда не правит тесты: падающий тест — это баг в
реализации. Свойства меняются только путём осознанной правки спеки
Аналитиком.

**doc-only путь (документационные результаты):** шаг 5.1 пропускается (нет
исполняемого контракта; свойство «документ соответствует спеке»
проверяется чтением). Роль Реализатора выполняет **Документатор** —
отдельный агент, чья единственная работа — произвести документ по
`spec.md` + `design.md`; задача помечается `doc-only` в `tasks.md`. Если
изменение содержит и код, и документацию, Документатор запускается
отдельной сессией, при желании — параллельно. Ревью всё равно проводится
(шаг 6) — семантическая проверка: полнота, согласованность, отсутствие
требований, которых нет в спеке.

**Гейт:** для кода — тесты не изменялись с момента написания
Тестировщиком; Реализатор не касался файлов тестов. Для doc-only — задача
помечена `doc-only`, артефакт создан, Документатор не правил файлы спек.
Провал → возврат к шагу 5.

### Шаг 6 — Verify (Ревьюэр)
Проверка соответствия спеке, а не ревью стиля. Для каждого сценария и
свойства: покрыто тестом и проходит на реализации (код), либо документ
соответствует сценариям и не добавляет ничего нового (doc-only). Также:
тесты не тавтологичны; все пункты `tasks.md` закрыты. Ревьюэр ничего не
правит — он создаёт `verify.md` (✅/❌) и маршрутизирует провалы: пробел в
тестах → Тестировщику, падающий тест → Реализатору, противоречие спеке →
Аналитику, неполный документ → Документатору.

**Гейт:** в `verify.md` только ✅ → переход к шагу 7. Любой ❌ → маршрутизация
назад и повтор затронутого шага.

### Шаг 7 — Archive (Оркестратор / автоматизация)
Запускается только после того, как verify весь ✅. Дельта-спека из
`changes/<name>/specs/` вливается в постоянные `openspec/specs/`, папка
изменения перемещается в `changes/archive/<date>-<name>/`. Механическая
операция, обычно через CLI (`openspec archive <name>` / `/opsx:archive`).
С этого момента требование — постоянный закон для всех будущих изменений.

## 3. Связь с `openspec-rules.md`

* Шаги 1–4 = работа «сильная модель / человек» согласно файлу правил.
* Результат шага 4 = волны + нумерация FR + калибровка размера, определённые там.
* Шаг 5 = запуски исполнителя: один запуск субагента = одна задача (FR);
  исполнитель коммитит после каждого завершённого этапа.
* Тяжёлая верификация — отдельная задача (шаг 6 выполняется в своём запуске).
* Архив (шаг 7) соответствует соглашениям `openspec/changes/archive/`.

## 4. Язык

Все артефакты (`proposal.md`, `spec.md`, `design.md`, `tasks.md`,
`verify.md`) и контекстные файлы процесса пишутся на английском, если
правила проекта не говорят иного. Тела сценариев внутри спек могут быть на
предметном языке проекта, если этого требует потребляющий их рантайм
(например, русский Gherkin для 1С/Vanessa), при этом сам документ спеки
остаётся на английском.

## 5. Минимальный ранбук (глазами пользователя)

1. Сформулируйте изменение простыми словами (например, «хочу записывать
   расходы и видеть месячную сумму по категории»); подтверждайте граничные
   случаи, когда спрашивают.
2. Оркестратор ведёт шаги 1–7, запуская по одной роли на шаг и сообщая
   результаты гейтов.
3. Вы вмешиваетесь только когда гейт проваливается настолько, что
   Оркестратор маршрутизирует возврат к вам (вопросы объёма, конфликты
   спек) либо на финальном verify ✅.
