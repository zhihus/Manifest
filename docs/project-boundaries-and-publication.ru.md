# Границы проекта и правила публикации

## 1. Независимость проектов

Этот репозиторий — самостоятельный проект со своим назначением, архитектурой,
планом развития, исходным кодом, документацией и критериями качества.

Другие проекты могут использовать его функциональность, если она им подходит.
Повторное использование необязательно и само по себе не является основанием
для изменения архитектуры или требований этого проекта.

Не дорабатывайте один проект под внутренние потребности другого. Интеграция
между проектами допускается только через явно определённые и согласованные
контракты. Каждый потребитель самостоятельно решает, подключать ли интеграцию.

## 2. Локальная разработка

Локальная рабочая копия может содержать несколько веток, временные файлы,
эксперименты, отчёты, вспомогательные скрипты, локальные конфигурации,
тестовые данные и другие материалы, необходимые разработчику.

Наличие файла в локальном проекте не означает, что он является частью продукта
или должен попасть в GitHub. Локальные материалы могут оставаться только
на компьютере разработчика.

Не создавайте приватные GitHub-репозитории или приватные зеркала для хранения
локальной разработки. Рабочие варианты и вспомогательные материалы хранятся
локально.

## 3. Единственная публичная ветка

Публичная ветка этого проекта: `develop`.

Разработка может вестись в нескольких локальных ветках. Перед публикацией
отобранные изменения интегрируются в публичную ветку. В GitHub отправляется
только эта ветка; рабочие локальные ветки не публикуются.

Не меняйте публичную ветку, не выполняйте push и не публикуйте дополнительные
ветки без явного разрешения пользователя. Не создавайте параллельные публичные
линии разработки.

## 4. Дистиллированный состав GitHub

Публичный репозиторий содержит только дистиллированный состав проекта:
файлы, необходимые для использования, сборки, проверки, сопровождения
и понимания самого продукта.

Перед публикацией исключите:

- персональные данные, идентификаторы и контактные данные;
- сведения о заказчиках, их процессы, документы и примеры, позволяющие их
  идентифицировать;
- локальные пути, имена пользователей и сведения об окружении разработчика;
- секреты, токены, пароли, приватные ключи и локальные конфигурации;
- временные файлы, scratch-каталоги, промежуточные результаты и личные отчёты;
- резервные копии, локальные базы и выгрузки, не являющиеся частью продукта;
- материалы других проектов, не входящие в явно определённый публичный
  контракт этого проекта.

Анонимизация должна быть реальной: замена имени на плейсхолдер недостаточна,
если по контексту можно восстановить заказчика или человека. Используйте
синтетические примеры. Не ослабляйте проверки и не удаляйте защитные тесты
ради прохождения публикационного контроля.

## 5. Проверка перед публикацией

Перед каждым push в `develop`:

1. Проверьте diff относительно предыдущего состояния публичной ветки.
2. Проверьте весь набор добавленных, изменённых и удалённых файлов, включая
   новые и неотслеживаемые файлы.
3. Подтвердите, что каждый публикуемый файл относится к назначению этого
   проекта и нужен для его публичного использования или сопровождения.
4. Проверьте отсутствие персональных данных, материалов заказчиков,
   локальных путей, секретов и посторонних файлов.
5. Выполните применимые тесты и проверки самого проекта.
6. Публикуйте только проверенный результат в `develop`.

Не синхронизируйте локальную рабочую папку с GitHub целиком. Публикация —
это осознанный отбор проверенных изменений, а не зеркалирование файлов.

## 6. Обязательность правил

Эти правила обязательны для всех агентов и участников разработки. При
сомнении, относится ли файл к публичному продукту, не публикуйте его:
зафиксируйте вопрос и запросите решение пользователя.
